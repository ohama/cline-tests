<objective>
Satisfy SVC-05 (criterion 4) and leave Phase 6 a standing gate of its own.

Purpose: `sync.sh` mirrors only the labels named in a hardcoded bash `LABELS=(...)` array — it does
NOT glob `~/Library/LaunchAgents/*.plist`. So running it changes nothing for the two new services,
and worse, `./sync.sh --check` would cheerfully report "실제 시스템과 일치한다" while two brand-new
plists sit untracked. That is the same shape of vacuous pass this project has already had to design
around twice. The array must be edited — and it lives in `~/local-llm-settings/`, outside this
repo's git history, so the change has to be captured here or it is invisible forever.

Separately, Phases 2 and 3 each left a standing, read-only, re-runnable gate. Phase 5 owes Phase 6
the same for its two services.

Output: an edited `~/local-llm-settings/sync.sh`, a synced mirror, `phase-05/services/verify_services.sh`,
and evidence.

**Budget: ZERO `cline` invocations.** `verify_services.sh` deliberately reads the plists itself
rather than calling `check_versions.sh` (whose Check B spends one cline invocation per run) —
`check_versions.sh` stays the deliberate drift gate, run on purpose, not from inside a health check.

**House rule reminder:** `~/local-llm-settings/` is a live→mirror snapshot and its *mirrored
content* is never hand-edited. `sync.sh` is the tool, not the snapshot, so editing its `LABELS`
array is the sanctioned way to track a new service — but the edit stays minimal and additive, and
the mirrored `launchagents/*.plist` files are still only ever written by `sync.sh` itself.
</objective>

  <name>Task 2: phase-05/services/verify_services.sh — the standing gate for Phase 6</name>
  <files>phase-05/services/verify_services.sh, phase-05/results/</files>
  <action>
Write a read-only, re-runnable gate in the same shape as `phase-02/infra/verify_no_regression.sh`
and `phase-03/sandbox/verify_sandbox.sh`: it mutates nothing, restarts nothing, prints one
`CHECK: PASS|FAIL <name>` line per assertion, and follows the house 3-way exit contract —
`0` all pass, `1` at least one FAIL, `2` inconclusive (a probe itself crashed; never report that
as a pass). `#!/bin/bash`, `set -uo pipefail`, sources `phase-05/services/config.env`,
`--out-dir <dir>` flag defaulting to a timestamped dir under `$RESULTS_ROOT`.

Header must state, in this order: this is Phase 5's standing gate, Phase 6 should call it before
and after opening anything to the network, it never calls `check_versions.sh` (that spends a
`cline` invocation — run it deliberately, not from a health check), and it never restarts or kills
anything.

Assertions:
1. For each of `$KANBAN_LABEL` and `$TELEGRAM_LABEL`: `launchctl print gui/$(id -u)/<label>`
   succeeds and reports `state = running` with a non-empty pid.
2. **Settled, not looping:** sample each pid three times over ~20s; all three identical. A service
   that is "running" because it keeps being restarted must FAIL here. This is the check that makes
   the whole gate non-vacuous.
3. Kanban: `lsof -nP -iTCP:$KANBAN_PORT -sTCP:LISTEN` non-empty AND held by the pid launchctl
   reported; `curl -s -o /dev/null -w '%{http_code}' -m 5 http://$KANBAN_HOST:$KANBAN_PORT/`
   returns a 3-digit code that is not `000` (any status is fine — the default passcode makes a
   401/302 the correct answer).
4. **Anti-orphan:** `ps -o args= -p <kanban pid>` shows the sandbox-exec/kanban chain;
   `pgrep -f 'connect telegram' | wc -l` is `0` whenever the installed plist's
   `TELEGRAM_BOT_TOKEN` is empty, and the connector log contains no
   `starting background connector pid=` line. If the token is non-empty, print an INFO line saying
   the orphan assertion is relaxed and that the pid must instead be the connector itself with `-i`.
5. **Port hygiene (Phase 6 precondition):** neither service pid appears in
   `lsof -nP -iTCP:3000 -sTCP:LISTEN`.
6. **Pin gates:** read both installed plists with `plutil -convert json` + `python3` and assert
   `CLINE_NO_AUTO_UPDATE=1` in both and `KANBAN_NO_AUTO_UPDATE=1` in both. No binary is invoked.
7. **Sandbox boundary unchanged:** `EXTRA_ALLOW_PATHS` is empty (source
   `phase-03/sandbox/config.env` in a subshell).
8. **Log growth watch:** report the byte size of each of the four log files under
   `$SERVICE_LOG_DIR`, and emit a WARN (not a FAIL) above 10 MB. launchd never rotates these; the
   gate's job is to make unbounded growth visible rather than to silently rotate.
9. **Mirror freshness (SVC-05 standing):** both labels appear in `~/local-llm-settings/sync.sh`'s
   `LABELS` array and both mirrored plists are byte-identical to the live ones.

Run it twice back to back with both services live, capturing both transcripts into
`phase-05/results/<ts>-gate/`. Both runs must exit 0 with identical CHECK lines (re-runnability is
part of the contract, not an afterthought).
