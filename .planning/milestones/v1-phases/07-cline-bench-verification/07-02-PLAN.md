<task type="auto">
  <name>Task 1: Can the container's Cline be given contextWindow=29000? Decide from source.</name>
  <files>phase-07/bench/config.env, phase-07/results/</files>
  <action>
The known problem: this project proved (`docs/32k-compaction-policy.md` §2) that compaction only
works when `contextWindow` sits at the **top level of `settings`** in `providers.json`, and that
the value must be **29000**, not 32768, to absorb the measured 2,700-3,100 token overshoot before
the server's `prompt_tokens + max_tokens <= 32768` ceiling. Harbor's `cline-cli` adapter installs
an unconfigured Cline inside each container, where an `openai-compatible`-family provider falls
back to `contextWindow = maxInputTokens = 128_000`. Compaction would then not fire until ~115,200
tokens — long after our server has already returned a hard 400.

Investigate, in this order, and record each avenue's result verbatim (command + output) in
`phase-07/results/<UTC>-ctxwindow/FINDING.md`:

  A. Read the INSTALLED adapter source, not a remote copy. Locate it:
     `find "$(dirname "$(command -v harbor)")/.." -name cline.py -path '*agents*' 2>/dev/null`
     or `python3 - <<'PY'`-style import-path resolution against the uv tool venv. Quote its
     `run_flags` / `CLI_FLAGS` / env dict / `PROVIDER_API_KEY_ENVS` verbatim into FINDING.md.
  B. `harbor run --help` and `harbor --help` — enumerate every `--agent-kwarg` key the cline
     adapter actually accepts. Record the literal list.
  C. Does the adapter forward arbitrary host env into the container, or only a fixed template?
     If it forwards a fixed set, name the set. Check specifically whether `BASE_URL` and
     `API_KEY` are in it (this also settles research Open Question 2 from the source side; the
     smoke run settles it empirically).
  D. Is there any documented Cline env var or config path that sets the context window? Consult
     `docs/cline-config-pins.md` (which already records the installed 3.0.53 `--help` surface)
     and, read-only, `strings /opt/homebrew/bin/cline | grep -i 'contextwindow\|CLINE_CONTEXT'`.
     Note that `CLINE_SANDBOX_DATA_DIR` relocates config but does not configure it, and that a
     container cannot see host paths anyway.
  E. Is there a bind mount into the container that we control WITHOUT editing `task.toml`?
     Read harbor's docker environment module and its compose files. If the only way in is
     editing a task file or patching harbor, the answer is no.

Then write the VERDICT section, one of exactly two:
  - `INJECTABLE` — name the exact mechanism and append the resulting extra arguments to
    `phase-07/bench/config.env` as `HARBOR_EXTRA_ARGS` (and set `CW_INJECTION=applied`), with a
    comment quoting the source line that makes it work.
  - `NOT-INJECTABLE` — set `CW_INJECTION=none` and `HARBOR_EXTRA_ARGS=""` in `config.env`, and
    write the consequence plainly in FINDING.md: the container's Cline will assume 128k, our
    server hard-rejects `prompt + max_tokens > 32768`, so some tasks are expected to die with a
    clean HTTP 400 a few turns in. **That is a real, disclosable BCH-03 result with a named
    cause — a `fail-context` row, not an excluded outlier and not a broken harness.**

Explicitly record as OUT OF SCOPE, with the reason, so nobody revisits it mid-run: patching
harbor, editing any task file, and changing litellm/role-shim configuration (the last would
require restarting a live service — a Phase 2 posture change this phase is not permitted to make).
  </action>
  <verify>
`grep -c 'VERDICT: \(INJECTABLE\|NOT-INJECTABLE\)' phase-07/results/*-ctxwindow/FINDING.md` is 1.
`grep -E '^(CW_INJECTION|HARBOR_EXTRA_ARGS)=' phase-07/bench/config.env` returns exactly 2 lines.
FINDING.md quotes at least the adapter's flag list and the `harbor run --help` agent-kwarg list
verbatim. `bash phase-01/config/verify_config.sh` exits 0 (host providers.json untouched).
  </verify>
  <done>The contextWindow question has a sourced, written answer; `config.env` carries the
decided invocation either way; the host config is provably unchanged.</done>

<task type="auto">
  <name>Task 2: run_task.sh — one task in, one evidence bundle out</name>
  <files>phase-07/bench/run_task.sh</files>
  <action>
Write `phase-07/bench/run_task.sh <task-dir-name> [--run-dir <path>]`. It sources `config.env`.
Behaviour:

  1. **Run directory.** If `--run-dir` is absent, read `$CURRENT_RUN_FILE`; if that is absent,
     create `bench/runs/$(date -u +%Y%m%dT%H%M%SZ)-phase07/` and write its path into
     `$CURRENT_RUN_FILE`. **All tasks in this phase land in ONE run directory** — criterion 1
     asks for a result directory holding the run, and criterion 3 asks for one table.
     Skip-if-done: if `<RUN>/meta/<task>.json` already exists, print `unchanged: <task>` and
     exit 0. That makes the batch resumable after an interruption without re-burning model time.
  2. **Pre-guards (abort, do not run, on any failure):** six pids present;
     `lsof -nP -iTCP:3000 -sTCP:LISTEN` empty; free disk >= `MIN_FREE_GIB`; the task directory
     exists under `bench/cline-bench/tasks/`; `$FLASHNEXT_ERR_LOG` readable.
  3. **Server-log offset.** Record `wc -c < "$FLASHNEXT_ERR_LOG"` as `OFF_BEFORE`.
  4. **Prompt capture, BEFORE the run** (so it exists even if the run dies):
     `<RUN>/prompts/<task>/instruction.md` — a verbatim `cp` of the task's `instruction.md`.
     This file is the agent prompt: harbor passes it to cline as the trailing `-- <prompt>`
     argument. `<RUN>/prompts/<task>/task.toml` — verbatim copy, so the prompt's execution
     parameters (timeout, memory) are recorded next to it.
  5. **The run.** Time it with `SECONDS`/`date +%s` around the call. Invoke, from `$BENCH_REPO`:
     `API_KEY="$HARBOR_API_KEY" BASE_URL="$HARBOR_BASE_URL" harbor run -p tasks/<task> -a "$HARBOR_AGENT" -m "$HARBOR_MODEL_SPEC" --agent-kwarg cline-version="$HARBOR_CLINE_VERSION" $HARBOR_EXTRA_ARGS --env docker`
     Tee all stdout/stderr to `<RUN>/logs/<task>.harbor.log`. Do NOT wrap this in
     `run_sandboxed.sh` (house rule 4). Capture harbor's exit code without `set -e` aborting.
  6. **Post-guards:** port 3000 still unbound (fail loudly if harbor published it); six pids
     unchanged (record any that moved — a restarted service is a finding, not something to
     silently absorb).
  7. **Collect harbor's own output.** Find the newest `jobs/<timestamp>/` created since the run
     started, and copy its trial directory tree to `<RUN>/jobs/<task>/`. Copy verbatim; do not
     reformat. Then, from the copied tree, extract:
     `<RUN>/prompts/<task>/agent-command.txt` <- concatenation of every
       `agent/command-*/command.txt` (harbor's own record of the exact resolved command,
       including the literal prompt argument and the resolved `-P` provider id).
     `<RUN>/prompts/<task>/system-prompt-probe.txt` <- the output of grepping
       `agent/cline.txt` case-insensitively for a system-prompt marker (e.g. `you are cline`,
       `<system>`, `system_prompt`), with line numbers, plus a one-line verdict
       `SYSTEM_PROMPT_IN_TRANSCRIPT: yes|no`.
     If any expected file is missing, write a `MISSING <path>` line into
     `<RUN>/prompts/<task>/CAPTURE-GAPS.txt` rather than failing — a gap must be visible, not fatal.
  8. **Server-side oracle slice.** `tail -c +$((OFF_BEFORE+1)) "$FLASHNEXT_ERR_LOG" >
     <RUN>/server-log/<task>.flashnext.err.txt`. This is a passive read of a log the model server
     already writes — no service configuration is changed and nothing is restarted. It yields,
     per request: `prompt_tokens`, `max_tokens`, TTFT, decode rate, `finish_reason`, `in_flight`.
     Warn in a comment that this log is shared: concurrent traffic from other surfaces may appear
     in the slice, so it bounds rather than isolates this task's turns.
  9. **Meta record** `<RUN>/meta/<task>.json` with: task dir name, suffix, difficulty,
     memory_mb, timeout_sec, harbor exit code, wall-clock seconds, `reward` (read from
     `verifier/reward.txt`, or `null`), harbor's own `duration_sec` from `result.json` if present,
     model turn count (count of `Request completed:` lines in the server-log slice),
     `max_prompt_tokens` (max `prompt_tokens=` seen in the slice), `http_400_seen`
     (whether the slice or `agent/cline.txt` shows a 400), `system_prompt_in_transcript`, and a
     `verdict` field set to exactly one of:
       `pass`         reward == 1
       `fail-task`    reward == 0 and no 400 and the agent visibly worked
       `fail-context` a 400 / context-window rejection is present, or `max_prompt_tokens` >= 32768
       `fail-infra`   harbor failed before any model request (image build, OOM, harness error)
     Write the verdict rule as a comment in the script so the classification is auditable.
 10. Append a one-line record to `<RUN>/MANIFEST.txt` for every file written.

Do NOT run any task in this plan — 07-03 runs the first one. Verify the script by
`bash -n phase-07/bench/run_task.sh` and by a `--dry-run` mode that prints the exact harbor
command it WOULD run and exits 0 without touching Docker.
  </action>

<task type="auto">
  <name>Task 3: make_summary.sh (BCH-03 table) + verify_bench.sh (re-runnable gate)</name>
  <files>phase-07/bench/make_summary.sh, phase-07/bench/verify_bench.sh</files>
  <action>
`phase-07/bench/make_summary.sh [--run-dir <path>]` walks `<RUN>/meta/*.json` and writes
`<RUN>/summary.md`:
  - A header stating: the live task pool size, how many were run, that percentage, the
    cline-bench commit SHA, the harbor version, the model spec, and the `CW_INJECTION` value
    from `config.env`.
  - **One table, all rows** — columns: `task` | `difficulty` | `verdict` | `reward` |
    `wall_clock_s` | `model_turns` | `max_prompt_tokens` | `note`. Every task that was attempted
    gets a row, including `fail-context` and `fail-infra` rows. Tasks deliberately not run get a
    `not-run` row with the reason. **No task is ever omitted from the table.**
  - A totals line: `pass`/`fail-task`/`fail-context`/`fail-infra`/`not-run` counts and total
    wall-clock.
  - A short **한계** section, mandatory, stating in plain language: a `fail-context` row proves
    the pipeline reached the model and the request was rejected by the 32K ceiling because the
    container's Cline was unconfigured — it is NOT evidence that this stack cannot complete
    agent tasks, and a `pass` row is NOT evidence that the whole 14-task suite would pass.
  Derive pass/fail ONLY from `verifier/reward.txt` (harbor's own binary score). Do not
  hand-write a grader over test output.

`phase-07/bench/verify_bench.sh [--run-dir <path>]` — read-only, re-runnable, exit 0/1/2, one
`CHECK: PASS|FAIL <id>` line per check plus a final `CASES n/m`, same contract as
`phase-06/net/verify_network.sh`. Checks:
  B1  the run directory exists and `config.json` in it names harbor version, cline-bench SHA,
      model spec and BASE_URL
  B2  `meta/*.json` count >= 1 and every one parses as JSON with a `verdict` in the allowed set
  B3  **BCH-02 (prompt half)**: for EVERY task with a meta record,
      `prompts/<task>/instruction.md` exists and is non-empty, AND
      (`prompts/<task>/agent-command.txt` exists and is non-empty, **OR**
      `prompts/<task>/CAPTURE-GAPS.txt` names the missing file AND that task's meta `verdict` is
      `fail-infra`). The escape valve exists because it is a real, planned-for outcome, not a
      loophole: when harbor dies before it ever launches cline inside the container, it never
      writes `agent/command-*/command.txt`, so `agent-command.txt` cannot exist — the same
      tolerance B4 already grants the result half. It is scoped tightly: `instruction.md` is
      required unconditionally (this phase copies it itself, before the run, so nothing harbor
      does can prevent it), and the excuse is only accepted for `fail-infra`. A task that reached
      the model — `pass`, `fail-task` or `fail-context` — must have a real `agent-command.txt`.
      A transcript never satisfies this check: `agent/cline.txt` is deliberately not accepted as
      the prompt artifact, and is not an acceptable substitute under the escape valve either.
      Emit `CHECK: PASS B3` with a trailing `(N task(s) excused as fail-infra)` note when the
      valve is used, so the exemption is visible in the gate output rather than silent.
  B4  **BCH-02 (result half)**: for every task, `jobs/<task>/**/verifier/reward.txt` exists, or a
      `CAPTURE-GAPS.txt` explains why not
  B5  **BCH-03**: `summary.md` exists, contains a table, and its data-row count equals the meta
      record count
  B6  `server-log/<task>.flashnext.err.txt` exists for every task
  B7  **SBX-04 re-assertion**: `bash phase-03/sandbox/verify_sandbox.sh` exits 0 and its SBX-04
      criterion is PASS — i.e. `bench/runs/CANARY.txt` is still unreadable from inside the
      sandbox after this phase wrote results next to it
  B8  `workspace/ALLOWED_REPOS.json` still contains no `bench` entry and no repo-root entry
  B9  `bench/runs/CANARY.txt` still exists with its original single line
  B10 port 3000 unbound; six pids present
Take `--run-dir`; default to `$CURRENT_RUN_FILE`. Never write anything except its own optional
`--out` transcript.

Guard against house rule 9: both scripts talk about paths and criteria that they also grep for.
Keep every literal used as a grep needle in a variable defined once at the top, and run the
plan's own verification greps against the two files before committing.
  </action>
