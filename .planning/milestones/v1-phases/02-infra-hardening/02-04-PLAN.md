end to end, then make the change durable and reversible — sync the mirror and write the record.

both depend on this stack staying healthy, and they should be able to call this one script.

<constraints>
HARD:

- **This plan makes no further service changes.** No plist edit, no bootout, no bootstrap, no restart.
  If the regression gate fails, the response is to report and to point at the two rollback blocks in
  plans 02-02 and 02-03 — not to start improvising fixes against a live stack.
- **`sync.sh` direction is live -> mirror, always.** Run `~/local-llm-settings/sync.sh` and let it copy
  `~/Library/LaunchAgents/*` into the mirror. Never hand-edit the mirror, never copy mirror -> live.
- **Timeouts must be generous.** Measured TTFT at 32K context on this machine is 64.3s. This gate uses a
  tiny prompt and `max_tokens: 8`, so it should be fast, but `-m 180` stays so a slow-but-correct
  response is a PASS rather than a flaky FAIL.
- **Do not invoke `cline`** — it self-updates on nearly every call in this environment. Plain `curl`
  only. Do not run `sudo sysctl`. Do not load a second model. Nothing heavy concurrently (headroom at
  32K is 4.39 GB).
- bash is 3.2 (no `declare -A`); the shell is zsh (wrap flag word-splitting in `bash -c '...'`).
</constraints>

  <files>phase-02/infra/verify_no_regression.sh, phase-02/results/</files>
  <action>
Create `phase-02/infra/verify_no_regression.sh` — `#!/bin/bash`, `set -euo pipefail`, executable,
sources `config.env`, accepts `--out-dir <dir>` (defaults to a fresh
`$RESULTS_ROOT/$(date -u +%Y%m%dT%H%M%SZ)-inf03`). It changes nothing and must be safe to re-run at any
time by any later phase. Every check reports PASS/FAIL individually into
`<out-dir>/inf03-verdict.txt`; the script exits non-zero if any check FAILs.

Checks in order — cheapest and most diagnostic first, so a failure localizes the broken hop:

1. **Both hardening flags still in place.** `/usr/libexec/PlistBuddy -c "Print :ProgramArguments"` on
   each of the two plists; assert `--max-num-seqs` + `$MAX_NUM_SEQS` in flashnext's and `--host` +
   `$LITELLM_BIND_HOST` in litellm's. This makes the script a standing guard against silent reversion,
   not just a one-shot check.
2. **All three services running.** `launchctl print "gui/$(id -u)/<label>"` shows `state = running` for
   flashnext, role-shim and litellm. Record each pid.
3. **Hop 3 (model server) alive.** `curl -s -m 60 -o <out>/models-8000.json -w '%{http_code}'
   http://127.0.0.1:8000/v1/models` == 200.
4. **Hop 2 (role-shim) alive.** Same against `http://127.0.0.1:8011/v1/models` == 200. If role-shim does
   not implement `/v1/models`, fall back to asserting the port accepts a TCP connection
   (`nc -z -G 5 127.0.0.1 8011`) and record which oracle was used — do not report a FAIL for a route
   that simply does not exist on that hop.
5. **Hop 1 (litellm) alive and still advertising the alias.** `curl -s -m 60
   http://127.0.0.1:4000/v1/models` == 200 and the body contains `flashnext`.
6. **THE GATE — full chain, real completion.** This is the check ROADMAP Success Criterion 3 asks for:
   ```
   curl -s -m 180 -X POST http://127.0.0.1:4000/v1/chat/completions \
     -H 'Content-Type: application/json' \
     -d '{"model":"flashnext","messages":[{"role":"user","content":"say hi"}],"max_tokens":8}' \
     -o <out>/chain-response.json -w '%{http_code}'
   ```
   PASS requires HTTP 200 AND, parsed with `python3 -c` + `json`, a non-empty
   `choices[0].message.content`. A 200 carrying an error object or an empty string is a FAIL — record
   the body. Also record the response `usage` block if present, since it is the same oracle Phase 1's
   verification relied on.
7. **Same call via the `localhost` hostname**, not the IP:
   `http://localhost:4000/v1/chat/completions`, same body, same assertions. The four existing consumers
   on this machine all use the hostname form, and `/etc/hosts` maps `localhost` to both `127.0.0.1` and
   `::1` while litellm is now bound v4-only. Expected to pass (getaddrinfo returns IPv4 first here and
   curl falls back), asserted because a FAIL is a real consumer-facing regression.
8. **Serialization did not deadlock the server.** Fire one more single small request at
   `:8000` directly and require a normal 200 with content — a cheap guard that `--max-num-seqs 1` caps
   concurrency without wedging the queue for sequential traffic.

Final line: `INF03: PASS` or `INF03: FAIL <check>`.

Run it now:
`bash phase-02/infra/verify_no_regression.sh` — it must print `INF03: PASS`.

If it FAILs, do not attempt repairs here. Report which hop failed, attach `inf03-verdict.txt`, and name
the applicable rollback block: plan 02-02's constraints block for flashnext, plan 02-03's for litellm.
If check 6 fails but checks 3-5 pass, the fault is in the chain wiring rather than in either service —
roll back the litellm bind FIRST (it is the cheaper restart and the likelier culprit for a routing
change), re-run this gate, and report the result of that bisection.
  </action>

`python3 -c "import json,sys;d=json.load(open('phase-02/results/'+sys.argv[1]));assert d['choices'][0]['message']['content'].strip()" <path-to-chain-response.json>`
succeeds.
`grep -E '^(PASS|FAIL)' phase-02/results/*-inf03/inf03-verdict.txt | grep -c '^FAIL'` returns 0.
Re-running the script a second time also exits 0.
  </verify>
