<constraints>
HARD — these apply to every task in this plan, and this plan is the one that must not break them:

- **This plan performs ZERO live mutations.** No `launchctl bootout`, no `bootstrap`, no `kickstart`,
  no plist edit, no `sync.sh`. It only *writes scripts* and *reads/observes*. The restart helper is
  authored here but not invoked against any service here.
- **HOUSE RULE (from `~/projs/qwen38-flash-next-tests/scripts/llm_services.sh`): never `kill`, never
  `pkill`, never `launchctl load`/`unload`.** All three plists are `KeepAlive: true`; `flashnext` also
  has `ThrottleInterval: 60`. Killing gets the process relaunched with launchd's in-memory (old) job
  definition and burns the throttle window. The only correct cycle is
  `bootout` -> edit -> `bootstrap` -> `launchctl print` verify.
- **`launchctl kickstart -k` is NOT a substitute for bootout/bootstrap** after a plist edit — it
  restarts the already-loaded job definition and does not re-read the file from disk.
- **Never edit anything under `~/local-llm-settings/`.** That tree is a MIRROR; `sync.sh` copies
  live -> mirror only. Editing it changes nothing and gets silently overwritten. The live files are
  `~/Library/LaunchAgents/com.ohama.{flashnext,litellm}.plist`.
- **Do not invoke `cline` anywhere in this phase.** STATE.md records that `cline` self-triggers a
  background `npm update` on essentially every invocation in this environment, including `--version`.
  All verification in Phase 2 uses plain `curl` / `lsof` / `launchctl`.
- **macOS `/bin/bash` is 3.2** — no `declare -A`, no `${var^^}`. Use parallel indexed arrays. The
  invoking shell is **zsh**, so any place a space-separated variable must word-split into argv has to
  be wrapped in `bash -c '...'`.
- Concurrency test prompts MUST be small. RESEARCH.md Pitfall 2: `flashnext.err` already contains a
  genuine single-request Metal OOM at `prompt_tokens=30505`. Two near-32K concurrent requests would
  plausibly crash a live service the user depends on. Small prompts only, always.
</constraints>

**`phase-02/infra/restart_service.sh`** — `#!/bin/bash`, `set -euo pipefail`, executable. Usage:
`restart_service.sh <label> <port> [--timeout SECONDS]` (default timeout 240). Sources `config.env`.
This helper is authored here and invoked by plans 02-02 and 02-03; it is NOT invoked in this plan.

Sequence, exactly. **Immediately before each of steps 2-5, set `CURRENT_STEP` to that step's name** —
this is the variable `print_rollback` reads for the `<what failed>` text in step 7, because an exit code
alone cannot distinguish a lint abort from a failed `bootout`, a failed `bootstrap`, or a poll timeout
(they can all surface the same code). Initialize `CURRENT_STEP="startup"` before step 1.

1. `PLIST="$LAUNCH_AGENTS_DIR/<label>.plist"`. Abort if it does not exist.
2. `CURRENT_STEP="plutil lint"` — then `plutil -lint "$PLIST"`; abort unless it prints `OK`. A malformed
   plist that gets booted out and then fails to bootstrap leaves the service DOWN, so this gate is
   mandatory and comes first.
3. `CURRENT_STEP="bootout"` — then `launchctl bootout "gui/$(id -u)/<label>"`; tolerate a non-zero exit
   whose stderr contains `No such process` (already unloaded); any other non-zero exit aborts.
4. `CURRENT_STEP="bootstrap"` — then `launchctl bootstrap "gui/$(id -u)" "$PLIST"`.
5. `CURRENT_STEP="health poll timeout"` — then poll; do NOT sleep a fixed amount (RESEARCH.md Pitfall 5:
   the flashnext model + MTP drafter needs ~45s from cold in the good case). Loop every 2s until
   `--timeout`: require BOTH `launchctl print "gui/$(id -u)/<label>"` to show `state = running`, AND
   `lsof -nP -iTCP:<port> -sTCP:LISTEN` to return a listener. Print a progress dot per poll.
6. On success print `RESTART OK: <label> pid=<pid> port=<port> waited=<n>s` and exit 0.
7. **Rollback guidance must print on EVERY failure path, not only on the poll timeout.** Define one
   shell function `print_rollback()` and route all failures through it. Because the script runs under
   `set -euo pipefail`, a hard error from `bootstrap` (step 4) or from `plutil`/`bootout` would
   otherwise kill the script before any rollback text is emitted, leaving the operator with a bare
   launchd error and a possibly-down service. Install an `ERR`/`EXIT` trap
   (`trap 'rc=$?; [ "$rc" -ne 0 ] && print_rollback "$rc"' EXIT`) so every non-zero exit — the lint
   abort, an unexpected `bootout` failure, a failed `bootstrap`, and the poll timeout alike — prints
   the same block to stderr before exiting 1.
   `print_rollback` takes the exit code as `$1` but MUST source the `<what failed>` text from
   `$CURRENT_STEP`, not from the code — the code goes in parentheses after it, as `rc=<n>`. So a failed
   bootstrap prints `RESTART FAILED: com.ohama.flashnext (bootstrap, rc=5)` and a poll timeout prints
   `RESTART FAILED: com.ohama.flashnext (health poll timeout, rc=1)`. Never emit a generic
   `<what failed>`; if `CURRENT_STEP` is somehow unset, print `unknown step` rather than guessing.
   ```
   RESTART FAILED: <label> (<$CURRENT_STEP>, rc=<n>)
   ROLLBACK:
     cp -p <BACKUP_DIR>/<label>.plist.<newest-timestamp> ~/Library/LaunchAgents/<label>.plist
     plutil -lint ~/Library/LaunchAgents/<label>.plist          # must print OK
     launchctl bootout   gui/$(id -u)/<label>   # ignore "No such process"
     launchctl bootstrap gui/$(id -u) ~/Library/LaunchAgents/<label>.plist
   ```
   Resolve `<newest-timestamp>` at runtime with `ls -t "$BACKUP_DIR"/<label>.plist.* 2>/dev/null | head -1`
   and print the literal resolved path; print `(no backup found in $BACKUP_DIR)` if there is none.
   The trap must be a no-op on exit code 0.
8. It must contain NO `kill`, NO `pkill`, NO `launchctl load`, NO `launchctl unload`, NO
   `launchctl kickstart`.

**`phase-02/infra/verify_queueing.sh`** — `#!/bin/bash`, `set -euo pipefail`, executable. Usage:
`verify_queueing.sh --label before|after [--concurrency <N>] [--cap <C>] [--out-dir <dir>]`. Sources
`config.env`. This is the INF-01 evidence collector. In `before` mode it records and always exits 0 (it
is a baseline, not a gate); in `after` mode it asserts.

`--cap` defaults to `$MAX_NUM_SEQS` and `--concurrency` defaults to `$((MAX_NUM_SEQS + 1))` — one more
request than the cap allows, which is the minimum that can demonstrate backpressure. This is what makes
the checkpoint's `proceed-2` branch executable without a second script: raising `MAX_NUM_SEQS` to 2 in
`config.env` automatically turns this into a 3-concurrent-request probe asserting a cap of 2. Neither
number may be hardcoded in the script.

Sequence:
1. `OFFSET=$(wc -c < "$FLASHNEXT_ERR")` — capture the log byte offset BEFORE firing anything.
2. Fire `$CONCURRENCY` concurrent requests **directly at `:8000`**, bypassing role-shim and litellm
   (this test exercises server-side admission only; the full chain is plan 02-04's job). Body for each,
   with `"model": "$MLX_MODEL_PATH"`, `"messages":[{"role":"user","content":"count from 1 to 20 slowly, one number per line"}]`,
   `"max_tokens": 60`, `"stream": false`. Small prompts only, whatever N is — never a large one, per
   Pitfall 2. N stays small (2 or 3 in practice); refuse to run with `--concurrency` above 4 and say why.
   The launch loop is plain bash 3.2 — no associative arrays needed:
   ```bash
   i=1
   while [ "$i" -le "$CONCURRENCY" ]; do
     curl -s -m 120 ... -o "$OUT/queueing-$LABEL-r$i.json" -w '%{http_code}' \
       > "$OUT/queueing-$LABEL-r$i.code" 2>"$OUT/queueing-$LABEL-r$i.err" &
     sleep 0.3
     i=$((i + 1))
   done
   wait
   ```
   Record each request's body, HTTP code and curl exit code as `queueing-<label>-r<i>.{json,code,err}`.
3. Slice only the new log: `tail -c "+$((OFFSET + 1))" "$FLASHNEXT_ERR" > <out-dir>/queueing-<label>-log-slice.txt`.
4. Parse the slice with `python3` (bash 3.2 cannot do this cleanly). The log format is confirmed
   verbatim on this machine, e.g.:
   `2026-08-29 19:05:24,847 - INFO - Generation queued: request=82eb4556a0 prompt_tokens=30505 ...`
   `2026-08-29 19:05:24,853 - INFO - Prefill started: request=82eb4556a0 backend=continuous_batching ...`
   `2026-08-29 19:06:24,426 - INFO - Decode started: request=82eb4556a0 time_to_first_token=59.608s`
   `2026-08-29 19:06:26,879 - INFO - Request completed: endpoint=/chat/completions ... in_flight=0`
   Timestamps are `%Y-%m-%d %H:%M:%S,%f`. Correlate per-request by the `request=<hexid>` token.
   `Request completed` lines do NOT carry a `request=` id — associate the Nth `Request completed` with
   the Nth request to reach `Decode completed`, and prefer `Decode completed: request=<id>` (which DOES
   carry the id) as the "A finished generating" marker. Emit a small table per request id:
   queued_at, prefill_started_at, decode_started_at, decode_completed_at.
5. Order the request ids by their `Generation queued` timestamp, so the table reads in submission
   order regardless of N.
6. **The assertion (after mode only).** Compute, in the same python3 pass, the half-open interval
   `[prefill_started, decode_completed]` for each request id — that interval is exactly "this sequence
   occupied a slot in the decode batch". Sweep the interval endpoints to get `max_overlap` (the largest
   number of sequences simultaneously in the batch) and `queued_count` (how many requests had
   `prefill_started >= min(decode_completed of all other requests)`, i.e. were admitted only after some
   earlier request finished decoding). This one sweep generalizes the whole assertion to any N and any
   cap; for the default N=2/cap=1 it reduces exactly to "B's prefill started at or after A's decode
   completed".
   PASS requires all four:
   - every curl exited 0 and every response JSON has a non-empty `choices[0].message.content`
     (i.e. queuing, not OOM, not a 5xx);
   - exactly `$CONCURRENCY` distinct request ids appear in the slice;
   - `max_overlap <= $CAP` — the cap actually held;
   - `queued_count >= $CONCURRENCY - $CAP` — at least the excess requests really were delayed, so the
     pass is not vacuous (N requests that happened never to overlap in time would satisfy the cap
     without demonstrating backpressure).
   Report `max_overlap`, `queued_count`, and the gap in seconds between the earliest
   `decode_completed` and the latest `prefill_started`.
   If the response bodies are fine but either numeric assertion fails, exit 1 with
   `QUEUEING: FAIL (max_overlap=<n> cap=<c> queued_count=<q> need>=<n-c>)`.
   If the expected log lines cannot be found at all, exit 2 with `QUEUEING: INCONCLUSIVE <reason>` —
   do not report a pass you did not observe.
7. **Explicitly encode this caveat in the script's output and in a comment**: the
   `Request started: ... in_flight=<N>` line is expected to reach the full concurrency count even with
   the cap in force, because `in_flight` counts HTTP requests being served, not sequences admitted to
   the decode batch. A high `in_flight` is NOT counter-evidence and must not be used as the pass/fail
   signal. Likewise, N HTTP 200s alone prove nothing — RESEARCH.md Pitfall 3 confirms 2 concurrent
   small requests already succeed today, uncapped, with `in_flight=2`. The interval overlap is the only
   evidence.
8. Final line `QUEUEING: <PASS|FAIL|BASELINE|INCONCLUSIVE> label=<label>`.

Now run the baseline against the **currently uncapped** server, writing into the same results
directory Task 1 created:
`bash phase-02/infra/verify_queueing.sh --label before --out-dir <the dir from Task 1>`

Expect it to record interleaved admission — `max_overlap` equal to the full concurrency, i.e. later

on the baseline being interleaved. In `before` mode the cap is not asserted, only recorded.
