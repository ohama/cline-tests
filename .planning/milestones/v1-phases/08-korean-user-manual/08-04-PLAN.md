<task type="checkpoint:decision" gate="blocking">
  <name>Task 1: Decide whether to widen the sandbox to metadata-only under $HOME</name>
  <decision>
Should `phase-03/sandbox/gen_sandbox_profile.py` be changed so the `$HOME` protection becomes
`deny file-read-data` + `allow file-read-metadata` (instead of `deny file-read*`), which is the
only measured way to make `git worktree add` — and therefore Kanban's per-task worktrees — work?
  </decision>
  <context>
**What is broken without it.** Kanban creates a git worktree per task. Inside the current sandbox
that fails every time, including for a target path inside an already-allowed subpath. Three
call-shape variants (pure relative path, path under an existing allowed subdirectory, pre-created
empty target directory) were each run and each failed identically:
`fatal: Invalid path '/Users/ohama': Operation not permitted`. The kernel log shows repeated
`deny(1) file-read-metadata /Users/ohama`. There is no env var, git flag or call shape that avoids
it, because git realpath-resolves through `/Users/ohama` and this project's whole tree is under
`$HOME`. **No no-widening fix exists — that is a reproduction, not an inference.**

**What the widening would cost, exactly (measured, not estimated).** With
`(deny file-read-data (subpath $HOME))` + `(allow file-read-metadata (subpath $HOME))` and
`file-write*` untouched:
- **Becomes readable:** stat-level metadata for any path under `$HOME` whose name you already
  know — existence, size, permissions, owner, the three timestamps, inode.
- **Stays denied:** file CONTENT (`cat /Users/ohama/.gitconfig` still refused), directory LISTING
  (`ls -la /Users/ohama` still refused — a directory listing is `file-read-data` on the directory,
  so there is no way to enumerate what exists; you must already know the path to stat it), and all
  writes (`file-write*` is not touched).
- Verified alongside: an unrelated project file's content (`cline-analysis.md` at the repo root)
  remained unreadable, and all three worktree variants succeeded with the worktree actually
  present on disk.

**Why it is a code change, not a config value.** macOS Seatbelt does not behave the way this
project's generator comments assume. A rule with a MORE SPECIFIC operation keyword
(`file-read-data`) is not overridden by a rule with a BROADER keyword (`file-read*`), regardless of
which line comes later — demonstrated with a four-way ordering experiment in which both orderings
of `deny file-read-data($HOME)` vs `allow file-read*(repo)` denied, and both same-keyword variants
allowed. So narrowing the `$HOME` deny to `file-read-data` would silently break every currently
allowed path unless `render_profile()` also emits an explicit `(allow file-read-data (subpath …))`
line per punched path. That means editing the generator, its four unit-test assertions, and the
standing gate's precheck, which greps for the old deny line shape.

**What this decision gates.** DOC-02's worktree section. Nothing else in Phase 8 depends on it —
cards, diff review and dependency chains were unblocked separately by plan 08-01 with no widening
at all.
  </context>

      <cons>`git worktree add` stays impossible inside the sandbox, so Kanban's per-task worktrees do not work. DOC-02 must record worktree as unavailable, and DOC-02 is then only partially met — recorded plainly, not promoted.</cons>
    </option>
  </options>
