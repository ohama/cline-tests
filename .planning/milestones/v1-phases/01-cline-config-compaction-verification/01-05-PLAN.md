<objective>
Find out what `max_tokens` Cline actually sends to the server, then decide and apply a mitigation.

Purpose: CFG-03, as redefined. The server's budget is `prompt_tokens + max_tokens ≤ 32768` — it rejects
with HTTP 400 *before* prefill, so an oversized `max_tokens` can 400 a task on turn one even with a tiny
prompt. Research found `providers.json`'s `maxTokens` is NOT honored (two different placements tried;
the server still logged `max_tokens=2048`), root cause unknown. So CFG-03 is not "set a config key" — it
is: observe the real wire value, then choose a mitigation that fits it.

This also gates the regression test. If the effective `max_tokens` is large enough that
`predicted_trigger + max_tokens > 32768` (the trigger being `contextWindow × 0.9 × 0.9`, i.e. 26542 at
the configured 32768), the server 400s before compaction can ever fire, and Plan 06 would measure a contaminated ② that says nothing about compaction. That check must be
settled here, before the live run.

Output: `observed.env` publishing the measured value, a mitigation baked into `apply_provider_config.sh`,
and a findings doc with the verbatim server log evidence.
</objective>
