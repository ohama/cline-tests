<objective>
Build the test inputs and the assertion machinery for this phase — the fixtures, the in-process
probe, and above all the helper that can tell a real kernel denial apart from a crashed process.

Purpose: `03-RESEARCH.md` Pitfall 1 is the single biggest quality risk in Phase 3. A `(deny default)`
profile crashes real binaries with SIGABRT and *zero* stderr, and a naive check of the form
"exit code != 0, therefore the sandbox blocked it" would report that crash as a passing denial test —
a false pass that would let a completely broken sandbox ship as verified. Pitfall 5 adds the mirror
risk: a profile with a typo or a shadowed deny rule fails OPEN while a shallow test still reports
success. Every denial assertion in this phase therefore routes through one helper that (a) demands
a specific denial signal on stderr naming the target, (b) classifies exit > 128 or empty stderr as
CRASHED rather than DENIED, and (c) requires an unsandboxed control of the same command to succeed
first. This plan builds that helper and the fixtures it fires at.

This plan is deliberately independent of plan 03-01 and runs in parallel with it: nothing here
sources `phase-03/sandbox/config.env` or needs a generated profile. `make_fixtures.sh` takes
`--root`, `probe_fs.js` reads paths from env vars, and `assert_denied.sh` takes an explicit
`--profile`. Plan 03-03 (wave 2) is what wires these to the real generator.

Output: three executable artifacts under `phase-03/sandbox/` and a recorded unsandboxed control
baseline under `phase-03/results/`.
</objective>

<task type="auto">
  <name>Task 2: assert_denied.sh — the false-pass-discriminating assertion helper</name>
  <files>phase-03/sandbox/assert_denied.sh</files>
  <action>
This is the quality-critical artifact of the whole phase. Write
`phase-03/sandbox/assert_denied.sh` (`set -uo pipefail` — NOT `-e`, because it must capture failing
exit codes rather than die on them). macOS `/bin/bash` is 3.2: use parallel indexed arrays, never
`declare -A`.

Interface:
```
assert_denied.sh --label <name> --profile <sandbox.sb> --expect deny|allow \
                 [--target <path>] [--expect-stdout <exact string>] \
                 [--write-target <path>] [--skip-control] \
                 -- <command> [args...]
```

Algorithm:

1. **CONTROL run (unsandboxed), unless `--skip-control`:** run `<command>` directly. It MUST exit 0.
   If it does not, emit `CASE <label> FAIL control-failed rc=<rc>` and return 1 — never credit a
   denial to a command that was broken to begin with (a missing fixture, a permission bit, a typo in
   the path). If `--write-target` is given, additionally assert the control run CREATED that file,
   then delete it before the sandboxed run.

2. **SANDBOXED run:** `/usr/bin/sandbox-exec -f "$PROFILE" <command>`, capturing stdout, stderr and
   the exit code to separate temp files.

3. **`--expect allow`:** PASS requires exit 0 AND, when `--expect-stdout` is given, stdout equal to
   that exact string (trailing newline trimmed). A silent empty success is a FAIL, not a pass.

4. **`--expect deny`:** classify, in this order, and emit exactly one verdict:
   - exit code `> 128` → `CASE <label> FAIL crashed-signal rc=<rc>` — this is a CRASHED sandbox
     (03-RESEARCH.md Pitfall 1: `(deny default)` aborts with SIGABRT/134 and no diagnostics), NOT a
     successful denial. Return 2 so the caller can surface it distinctly.
   - exit code `== 0` → `CASE <label> FAIL not-denied` — the sandbox failed open.
   - stderr empty → `CASE <label> FAIL crashed-silent rc=<rc>`, return 2. A non-zero exit with no
     diagnostic is indistinguishable from a crash and must never be counted as a denial.
   - stderr does NOT match `Operation not permitted|EPERM|not permitted` → `CASE <label> FAIL
     wrong-error <first line of stderr>`. Denials must be denials, not ENOENT or anything else.
   - `--target` given and its basename does not appear in stderr → `CASE <label> FAIL
     error-names-wrong-path`.
   - `--write-target` given and the file EXISTS after the sandboxed run → `CASE <label> FAIL
     write-succeeded`.
   - otherwise → `CASE <label> PASS denied`.

5. Always append the full sandboxed stdout/stderr/rc to `$EVIDENCE_DIR/<label>.txt` when
   `EVIDENCE_DIR` is set in the environment, so plan 03-03 gets a durable transcript of every case.

6. Exit codes: `0` = PASS, `1` = FAIL, `2` = CRASHED/inconclusive.

Include a header comment stating plainly: "A non-zero exit code alone is NOT evidence of a sandbox
denial. This helper exists because a `(deny default)` profile crashes real binaries with SIGABRT and
zero stderr, and a naive rc!=0 check would report that broken sandbox as a passing test."
  </action>
  <verify>
Self-test the helper's own discrimination before trusting it. With a throwaway profile
`/tmp/sbx-selftest.sb` containing `(version 1)\n(allow default)\n(deny file-read* (subpath "<abs fixtures>/forbidden"))\n(deny file-write* (subpath "<abs fixtures>/forbidden"))`:
1. deny case passes: `assert_denied.sh --label t-deny --profile /tmp/sbx-selftest.sb --expect deny --target <fx>/forbidden/secret.txt -- /bin/cat <fx>/forbidden/secret.txt` → prints `CASE t-deny PASS denied`, exit 0.
2. allow case passes: same helper `--expect allow --expect-stdout ALLOWED-CANARY-OK -- /bin/cat <fx>/allowed/canary.txt` → exit 0.
3. **fail-open is caught:** re-run case 1 against a profile that is only `(version 1)\n(allow default)` → prints `CASE ... FAIL not-denied`, exit 1.
4. **crash is caught, not counted as a pass:** run `--expect deny` with a command that dies on a signal, e.g. `-- /bin/sh -c 'kill -ABRT $$'` and `--skip-control` → prints `FAIL crashed-signal`, exit 2. This is the anti-false-pass proof; record its output in the summary.
5. **broken control is caught:** `--expect deny --target /nonexistent/x -- /bin/cat /nonexistent/x` → prints `FAIL control-failed`, exit 1 (never PASS).
  </verify>
  <done>All five self-tests behave as specified; in particular a signal-killed process and a fail-open profile both produce FAIL, and a missing target produces control-failed rather than a spurious PASS.</done>

<task type="auto">
  <name>Task 3: probe_fs.js plus the unsandboxed control baseline</name>
  <files>phase-03/sandbox/probe_fs.js, phase-03/results/</files>
  <action>
**Part A — `phase-03/sandbox/probe_fs.js`.** A Node script that is the closest available proxy to
Cline's own tool loop: it exercises in-process `fs` calls (SBX-02) and `child_process.execSync`
subprocesses (SBX-03) inside ONE process, which is what 03-RESEARCH.md verified collapses the two
requirements into one mechanism. Reads `ALLOWED_PATH` and `FORBIDDEN_PATH` from the environment
(fail fast with exit 3 if either is unset). No config.env dependency.

Emits one line per check, exactly: `PROBE <label> <RESULT> <detail>` where RESULT is one of
`SUCCEEDED`, `DENIED`, `ERROR`. Classification rule — this is load-bearing:
  - `DENIED` ONLY when the caught error's `code === 'EPERM'`, or (for `execSync`) the child's exit
    status is non-zero AND its captured stderr matches `Operation not permitted`.
  - `ENOENT`, `EACCES`, `EISDIR` and everything else → `ERROR` with the code in the detail field.
    A missing file must never be reported as a successful block.

Checks (labels are the contract plan 03-03 greps for):
  - `inproc-read-allowed`     : `fs.readFileSync($ALLOWED_PATH/canary.txt)` — expect SUCCEEDED
  - `inproc-read-forbidden`   : `fs.readFileSync($FORBIDDEN_PATH/secret.txt)`
  - `inproc-write-forbidden`  : `fs.writeFileSync($FORBIDDEN_PATH/probe-write.txt, 'x')`
  - `inproc-write-allowed`    : `fs.writeFileSync($ALLOWED_PATH/probe-write.txt, 'x')` — expect SUCCEEDED
  - `subproc-read-forbidden`  : `execSync("/bin/cat '$FORBIDDEN_PATH/secret.txt'")`
  - `subproc-write-forbidden` : `execSync("/bin/sh -c \"echo x > '$FORBIDDEN_PATH/probe-subwrite.txt'\"")`
  - `escape-symlink-read`     : `fs.readFileSync($ALLOWED_PATH/escape-link/secret.txt)` — the
    symlink-inside-allowed-pointing-out case
Finish with a `PROBE-SUMMARY succeeded=<n> denied=<n> error=<n>` line. Exit 0 always (the caller
judges the lines, not the exit code) except for the unset-env fail-fast.

**Part B — record the unsandboxed control baseline.** Create
`phase-03/results/<UTC timestamp>-control/` and capture, WITHOUT any sandbox-exec:
  1. `phase-03/sandbox/make_fixtures.sh` manifest output.
  2. `ALLOWED_PATH=<fx>/allowed FORBIDDEN_PATH=<fx>/forbidden node phase-03/sandbox/probe_fs.js`
     output — every single line must read `SUCCEEDED`, including the forbidden ones and the escape
     symlink. Assert `denied=0 error=0` in the summary line and fail the task if not.
  3. `node --version` and `/usr/bin/sandbox-exec` presence (`test -x`), plus `sw_vers -productVersion`.
  4. A short `README.md` in that directory stating what the baseline means: every operation the
     later denial tests will assert as blocked is proven to WORK when unsandboxed, on this exact
     host, with these exact fixtures. Without this, a later "DENIED" could be an artifact of a
     broken fixture rather than of the sandbox.
Re-run `make_fixtures.sh` afterwards to clear the `probe-write.txt` files the control run created.
  </action>
  <verify>
`ALLOWED_PATH=$(cd phase-03/fixtures/allowed && pwd) FORBIDDEN_PATH=$(cd phase-03/fixtures/forbidden && pwd) node phase-03/sandbox/probe_fs.js`

  <done>probe_fs.js distinguishes DENIED (EPERM only) from ERROR (everything else) and covers in-process read/write, subprocess read/write and the escape-symlink case; the unsandboxed control baseline is recorded and shows every one of them succeeding.</done>
