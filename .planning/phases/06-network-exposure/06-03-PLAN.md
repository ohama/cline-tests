  <name>Task 1: Write setup_tailscale_serve.sh — fail-closed, idempotent, one entry only</name>
  <files>phase-06/net/setup_tailscale_serve.sh</files>
  <action>
Write `phase-06/net/setup_tailscale_serve.sh`, sourcing `phase-06/net/config.env`.

Usage: `setup_tailscale_serve.sh [--check|--apply] [--out-dir <dir>]`. Default is `--check`.
`--check` performs every pre-flight assertion and prints exactly what it WOULD run, then
exits without mutating anything. Only `--apply` mutates.

PRE-FLIGHT (all must pass; any failure exits non-zero WITHOUT mutating):
  P1. `$TAILSCALE_BIN` exists and `tailscale status` succeeds (stderr filtered with
      `$TS_WARN_FILTER`).
  P2. `$TS_SERVE_PORT` is not in `$FORBIDDEN_SERVE_PORTS`. Print the reason for each
      exclusion in the failure message, naming the pre-existing public entry that forwards
      to port 3000.
  P3. `lsof -nP -iTCP:3000 | wc -l` == 0. If anything is bound to 3000, ABORT — do not open
      anything while that trap is armed.
  P4. Capture `tailscale serve status --json` (warning filtered) and assert with python3
      that its `Web` handlers and `AllowFunnel` map match
      `$EXPECTED_SERVE_BASELINE` EXACTLY for the three pre-existing entries and the single
      pre-existing public key. Any drift = ABORT with a diff. This is the fail-closed heart
      of the script: if the machine's Tailscale config has changed since 06-01 captured it,
      a human must look before anything is added.
  P5. kanban is listening on exactly `127.0.0.1:$KANBAN_PORT` and nothing is bound to
      `*:$KANBAN_PORT`. `curl -s -o /dev/null -w '%{http_code}' http://127.0.0.1:$KANBAN_PORT/`
      returns a 2xx/3xx.
  P6. If a Serve entry for `$TS_SERVE_PORT` ALREADY exists and already proxies to
      `$TS_SERVE_TARGET`, print `ALREADY-CONFIGURED` and exit 0 without running anything.
      This is what makes the script idempotent.

APPLY (only under `--apply`, and only one command, printed before it runs):
  `"$TAILSCALE_BIN" serve --bg --https="$TS_SERVE_PORT" "$TS_SERVE_TARGET"`
  `--bg` is mandatory: without it the config is foreground-bound and evaporates when the
  invoking process exits.

POST-ASSERTIONS (run immediately, and if ANY fails, print the rollback command loudly and
exit 2 — inconclusive, never a pass):
  Q1. `AllowFunnel` still has exactly `$EXPECTED_FUNNEL_KEY_COUNT` key and that key is
      exactly `$EXPECTED_FUNNEL_KEY`. NO new public-exposure key may appear. This is the
      single most important assertion in Phase 6.
  Q2. The three pre-existing `Web` handlers are still byte-identical to
      `$EXPECTED_SERVE_BASELINE`.
  Q3. A new `Web` handler exists for `$TAILNET_HOSTNAME:$TS_SERVE_PORT` with `/` proxying to
      `$TS_SERVE_TARGET`, and no other new entry appeared (handler count is exactly
      baseline+1, TCP key count exactly baseline+1).
  Q4. `lsof -nP -iTCP:3000 | wc -l` is still 0.
  Q5. kanban's listener is STILL `127.0.0.1:$KANBAN_PORT` only — adding a Serve entry must
      not change kanban's bind, and if it somehow did, that is a hard failure.

Save before/after JSON captures and a full transcript to the out-dir (default
`$RESULTS_ROOT/$(date -u +%Y%m%dT%H%M%SZ)-serve-setup`).

ROLLBACK: determine the exact removal syntax from `"$TAILSCALE_BIN" serve --help` at author
time (do not guess) and write it into the script header AND print it in every failure path,
so an operator always has the one-line undo in front of them. Do not execute it in this plan.

House rule 8 applies to this file specifically: it must never contain the public-exposure
subcommand name adjacent to `tailscale`. Refer to it as "the public-exposure mode" and to
its config key as `$EXPECTED_FUNNEL_KEY`.
  </action>

  <name>Task 2: Write verify_network.sh — the standing Phase 6 gate</name>
  <files>phase-06/net/verify_network.sh</files>
  <action>
Write `phase-06/net/verify_network.sh` in the exact house shape of
`phase-05/services/verify_services.sh`: `source config.env`, `--out-dir` argument,
`record_check <id> <rc> [detail]` writing `CHECK: PASS <id>` / `CHECK: FAIL <id> -- <detail>`,
parallel indexed arrays (bash 3.2), a `CASES n/N` + `CRASHED n` tail, and the 3-way exit
contract: 0 = all pass, 1 = at least one FAIL, 2 = at least one probe CRASHED
(inconclusive — never reported as a pass). Read-only: it must never mutate Tailscale config,
never restart a service, never send a signal, and never call any state-changing `launchctl`
subcommand.

Checks, with these exact ids:

  1. `tailscale-reachable` — `tailscale status` succeeds (warning filtered).
  2. `no-new-public-exposure` — `AllowFunnel` has exactly one key and it is
     `$EXPECTED_FUNNEL_KEY`. **Traces to: the phase's overriding safety property.**
  3. `preexisting-serve-entries-untouched` — the three baseline `Web` handlers and three TCP
     keys match `$EXPECTED_SERVE_BASELINE` exactly.
  4. `kanban-serve-entry-present` — a handler for `$TAILNET_HOSTNAME:$TS_SERVE_PORT` proxies
     `/` to `$TS_SERVE_TARGET`. **NET-01 (server side).**
  5. `port-3000-unbound` — `lsof -nP -iTCP:3000` empty. Failure detail must state the reason
     (a pre-existing public entry on :8443 already forwards there). **NET-03.**
  6. `kanban-bind-loopback-only` — `lsof -nP -iTCP:$KANBAN_PORT -sTCP:LISTEN` contains
     `127.0.0.1:$KANBAN_PORT` and does NOT contain a wildcard bind. **NET-02.**
  7. `lan-refused-kanban-port` — `curl -s -m 5 -o /dev/null -w '%{http_code}'
     http://$LAN_IP:$KANBAN_PORT/` must fail at the connection level: curl rc 7 (refused) or
     28 (timeout) is PASS; rc 0 is FAIL. Mirror `phase-02/infra/verify_lan_bind.sh` Check 2
     exactly, including the INCONCLUSIVE path when no LAN IP can be derived. **NET-02.**
  8. `lan-refused-serve-port` — same probe against `http://$LAN_IP:$TS_SERVE_PORT/`; the
     Serve listener must not be reachable from the LAN interface either.
  9. `tailnet-https-200` — `curl -s -m 15 -o /dev/null -w '%{http_code}' "$TS_SERVE_URL"`
     returns 200, using the MagicDNS hostname (NOT loopback — the point is that the tailnet
     address itself answers). **NET-01 (server side).**
 10. `tailnet-no-passcode-gate` — the body fetched from `$TS_SERVE_URL` is the board, and
     `~/.cline/logs/kanban.log` contains no remote-access passcode banner. Kanban's passcode
     gate is decided once at startup from its host flag; keeping the bind on loopback is what
     keeps it off, so a banner appearing means someone changed the bind.
 11. `net04-guard-present` — `phase-05/services/run_telegram_service.sh` contains the
     `ABORT-NET04` guard and passes `--allowed-user-id` on its exec line. **NET-04.**
 12. `net04-guard-refuses` — behavioural: run the wrapper with `$NET04_PROBE_TOKEN` and the
     allowlist id unset, hard-bounded to 15s, and require exit 1 plus `ABORT-NET04` on stderr
     plus zero `connect telegram` processes. Safe and re-runnable because the guard fires
     before cline is executed. **NET-04.**
 13. `no-wildcard-bind-in-repo` — `grep -rn '0\.0\.0\.0' phase-05/ phase-06/` over `.sh`,
     `.env` and `.plist` files returns nothing.
 14. `no-public-exposure-command-in-repo` — no file under `phase-06/net/` invokes the
     public-exposure subcommand. Implement this by grepping for the subcommand name adjacent
     to `tailscale`; the check's own failure message must not contain that adjacency
     (build the needle from two variables) or the check will flag itself. This is the
     wording-collision trap, live.
 15. `live-pids-stable` — the four upstream pids recorded in `phase-06/net/config.env`'s
     companion baseline (flashnext, litellm, role-shim, kanban) are still the same. Read the
     expected values from the 06-01 baseline README path passed via `--baseline <dir>`, and
     record INCONCLUSIVE (rc 2) rather than FAIL if that file is absent.

Write a header comment stating: this is Phase 6's standing gate, Phase 7 and Phase 8 should
run it, it is read-only and re-runnable, and it must be run BEFORE and AFTER any change to
network posture.
