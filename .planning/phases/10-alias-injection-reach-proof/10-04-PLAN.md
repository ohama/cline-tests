<objective>
Answer the two questions that HTTP 200 cannot: does the shipped alias actually make the model think
(CFG-16), and does a parameter injected at the alias definition actually reach the model (VRF-01 /
VRF-02) — with a script that can be run again (VRF-03).

Purpose: this project has been burned twice by a configuration that existed, returned 200, and did
nothing. `drop_params` is banned for exactly that reason, and VRF-02 exists to make the standard
explicit: **the evidence is the server-side `prompt_tokens`, not the response code.** Phase 9
established the oracle and simultaneously took away the easy version of this proof — the shipped
`et-medium` combination's `prompt_tokens` delta is exactly **−2**, identical to `medium` alone, and
`PRB-03-ORACLE.md` §4 rules that margin out as a reach probe. So reach is proven with
`flashnext-reach-xhigh` (+40), and the shipped arm is measured and reported beside it as the weaker
proof it is. That distinction must survive into the document, not be smoothed over.

The plan also owns a confound the research raised and did not resolve: `flashnext` is
`openai/`-prefixed and `flashnext-plan` is `hosted_vllm/`-prefixed, and litellm sends them through
two different low-level request paths. If that alone shifts `prompt_tokens`, VRF-01's delta is not
cleanly attributable to the injected parameters. A 2×2 of the same request body across
`:8011`-direct and `:4000`-alias, on both an unspecified and an injected arm, settles it by
measurement.

Output: `phase-10/probe_cfg16.sh`, `phase-10/verify_reach.sh`, `phase-10/REACH-PROOF.md`.

**Outcome neutrality:** CFG-16 may come back negative — the combination may not produce reasoning
through the alias. That is an answer, and the plan's obligation is then to localize it and either
fix the alias definition or write down why it cannot be fixed. Likewise the confound check may find
a non-zero offset; the response is to quantify it and re-read VRF-01 in light of it, not to
suppress it. Nothing here requires a particular number.
</objective>

  <files>phase-10/probe_cfg16.sh, phase-10/results/CURRENT_CFG16_RUN</files>
  <action>
Create `phase-10/probe_cfg16.sh` (sources `phase-10/probe_lib10.sh`) and run it. `new_run_dir10
cfg16`, write `phase-10/results/CURRENT_CFG16_RUN`, `preflight10`.

Phase 9 narrowed this question and the probe must be scoped to what is actually open.
`GATE-VERDICT.md` §3.2 established: `reasoning_effort: medium` **alone** already turns thinking on
(PRB-01: 179 chars vs an empty negative control), and `et-medium`'s token cost is indistinguishable
from `medium` alone — so `enable_thinking` is either redundant or silently no-op'd once effort is
explicit, and a token measurement cannot tell those apart. What remains open is narrower and is what
this task measures: **does litellm's alias-level injection deliver the combination through to the
model at all**, given that litellm's own validation layer treats the two parameters differently
(`reasoning_effort` is a whitelisted param under `hosted_vllm`; `enable_thinking` is unrecognized
and rides `extra_body`). Phase 9 also never checked reasoning *content* at a realistic generation
length — it measured `et-medium` only at `max_tokens: 4`, which truncates before thinking can
surface. That is the gap.

Three requests, `max_tokens: 256`, identical single user message (choose something that invites a
little reasoning and finishes fast, e.g. `"1부터 20까지의 소수를 모두 더하면? 답만 한 줄로."`),
strictly sequential with an `in_flight=0` check before each:

- **Arm 8011** — `POST http://localhost:8011/v1/chat/completions`, body carries the literal
  `"reasoning_effort": "medium", "enable_thinking": true` alongside `"model": "<the model path>"`.
  This is ROADMAP criterion 1b's `:8011` half.
- **Arm 4000-plan** — `POST http://127.0.0.1:4000/v1/chat/completions`,
  `{"model": "flashnext-plan"}` and **no reasoning parameters in the client body at all**. The
  parameters must come from the alias definition or not at all; sending them from the client would
  prove nothing about injection. This is criterion 1b's `:4000` half.
- **Arm 4000-control** — same endpoint, `{"model": "flashnext"}`, same message, same `max_tokens`.
  The negative control: without it, an empty `reasoning` result cannot be distinguished from a stack
  that never emits the field. Phase 9's PRB-01 got its clean reading precisely because it had one.

For every arm, save the raw body and extract **both** field spellings from
`choices[0].message`: `reasoning_content` (litellm's name) and `reasoning`. Record for each: HTTP
code, `reasoning_content` char length, `reasoning` char length, `content` char length,
`prompt_tokens`, `completion_tokens`. Write `"$RUN"/cfg16.tsv`. Close with `flake_window` and
`record_verdict` per arm — a single unlucky sample during the `no Stream(gpu, 1)` flake must not be
recorded as a confirmed negative; the four-state rule inherited from `probe_lib.sh` enforces that.

**Reading the outcome — all four readings are legitimate results, and the plan handles each:**
- 8011 non-empty **and** 4000-plan non-empty, control empty → CFG-16 answered positively; nothing
  further needed.
- 8011 non-empty, 4000-plan **empty** → the model can do it but the alias does not deliver it. The
  fault is localized to litellm. Diagnose before concluding: re-check `/v1/models` lists
  `flashnext-plan`, confirm the installed config's alias block (`grep -A8 'model_name: flashnext-plan'`
  on the live file), and check `/Users/ohama/agent-stack/litellm/litellm.log` for the outgoing body
  or an `UnsupportedParamsError`. Then write `phase-10/CFG-16-REMEDIATION.md` naming the exact
  proposed alias change and the evidence for it — and **stop**; do not restart.
- 8011 **empty** as well → the stack itself does not produce reasoning at this prompt/length. Record
  it, note that it contradicts PRB-01's 179-char result, and re-run once at a longer `max_tokens`
  (still ≤ 256) with a different prompt before recording a confirmed negative.
- control **non-empty** → the negative control failed and none of the readings discriminate. Record
  that plainly; the probe is inconclusive and says so rather than claiming a positive.

Close with `postflight10 "$RUN" <installed cfg sha> 0`.

  <name>Task 2: Build the re-runnable reach proof and resolve the hosted_vllm confound</name>
  <files>phase-10/verify_reach.sh, phase-10/results/CURRENT_REACH_RUN</files>
  <action>
Create `phase-10/verify_reach.sh` (sources `phase-10/probe_lib10.sh`) and run it. This script is the
VRF-03 deliverable: it must be runnable again later, standalone, and reproduce its own verdict.
`new_run_dir10 reach`, write `phase-10/results/CURRENT_REACH_RUN`, `preflight10`.

**One fixed request body across every arm** — single user message `"hi"`, `max_tokens: 4`. Holding
the body constant is what makes a `prompt_tokens` difference attributable to the injected parameters
rather than to the text. Seven arms:

| id | endpoint | model / alias | client-sent params |
|---|---|---|---|
| A | `:8011` | the model path | none |
| B | `:4000` | `flashnext` (`openai/`) | none |
| C | `:8011` | the model path | `reasoning_effort: medium`, `enable_thinking: true` |
| D | `:4000` | `flashnext-plan` (`hosted_vllm/`) | **none** — injected by the alias |
| E | `:8011` | the model path | `reasoning_effort: xhigh` |
| F | `:4000` | `flashnext-reach-xhigh` (`hosted_vllm/`) | **none** — injected by the alias |
| G | `:4000` | `flashnext-act` (`hosted_vllm/`) | **none** — injected by the alias |

Run the whole seven-arm sweep **twice**, back to back (sweep A then sweep B), 14 requests total.
`prompt_tokens` is a deterministic function of the tokenized prompt, so the repeat is not for
statistics — it is to catch the `no Stream(gpu, 1)` flake and any incidental drift. If the two
sweeps disagree on any arm, **that disagreement is the finding**: record it, run a third sweep, and
report all three rather than picking a winner.

**Per-request attribution.** For each request: `MARK=$(wc -l < "$FLASHNEXT_LOG")` immediately before
firing; fire; then read only `sed -n "$((MARK+1)),\$p" "$FLASHNEXT_LOG" | grep 'Prefill started'`.
Expect exactly one line. Zero → retry once. Two or more → another tenant landed in the window,
attribution is ambiguous, discard and re-fire (bounded at 3 attempts). Extract portably with
`grep -oE 'prompt_tokens=[0-9]+' | cut -d= -f2` (macOS `grep` may lack PCRE). Append to
`"$RUN"/reach.tsv`: sweep, arm, endpoint, model, http_code, prompt_tokens, matched log line. Also
write `"$RUN"/sweep-lines.txt` with every consumed log line so the raw evidence survives log
rotation.

**The readings the script must compute and print**, each as a labelled line in
`"$RUN"/reach-report.txt` and on stdout — reporting values, never asserting a required one:

- **VRF-01 (ROADMAP criterion 4):** `B` vs `D` — the same user message through `flashnext` and
  through `flashnext-plan`. Print both values and their difference. The oracle predicts −2.
- **VRF-02 banner:** print, in words, `판정 근거는 서버 로그의 prompt_tokens 값이며 HTTP 200 응답이
  아니다` together with the HTTP code of every arm — the codes are recorded precisely so a reader can
  see they were available and were *not* used as the basis. Add the one-line reason: a
  `drop_params`-style silent drop would return 200 while changing nothing, so 200 carries no
  information about reach.
- **Wide-margin reach:** `B` vs `F` (oracle: +40) and `D` vs `F` (both `hosted_vllm/`, oracle:
  53−11 = +42). The second is the confound-free one — same provider prefix, same request path, only
  the injected `reasoning_effort` differs — so a difference there is attributable to injection
  alone. Print both deltas beside the oracle's.
- **The `hosted_vllm/` confound, resolved by measurement:** `A` vs `B` (does litellm's `openai/`
  path change `prompt_tokens` relative to `:8011` direct?), `C` vs `D` (does the `hosted_vllm/` path
  change it, beyond the parameters, relative to the same parameters sent directly?), and `E` vs `F`
  (same, at `xhigh`). If all three differences are 0, the provider-prefix swap introduces no
  confound and VRF-01's delta is cleanly attributable to the injected parameters. If any is non-zero,
  print the magnitude and state how it changes the VRF-01 reading — **quantify it, do not suppress
  it, and do not treat a non-zero offset as a failure of this plan.**
- **CFG-12 corroboration:** `G` vs `B` — `flashnext-act` vs the unmodified `flashnext`. A difference
  of 0 is the *expected* result (`enable_thinking:false` is already the model's default) and
  confirms `ALIAS-DESIGN.md`'s stated redundancy rather than contradicting anything.
- **Delta table:** every arm's delta from **this run's own arm A**, beside `PRB-03-ORACLE.md` §2/§2b's
  declared deltas (medium −2, xhigh +40, et-medium −2, et-true +40). State that the comparison is
  delta-to-delta and that absolutes are not portable across sessions.

Close with `flake_window`, `record_verdict` per arm, and `postflight10 "$RUN" <installed cfg sha> 0`.

The script must exit 0 on a completed measurement regardless of which way the numbers came out; it
exits non-zero only on an operational failure (attribution ambiguity it could not resolve, an arm
that never returned, a postflight violation).
