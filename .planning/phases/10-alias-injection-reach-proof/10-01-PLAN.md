<objective>
Author the exact bytes Phase 10 proposes to install into the file litellm actually loads, and build
— then break on purpose — the gate that decides whether those bytes are safe to install.

Purpose: Phase 10 is the first phase in this milestone that mutates the running stack. `litellm`'s
launchd job has `KeepAlive: true` and **no `--config` fallback**: a config that fails to parse, or
that pydantic rejects at startup, does not break one alias — it takes the whole gateway down into a
`ThrottleInterval: 10` crash loop, and Kanban (`:3484`) and the Telegram connector go with it.
The cheapest way to never meet that failure mode is to refuse to install a config that has not
already been booted successfully by the real `litellm` binary on a scratch port. That is what this
plan builds. Phase 9's precedent governs how it is accepted: its safety envelope was believed only
after it was seeded with a real mutation and observed to exit non-zero. The same standard applies
here — a ladder that has only ever seen a good config proves nothing.

Nothing in this plan touches the live stack. No file under `/Users/ohama/agent-stack/` or
`~/local-llm-settings/` is written, no service is restarted, no request reaches the model. The
candidate lives entirely inside `phase-10/config/`.

Output: `phase-10/build_candidate.sh`, `phase-10/config/config.yaml.candidate`,
`phase-10/validate_config.sh`, `phase-10/selftest_validate_config.sh`, `phase-10/ALIAS-DESIGN.md`,
and a run directory holding the ladder's own evidence.

**Outcome neutrality:** this plan does not require the ladder to catch every class of bad config.
It requires the ladder to be *measured* — each seeded mutant's outcome recorded as observed. A
mutant the ladder is blind to is a finding to write down (and to hand to plan 10-03 as a residual
risk), not a result to engineer away.
</objective>
