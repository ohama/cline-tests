**a) `--thinking` — per alias prefix, not one status code.** USE-04 and ROADMAP Phase 12 criterion 2
both say flatly that `--thinking` "이 litellm 에서 400 이 된다". `phase-11/PHASE-11-FINDINGS.md` §6
flags that as imprecise, and it is: measured end-to-end
(`phase-11/OPEN-ITEMS.md` Open Item 1, cases 1a/1c),

- `flashnext` (`openai/` prefix): litellm's own `UnsupportedParamsError` → **HTTP 400**.
- `flashnext-plan` / `flashnext-act` / `flashnext-reach-xhigh` (`hosted_vllm/` prefix): the value
  passes litellm and the **model server** rejects it → **HTTP 500**.
- A raw `cline --thinking high` bypassing the wrapper surfaces that model-side 500 as Cline's own
  error event and **exits 1** — a user never sees a 400 on that path.
- None of the three consumed a generation-queue slot; value validation precedes queueing.

So the requirement's "400" is accurate for exactly one of the five live aliases. Give the status code
per prefix and note the imprecision explicitly — an imprecise success criterion that goes unremarked
is how a false claim survives a milestone.

**b) The CFG-11 premise correction, which `.planning/REQUIREMENTS.md` already carries (2026-09-02).**
At cline 3.0.53 `--thinking` was believed absent from the CLI. At the now-installed 3.0.60+ it is a
real flag (`none|low|medium|high|xhigh`), and a client-sent value **overrides** the alias's injected
`reasoning_effort`, because litellm merges client kwargs *after* `litellm_params`. That is precisely
why `phase-11/cline-plan`/`cline-act` refuse the flag outright rather than allowing it through —
cite `phase-11/WRAPPER-DESIGN.md` §3/§4 for the deny-by-default rationale.

**c) The pin-versus-measurement rule — the section's most important paragraph.** State it once,
explicitly, in the file's existing 고정 / 요구사항 / 증거 vocabulary:

**Pins** (must not silently drift):
- The alias names and their injected parameter values — `flashnext-plan` always injects
  `enable_thinking:true` + `reasoning_effort:medium`.
- The `hosted_vllm/` vs `openai/` prefix choice — changing it reopens the 400.
- `providers.json`'s `model` and `contextWindow`, which `verify_config.sh` already asserts.

**Measurements, not pins** (have already drifted, judge nothing on them):
- The absolute `prompt_tokens` oracle values, which moved **23/21/51/63 → 13/11/41/53** with the
  cause unexplained.
- The wire `max_tokens`, formerly recorded as a fixed `2048`, measured at **20983** at 3.0.60/3.0.61
  and since shown not to be fixed at all — cline sizes it per request so `prompt + max_tokens` lands
  near `contextWindow × 0.9`. Cross-reference `docs/cline-max-tokens-findings.md` and
  `docs/32k-compaction-policy.md`, which plan 12-06 is correcting concurrently; **link to them, do
  not restate their arithmetic.**

**Judge future drift on deltas, never on absolutes and never on a file hash.** The deltas from
`unspecified` — `medium` −2, `low` +28, `xhigh` +40 — held bit-for-bit across three independent
measurement rounds (`phase-09/PRB-03-ORACLE.md` §2/§5) while every absolute moved. And for
`providers.json`, judge on `model` and `contextWindow`, **not sha256**: that constraint was already
corrected once this milestone after a timestamp-only rewrite changed the hash while nothing that
mattered moved.

**d) `providers.json` is repeatedly corrected, never stable — say so.** It currently reads
`model=flashnext`, `contextWindow=29000`, but that is a **point-in-time observation, not a pin**.
Every uncontained `cline -m` call rewrites `model` (31/31 measured, 100%); the wrappers redirect that
write to a scratch copy as of 2026-09-10, but any bare `cline -m` outside a wrapper still mutates the
shared file. Do not write anything implying the file "stays" correct. The sweep requires a phrase of
the form 호출마다 / 매 호출 / 호출할 때마다 to appear, because this is the property most likely to be
softened into something reassuring and false.

**e) Version-pin interaction — a note, not a new section.** This file's §5/§6 describe Phase-1-era

nothing that implies the 3.0.53 pin is currently honoured**, and cross-reference

duplicating it.
