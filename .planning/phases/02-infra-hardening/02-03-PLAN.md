<objective>
Satisfy INF-02: stop `litellm` from listening on every interface, so nothing on the LAN can reach the
unauthenticated `:4000` router.

Purpose: `litellm` is the only one of the three stack services actually exposed today — `lsof` shows
`TCP *:4000 (LISTEN)`, its plist passes no `--host` at all (so uvicorn's `0.0.0.0` default applies),
and its `config.yaml` has no `general_settings` and no `master_key` anywhere. `mlx_vlm.server` is
already `--host 127.0.0.1` and `role_shim.py` hardcodes `127.0.0.1` in its own source, so neither needs
a change. The bind is chosen over `master_key` deliberately: all four current consumers on this machine
(Cline's `providers.json`, `~/.hermes/config.yaml`, `~/.openjarvis/config.toml`, `~/.claude/proxy.env`)
already point at `localhost:4000` and all four send the placeholder key `dummy`. A loopback bind breaks
none of them; a `master_key` would start 401-ing every one of them — a materially larger regression
surface for the exact INF-03 this phase is trying to protect.

Output: an idempotent plist writer, a re-runnable LAN-rejection verifier, a restarted litellm bound to
loopback, and captured proof from both sides (refused from the LAN IP, 200 from loopback).
</objective>

Create `phase-02/infra/verify_lan_bind.sh` — `#!/bin/bash`, `set -euo pipefail`, executable, sources
`config.env`, accepts `--out-dir <dir>`. This is the re-runnable INF-02 proof; it makes no changes and
must be safe to run at any time (plan 02-04 and any future phase can re-run it).

Checks, all recorded to `<out-dir>/inf02-verdict.txt`, each reported PASS/FAIL individually and the
script exiting non-zero if any FAIL:

1. **Bind address.** `lsof -nP -iTCP:4000 -sTCP:LISTEN` — record verbatim. PASS requires a line
   containing `127.0.0.1:4000` and NO line containing `*:4000`. This is the direct structural proof.
2. **LAN rejection.** `LAN_IP="$(ipconfig getifaddr en0)"` (record it; it was `192.168.75.108` at
   research time — read it live, never hardcode; if `en0` yields nothing, try `en1` and record which
   interface was used, and if neither yields an address report INCONCLUSIVE for this check rather than
   a false PASS).
   `curl -s -m 5 -o /dev/null -w '%{http_code}' "http://$LAN_IP:4000/v1/models"; rc=$?`
   PASS requires `rc == 7` (connection refused). Accept `rc == 28` (timeout — no listener answering) as
   a secondary PASS and record which one occurred. A `rc == 0` with an HTTP code is a FAIL: the port is
   still reachable off-loopback. A bind-level restriction rejects by interface regardless of source, so
   this is a valid proof from this same Mac — no second LAN device is needed.
3. **Loopback by IP still works.** `curl -s -m 30 http://127.0.0.1:4000/v1/models` returns 200 and the
   body contains `flashnext`.
4. **Loopback by HOSTNAME still works.** `curl -s -m 30 http://localhost:4000/v1/models` returns 200.
   This check exists because all four existing consumers use the `localhost` hostname, not the IP, and
   `/etc/hosts` on this machine maps `localhost` to BOTH `127.0.0.1` and `::1` — a v4-only bind means
   any client that prefers or pins IPv6 would hit a closed `::1:4000`. `getaddrinfo` here returns IPv4
   first and curl falls back, so this is expected to pass; it is asserted anyway because a FAIL here is
   a genuine INF-03 regression, not a cosmetic one. If it FAILS, do not paper over it: record it, and
   report the two real options (leave the bind and update the four consumer configs to `127.0.0.1`, or
   roll back to the pre-edit plist) rather than choosing one unilaterally.
5. **The other two services are unchanged.** `lsof -nP -iTCP:8000 -sTCP:LISTEN` and
   `-iTCP:8011` still show `127.0.0.1` listeners. (They already bound loopback before this phase; this
   check catches accidental collateral damage.)

Final line: `INF02: PASS` / `INF02: FAIL <check>` / `INF02: INCONCLUSIVE <check>`.

Run it: `bash phase-02/infra/verify_lan_bind.sh --out-dir "$OUT"` (the `-inf02` dir from Task 1).
