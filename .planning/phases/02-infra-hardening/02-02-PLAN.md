<objective>
Satisfy INF-01: put a concurrency cap on the live `mlx_vlm.server`, restart it correctly, and prove
with log timing that a second concurrent request is now queued behind the first rather than batched
alongside it.

Purpose: ROADMAP Phase 2 Success Criterion 1 requires that after this change, two simultaneous
requests result in "하나가 즉시 처리되고 다른 하나는 큐잉/지연" — one served immediately, the other
queued/delayed — observable in the log, and specifically NOT an OOM. `--max-num-seqs` is a real
`mlx_vlm.server` flag on the installed build (mlx-vlm 0.6.17), verified in both `--help` and the
argparse source, and its own docstring describes exactly this behaviour: "Requests beyond this wait in
the queue (backpressure), bounding peak memory. Default: unbounded." Today it is unbounded, and
headroom at 32K is only 4.39 GB.

Output: an idempotent plist writer, a timestamped pre-edit backup, a restarted-and-healthy flashnext
service running with the cap, and the "after" half of the INF-01 timing evidence.
</objective>

HARD:

- **Serialization is deliberate.** This plan is wave 2 and 02-03 (litellm) is wave 3 even though the
  two edits are logically independent. Two concurrent `bootout`/`bootstrap` cycles against services in
  the same request chain is a real hazard: litellm restarting while flashnext is still cold-loading
  104 GiB of weights produces false health failures, both plans would race on the same
  `~/local-llm-settings/sync.sh` and the same results tree, and if the INF-03 gate later fails there
  would be no way to attribute the regression to one change. Nominal parallelism here buys perhaps 30
  seconds and costs attributability on the first live restart this project has ever performed.
  **Do not reorder these into one wave.**
- **HOUSE RULE: never `kill`, never `pkill`, never `launchctl load`/`unload`, never
  `launchctl kickstart` after a plist edit.** Use `phase-02/infra/restart_service.sh` from 02-01 —
  do not open-code a second restart sequence here.
- **Edit only `~/Library/LaunchAgents/com.ohama.flashnext.plist`.** Never
  `~/local-llm-settings/launchagents/` (a mirror; edits there do nothing and get overwritten).
  `sync.sh` is run once, by plan 02-04, after everything is verified.
- **Back up before touching.** The pre-edit copy goes to `phase-02/infra/backups/` (gitignored) and
  its path must be echoed to stdout and recorded in the SUMMARY.
- **Do not touch `role-shim` or `litellm` in this plan.** Do not run `sudo sysctl`.
- Small prompts only for the concurrency test (RESEARCH.md Pitfall 2 — `flashnext.err` holds a real
  single-request Metal OOM at 30,505 tokens; two large concurrent requests would likely crash the

Create `phase-02/infra/apply_max_num_seqs.sh` — `#!/bin/bash`, `set -euo pipefail`, executable,
sources `phase-02/infra/config.env` relative to its own directory. It must NOT hardcode the cap value;
it reads `$MAX_NUM_SEQS`. It must NOT restart anything — editing the plist on disk has zero live effect
until a `bootout`/`bootstrap`, which is Task 3's job under user consent.

Behaviour:
1. `PLIST="${TARGET_PLIST:-$LAUNCH_AGENTS_DIR/$FLASHNEXT_LABEL.plist}"` — the path MUST be overridable
   via `TARGET_PLIST` so the idempotence check in <verify> can run against a throwaway copy instead of
   the live file.
2. `mkdir -p "$BACKUP_DIR"`; copy the plist to
   `$BACKUP_DIR/$(basename "$PLIST").$(date -u +%Y%m%dT%H%M%SZ)` with `cp -p`. Echo the backup path.
   Do this before any modification, unconditionally, even if the change turns out to be a no-op.
3. Modify with `python3` + `plistlib` (NOT PlistBuddy — PlistBuddy cannot cleanly update an existing
   element by value, and bash 3.2 array handling here is error-prone):
   - read `ProgramArguments` (a list of strings);
   - if `--max-num-seqs` is present, set the element immediately after it to `str(MAX_NUM_SEQS)`;
   - if it is absent, append `--max-num-seqs` and `str(MAX_NUM_SEQS)` to the end of the list (argparse
     does not care about flag order);
   - if `--max-num-seqs` appears more than once, that is corruption from a previous bad run: abort
     with exit 1 and tell the operator to restore from `$BACKUP_DIR`;
   - write back with `plistlib.dump(..., fmt=plistlib.FMT_XML)`.
   Note in a comment that plistlib rewrites the whole file, so whitespace/ordering may differ from the
   original — this is why the backup is taken first and why plan 02-04 re-runs `sync.sh`.
4. `plutil -lint "$PLIST"` — abort with exit 1 if it does not print `OK`. A plist that fails lint must
   never reach a `bootout`.
5. Re-read the file and assert the pair is present exactly once with the right value; print the full
   resulting `ProgramArguments` array.
6. Print `APPLIED: --max-num-seqs <value>` or `ALREADY APPLIED: --max-num-seqs <value>` and exit 0.

Run it once against the live plist: `bash phase-02/infra/apply_max_num_seqs.sh`.

The live service is still running with the OLD arguments at this point. That is expected and correct.

Value: `MAX_NUM_SEQS=1` (full serialization) is what is currently written, chosen because the roadmap's
success criterion literally asks for one request served and the other queued/delayed, and because

will now be serialized, adding latency to that previously-fine case. `2` still bounds worst-case memory

measured, because measuring it risks reproducing the documented Metal OOM on a live service.
