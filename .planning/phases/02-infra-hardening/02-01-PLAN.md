<objective>
Build the Phase 2 safety toolkit and capture the pre-change baseline, without mutating anything live.

Purpose: this is the first phase in the project that will restart the always-on inference stack
(Phase 1 completed 6/6 plans without ever restarting `flashnext`/`role-shim`/`litellm`). Plans 02-02
and 02-03 each bootout/bootstrap a live `KeepAlive` service. Before that happens, three things must
exist: (a) a re-runnable pre-flight that proves the stack is in a known-good state and that the machine
has not been rebooted out from under the GPU wired limit, (b) one restart helper that both mutation
plans share so the bootout/bootstrap/health-wait sequence is written and reviewed exactly once, and
(c) a recorded baseline of how the CURRENTLY UNCAPPED server handles two concurrent requests — because
RESEARCH.md Pitfall 3 establishes that "two 200s" proves nothing about queueing on its own. The
evidence for INF-01 is a *behaviour change*, and a change needs a before.

Output: four scripts under `phase-02/infra/` and a timestamped evidence directory under
`phase-02/results/` containing the pre-change service snapshot and the uncapped concurrency baseline.
</objective>

<constraints>
HARD — these apply to every task in this plan, and this plan is the one that must not break them:

- **This plan performs ZERO live mutations.** No `launchctl bootout`, no `bootstrap`, no `kickstart`,
  no plist edit, no `sync.sh`. It only *writes scripts* and *reads/observes*. The restart helper is
  authored here but not invoked against any service here.
- **HOUSE RULE (from `~/projs/qwen38-flash-next-tests/scripts/llm_services.sh`): never `kill`, never
  `pkill`, never `launchctl load`/`unload`.** All three plists are `KeepAlive: true`; `flashnext` also
  has `ThrottleInterval: 60`. Killing gets the process relaunched with launchd's in-memory (old) job
  definition and burns the throttle window. The only correct cycle is
  `bootout` -> edit -> `bootstrap` -> `launchctl print` verify.
- **`launchctl kickstart -k` is NOT a substitute for bootout/bootstrap** after a plist edit — it
  restarts the already-loaded job definition and does not re-read the file from disk.
- **Never edit anything under `~/local-llm-settings/`.** That tree is a MIRROR; `sync.sh` copies
  live -> mirror only. Editing it changes nothing and gets silently overwritten. The live files are
  `~/Library/LaunchAgents/com.ohama.{flashnext,litellm}.plist`.
- **Do not invoke `cline` anywhere in this phase.** STATE.md records that `cline` self-triggers a
  background `npm update` on essentially every invocation in this environment, including `--version`.
  All verification in Phase 2 uses plain `curl` / `lsof` / `launchctl`.
- **macOS `/bin/bash` is 3.2** — no `declare -A`, no `${var^^}`. Use parallel indexed arrays. The
  invoking shell is **zsh**, so any place a space-separated variable must word-split into argv has to
  be wrapped in `bash -c '...'`.
- Concurrency test prompts MUST be small. RESEARCH.md Pitfall 2: `flashnext.err` already contains a
  genuine single-request Metal OOM at `prompt_tokens=30505`. Two near-32K concurrent requests would
  plausibly crash a live service the user depends on. Small prompts only, always.
</constraints>

**`phase-02/infra/restart_service.sh`** — `#!/bin/bash`, `set -euo pipefail`, executable. Usage:
`restart_service.sh <label> <port> [--timeout SECONDS]` (default timeout 240). Sources `config.env`.
This helper is authored here and invoked by plans 02-02 and 02-03; it is NOT invoked in this plan.

Sequence, exactly:
1. `PLIST="$LAUNCH_AGENTS_DIR/<label>.plist"`. Abort if it does not exist.
2. `plutil -lint "$PLIST"` — abort unless it prints `OK`. A malformed plist that gets booted out and
   then fails to bootstrap leaves the service DOWN, so this gate is mandatory and comes first.
3. `launchctl bootout "gui/$(id -u)/<label>"` — tolerate a non-zero exit whose stderr contains
   `No such process` (already unloaded); any other non-zero exit aborts.
4. `launchctl bootstrap "gui/$(id -u)" "$PLIST"`.
5. Poll, do NOT sleep a fixed amount (RESEARCH.md Pitfall 5: the flashnext model + MTP drafter needs
   ~45s from cold in the good case). Loop every 2s until `--timeout`: require BOTH
   `launchctl print "gui/$(id -u)/<label>"` to show `state = running`, AND
   `lsof -nP -iTCP:<port> -sTCP:LISTEN` to return a listener. Print a progress dot per poll.
6. On success print `RESTART OK: <label> pid=<pid> port=<port> waited=<n>s` and exit 0.
7. On timeout, print to stderr the exact rollback commands and exit 1:
   ```
   RESTART FAILED: <label> did not become healthy within <timeout>s
   ROLLBACK:
     cp -p <BACKUP_DIR>/<label>.plist.<newest-timestamp> ~/Library/LaunchAgents/<label>.plist
     launchctl bootout   gui/$(id -u)/<label>   # ignore "No such process"
     launchctl bootstrap gui/$(id -u) ~/Library/LaunchAgents/<label>.plist
   ```
   Resolve `<newest-timestamp>` at runtime with `ls -t "$BACKUP_DIR"/<label>.plist.* 2>/dev/null | head -1`
   and print the literal resolved path; print `(no backup found in $BACKUP_DIR)` if there is none.
8. It must contain NO `kill`, NO `pkill`, NO `launchctl load`, NO `launchctl unload`, NO
   `launchctl kickstart`.

**`phase-02/infra/verify_queueing.sh`** — `#!/bin/bash`, `set -euo pipefail`, executable. Usage:
`verify_queueing.sh --label before|after [--out-dir <dir>]`. Sources `config.env`. This is the INF-01
evidence collector. In `before` mode it records and always exits 0 (it is a baseline, not a gate); in
`after` mode it asserts.

Sequence:
1. `OFFSET=$(wc -c < "$FLASHNEXT_ERR")` — capture the log byte offset BEFORE firing anything.
2. Fire two concurrent requests **directly at `:8000`**, bypassing role-shim and litellm (this test
   exercises server-side admission only; the full chain is plan 02-04's job). Body for each, with
   `"model": "$MLX_MODEL_PATH"`, `"messages":[{"role":"user","content":"count from 1 to 20 slowly, one number per line"}]`,
   `"max_tokens": 60`, `"stream": false`. Small prompt — never a large one, per Pitfall 2.
   Launch request A in the background, `sleep 0.3`, launch request B in the background, then `wait`.
   Save each body to `<out-dir>/queueing-<label>-r{1,2}.json` and each curl exit code.
   Use `curl -s -m 120`.
3. Slice only the new log: `tail -c "+$((OFFSET + 1))" "$FLASHNEXT_ERR" > <out-dir>/queueing-<label>-log-slice.txt`.
4. Parse the slice with `python3` (bash 3.2 cannot do this cleanly). The log format is confirmed
   verbatim on this machine, e.g.:
   `2026-08-29 19:05:24,847 - INFO - Generation queued: request=82eb4556a0 prompt_tokens=30505 ...`
   `2026-08-29 19:05:24,853 - INFO - Prefill started: request=82eb4556a0 backend=continuous_batching ...`
   `2026-08-29 19:06:24,426 - INFO - Decode started: request=82eb4556a0 time_to_first_token=59.608s`
   `2026-08-29 19:06:26,879 - INFO - Request completed: endpoint=/chat/completions ... in_flight=0`
   Timestamps are `%Y-%m-%d %H:%M:%S,%f`. Correlate per-request by the `request=<hexid>` token.
   `Request completed` lines do NOT carry a `request=` id — associate the Nth `Request completed` with
   the Nth request to reach `Decode completed`, and prefer `Decode completed: request=<id>` (which DOES
   carry the id) as the "A finished generating" marker. Emit a small table per request id:
   queued_at, prefill_started_at, decode_started_at, decode_completed_at.
5. Identify A = the request whose `Generation queued` is earliest, B = the other.
6. **The assertion (after mode only).** PASS requires all three:
   - both curls exited 0 and both response JSONs have a non-empty `choices[0].message.content`
     (i.e. queuing, not OOM, not a 5xx);
   - exactly two distinct request ids appear in the slice;
   - `prefill_started(B) >= decode_completed(A)` — B was not admitted into the decode batch until A
     was done. Report the gap in seconds.
   If the response bodies are fine but the ordering assertion fails, exit 1 with
   `QUEUEING: FAIL (B admitted at <ts>, before A completed at <ts>)`.
   If the expected log lines cannot be found at all, exit 2 with `QUEUEING: INCONCLUSIVE <reason>` —
   do not report a pass you did not observe.
7. **Explicitly encode this caveat in the script's output and in a comment**: the
   `Request started: ... in_flight=2` line is expected to appear even with the cap in force, because
   `in_flight` counts HTTP requests being served, not sequences admitted to the decode batch.
   `in_flight=2` is NOT counter-evidence and must not be used as the pass/fail signal. Likewise, two
   HTTP 200s alone prove nothing — RESEARCH.md Pitfall 3 confirms 2 concurrent small requests already
   succeed today, uncapped, with `in_flight=2`. The timing ordering is the only evidence.
8. Final line `QUEUEING: <PASS|FAIL|BASELINE|INCONCLUSIVE> label=<label>`.

Now run the baseline against the **currently uncapped** server, writing into the same results
directory Task 1 created:
`bash phase-02/infra/verify_queueing.sh --label before --out-dir <the dir from Task 1>`

Expect it to record interleaved admission (B's `Prefill started` landing before A's
`Decode completed`) — that interleaving is precisely the "before" half of the INF-01 contrast. If the
baseline happens to look serialized anyway (possible if A finishes very fast), record that fact
plainly in the SUMMARY rather than re-running repeatedly; the after-run assertion still stands on its
own and plan 02-02 does not depend on the baseline being interleaved.
