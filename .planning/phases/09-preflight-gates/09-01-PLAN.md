<objective>
Build Phase 9's own safety envelope and use it to **independently reproduce** PRB-01 and PRB-02.

Purpose: `09-RESEARCH.md` already ran these probes and recorded PASS for PRB-01. That is not
enough. PRB-01 is a 🔴 gate that decides whether the entire v1.1 milestone proceeds; a gate
verdict may not rest on a single unreproduced run by a research agent. This plan re-runs the
probes from the research's literal commands and captures **fresh evidence into this phase's own
results directory**. It also builds the harness that plans 09-02 and 09-03 reuse, so that no
probe in this phase can silently restart a service, mutate a config, or record a flake-corrupted
sample as a real answer.

Output: `phase-09/probe_lib.sh`, `phase-09/probe_prb01.sh`, `phase-09/probe_prb02.sh`, and a
timestamped run directory under `phase-09/results/` holding raw response bodies, HTTP statuses,
a before/after service-and-config snapshot, and a `RESULT.md` recording the fresh values.

**Outcome neutrality:** this plan does NOT require PRB-01 to pass. It requires that a fresh,
flake-discriminated, evidence-backed answer exists. If the fresh run disagrees with the research
(e.g. `reasoning` comes back empty), recording that disagreement with its raw evidence is a
**passing** outcome for this plan. Plan 09-04 adjudicates; this plan measures.
</objective>

  <files>phase-09/probe_lib.sh</files>
  <action>
Create `phase-09/probe_lib.sh` (bash, `set -euo pipefail`, chmod +x). It is a **library**: it
defines functions and is sourced by the probe scripts, it does not run probes itself.

Define these constants at the top:
- `MODEL=/Users/ohama/projs/qwen38-flash-next-tests/models/Qwen3.8-Flash-Next-MLX-oQ4`
- `FLASHNEXT_LOG="$HOME/llm-system/services/logs/flashnext.err"`
- `LITELLM_CFG="$HOME/local-llm-settings/config/litellm-config.yaml"`
- `PROVIDERS_JSON="$HOME/.cline/data/settings/providers.json"`
- `SVC_RE='com\.ohama\.(flashnext|role-shim|litellm)'`

`new_run_dir <tag>` — echoes `phase-09/results/$(date -u +%Y%m%dT%H%M%SZ)-<tag>`, creating it.

`preflight <run_dir>` — writes `"$run_dir"/preflight.txt` and exports state:
- `launchctl list | grep -E "$SVC_RE" | awk '{print $3" "$1}' | sort` -> save as
  `"$run_dir"/pids-before.txt`. Fail hard if fewer than 3 lines.
- `shasum -a 256 "$LITELLM_CFG" "$PROVIDERS_JSON"` -> `"$run_dir"/hashes-before.txt`.
- `export LOG_WATERMARK=$(wc -l < "$FLASHNEXT_LOG")` and record it.
- Idle check: `tail -2 "$FLASHNEXT_LOG"`. If the last line containing `in_flight=` does not show
  `in_flight=0`, sleep 3 and retry up to 10 times; after that, abort with a clear message rather
  than firing probes into someone else's request.
- Advisory: `pgrep -fl 'bin/\.cline|bin/cline' || true` -> record (a running `cline-hub-daemon`
  is NOT proof of an in-flight model request; this is a hint only, never a hard gate).

`postflight <run_dir>` — writes `"$run_dir"/postflight.txt`, and FAILS the run (exit 1) if:
- `launchctl list | grep -E "$SVC_RE" | awk '{print $3" "$1}' | sort` differs from
  `pids-before.txt` (a service restarted -> constraint violated, results untrustworthy).
- `shasum -a 256 "$LITELLM_CFG" "$PROVIDERS_JSON"` differs from `hashes-before.txt` (this phase
  wrote a config file -> constraint violated). If it DOES differ, also run
  `phase-01/config/verify_config.sh` and record its output.
    **복구 절차 없음(의도적):** Phase 9 는 어떤 설정도 쓰지 않으므로 이 분기는 발동해서는 안 된다.
    발동했다면 이 페이즈 밖의 무언가가 설정을 바꾼 것이므로, `postflight` 는 불일치를 기록하고
    non-zero 로 종료한다. **Phase 9 가 스스로 복구를 시도하지 않는다** — 무엇이 썼는지 모르는 채
    되돌리면 그 사실 자체가 사라진다.
Additionally (non-fatal, but recorded): run `phase-01/config/verify_config.sh` once and append
its output, as an independent check that providers.json is still the known-good shape.

`flake_window <run_dir>` — the gpu-stream discriminator, implementing 09-RESEARCH.md
§"Distinguishing a Genuine Negative from the `no Stream(gpu, 1)` Flake":
- `sed -n "${LOG_WATERMARK},\$p" "$FLASHNEXT_LOG" | grep -c 'no Stream(gpu' || true`
- Write the count to `"$run_dir"/flake-count.txt` and echo `CLEAN` (count 0) or `DIRTY` (count>0).
- When DIRTY, also dump the matching lines plus 3 lines of context to
  `"$run_dir"/flake-lines.txt` so the timestamps can be compared against the probe window.

`record_verdict <run_dir> <label> <result> <flake_state>` — appends one line to
`"$run_dir"/verdicts.tsv` and enforces the **anti-flake rule**, which is the whole point of this
function. Encode it literally in a comment block at the top of the function AND in the logic:
- A **positive/expected** result in a CLEAN window is recorded as `CONFIRMED`.
- A **negative/unexpected** result in a DIRTY window is recorded as `DISCARDED-FLAKE` and the
  caller must re-run (the probe scripts implement up to 3 re-runs).
- A **negative/unexpected** result in a CLEAN window is recorded as `PROVISIONAL-NEGATIVE` on the
  first observation, and only promoted to `CONFIRMED-NEGATIVE` after it reproduces in a second
  independent CLEAN window. **A single run may never produce a CONFIRMED negative.**
- If after 3 attempts a result cannot be obtained in a CLEAN window, record `INDETERMINATE`.
  `INDETERMINATE` is a legitimate recorded outcome and is explicitly NOT a gate verdict — plan
  09-04 treats it as "no answer", not as "fail".

Write a short header comment explaining that this library exists so that no single flaky run can
flip a milestone gate, and that its preflight/postflight assertions are the mechanical enforcement
of Phase 9's "stack unchanged" constraint.
  </action>
