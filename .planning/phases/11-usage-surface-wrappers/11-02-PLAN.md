<objective>
Build the instrument USE-03 will be measured with, and decide — in writing, before any number
exists — that it will not be cline-bench.

Purpose: ROADMAP criterion 3 names cline-bench. Phase 07 already measured that pool: 4 tasks
attempted, **0 passed**, 3 of them dying at the 32K context ceiling at 21K–37K attempted prompt
tokens — including *both* tasks labelled `easy`. `medium` reasoning's only measured effect on
`prompt_tokens` is **−2** (`phase-09/PRB-03-ORACLE.md` §2b). A −2-token effect cannot rescue a task
that overflows by 5,000–15,000 tokens. An A/B on that pool would return 0/N vs 0/N and would be
measuring the compaction-pruning defect this project already carries as an open v1 blocker, not
whether thinking helps. Setting cline-bench aside is therefore a real scope decision that must be
made explicitly, with its evidence and its reversal condition on the record — not slipped past.

This plan builds the replacement: a small, bounded-turn, objectively gradable task set, and a grader
that has been proven able to return every verdict it claims to be able to return.

Output: `phase-11/AB-TASKSET.md`, `phase-11/tasks/`, `phase-11/grade_ab.py`,
`phase-11/selftest_grade_ab.sh`, `phase-11/fixtures/`.

**Outcome neutrality:** nothing here presumes the A/B will find an improvement. The task set is
chosen to be *able* to separate the arms if a difference exists; if it later turns out both arms
score identically, or both score near-ceiling, or both score near-floor, those are all valid results
and §4 of `AB-TASKSET.md` records in advance what each of them would mean.
</objective>

**§2 — Design constraints for the replacement set**, each with its source:
  - **Bounded turns (1–3).** Prompts must be answerable without tool use, so no task can spend turns
    on file reads. Note the second reason: `docs/headless-wrapper.md` §4 records that tool calls in
    headless mode interact badly with approval gating; keeping tools out of the picture removes that
    whole axis from the comparison.
  - **Prompt size ≪ trigger.** `verify_config.sh` prints the live compaction trigger
    (`trigger = maxInputTokens × 0.9`; currently 26,100). Cap each prompt at 1,500 bytes and record
    the measured byte size of each. The pilot in 11-05 measures the real `prompt_tokens`; this task
    only has to make overflow structurally implausible.
  - **Answer budget ≪ completion cap.** Cline sends a fixed per-turn `max_tokens` (measured 2048 at
    3.0.53; **re-measured at 3.0.60 by plan 11-04, open item 2**). A thinking arm shares that budget
    with its reasoning trace — Phase 9 saw `xhigh` consume a 300-token budget entirely and return
    empty content at `finish_reason: length` (`phase-09/PRB-03-ORACLE.md` §3). Every task's expected
    answer must be a handful of tokens, so the answer is not what runs out of room.
  - **Objectively gradable.** No LLM judge, no human judgement: a fixed expected value and a
    mechanical comparison.
  - **Plausibly reasoning-sensitive.** `phase-10/VRF-04-OBSERVATION.md` §3 says its own prime-sum
    prompt was too easy to separate the arms; a set of one-liners would produce a ceiling result and
    answer nothing.

**§3 — Answer protocol.** Every prompt ends with the same instruction: the model must put its answer
on the last line in exactly the form `ANSWER: <value>` and nothing else on that line. Record the
exact Korean/English wording used, verbatim, once — it is part of the instrument and must be
identical across arms and tasks.

**§4 — What each possible aggregate outcome would mean, written now, before any data exists.** At
minimum: (a) both arms near 100% → the set is too easy, the A/B cannot discriminate, and that is
what gets reported; (b) both arms near 0% → the set is too hard or the harness is broken, and the
pilot must catch this before the main run; (c) arms differ → the measured gap is the finding;
(d) the thinking arm shows many `no-answer` verdicts → completion-budget starvation, a real finding
about deploying medium thinking through cline, to be reported as such and not corrected away.

- **3 × code tracing**: a self-contained 12–20 line Python function embedded in the prompt, asked

- **2 × bug localisation**: a short numbered snippet with exactly one defect; the answer is the line

**Derive every answer mechanically, never by assertion.** For code-tracing and bug-localisation
tasks, write the snippet to `phase-11/tasks/NN-<slug>.truth.py` and actually execute it with
`python3` to obtain the return value; for word problems, compute the answer with a `python3 -c`
expression and record that expression. The derivation method and its output go into
`MANIFEST.tsv`. This project has lost time to values that were "known" rather than measured; an
answer key that was typed from memory would make every downstream accuracy number unfalsifiable.

`.expected` file format (one `key: value` per line, so the grader parses it without a YAML
dependency):
```
task_id: 03
match: exact_normalized      # exact_normalized | numeric | regex
expected: 84
tolerance: 0                 # numeric only
derivation: python3 phase-11/tasks/03-widget-rate.truth.py -> 84
notes: <anything a future reader needs to re-derive this>
```
`exact_normalized` = strip whitespace, lowercase, strip a trailing period and any thousands
separators before comparing. `numeric` = parse both sides as floats and compare within `tolerance`.
Prefer `numeric` for anything whose answer is a number, so `84`, `84.0` and `84 개` do not read as
three different answers — grading noise would otherwise be indistinguishable from arm differences.

Every `.prompt` ends with the §3 answer-protocol sentence verbatim.

`MANIFEST.tsv` columns: `id, slug, category, prompt_file, expected_file, prompt_bytes, match_mode,
derivation`.

match mode) — **without the expected answers inline**; the answer keys live in the `.expected`
files, and §5 says so, so a reader can see the set's shape without the document itself becoming the
answer sheet.

protocol sentence (a stray example would leak the format into the model's context in a way that

  <name>Task 3: The grader, and the fixtures that prove it can return every verdict</name>
  <files>phase-11/grade_ab.py, phase-11/selftest_grade_ab.sh, phase-11/fixtures/</files>

**Part A — `phase-11/grade_ab.py`** (`python3` stdlib only):

```
usage: grade_ab.py --ndjson <stream.log> --expected <task.expected> [--json]
```

Extraction, deliberately shape-tolerant, because `phase-10/VRF-04-OBSERVATION.md` §2 established
that the 3.0.53-documented NDJSON shape must not be trusted as the only path at 3.0.60:
1. **Primary**: walk every JSON line, collect string values under any key named `text` or `content`,
   in stream order, **excluding** any event whose `contentType` is `reasoning` (or that is otherwise
   marked as reasoning). Join into the assistant's visible output.
2. **Fallback net**: a raw line-level scan of the whole file for `ANSWER:`.
3. **Reasoning-only net**: the same scan restricted to reasoning-marked events.

Verdicts — four, plus one qualifier:
- `correct` — an `ANSWER:` line was found by path 1 and matches the key under the task's match mode.
- `incorrect` — found by path 1, does not match.
- `no-answer` — path 1 produced visible output but no `ANSWER:` line. If path 3 found one, the
  verdict stays `no-answer` and the qualifier `answer-seen-in-reasoning-only` is attached.
  **The fallback nets never overturn a `no-answer`** — they are reported, not applied. A model that
  reasoned its way to the answer and then got truncated before saying it did not answer the
  question, and folding that into `correct` would flatter the thinking arm; folding it into
  `incorrect` would libel it. It is its own state.
- `no-output` — path 1 produced no visible text at all (the empty-content / `finish_reason:length`
  shape from `phase-09/PRB-03-ORACLE.md` §3).
- `unparseable` — the file is missing, empty, or contains no valid JSON line.

Output one TSV row (and `--json` for the same fields): `task_id, verdict, qualifier, extracted_answer,
expected, match_mode, visible_chars, reasoning_chars, ndjson_lines, primary_hit, fallback_hit,
reasoning_hit`. Exit 0 whatever the verdict — a grader that exits non-zero on a wrong answer cannot
be used inside a loop. **Never print a verdict the row does not also justify with its counts.**

**Part B — `phase-11/selftest_grade_ab.sh` and `phase-11/fixtures/`.** Hand-write fixture NDJSON
files (do not generate them from a live run) and require the grader to return exactly the stated
verdict for each. At minimum seven fixtures:
| fixture | shape | required verdict |
|---|---|---|
| `f1-correct.ndjson` | normal stream, `ANSWER: <key value>` last | `correct` |
| `f2-wrong.ndjson` | normal stream, `ANSWER: <different value>` | `incorrect` |
| `f3-noanswer.ndjson` | prose only, no `ANSWER:` line | `no-answer` |
| `f4-truncated.ndjson` | reasoning events only, zero visible content | `no-output` |
| `f5-reasoning-only.ndjson` | `ANSWER:` present but only inside a reasoning event | `no-answer` + qualifier `answer-seen-in-reasoning-only` |
| `f6-malformed.ndjson` | one valid line plus one line of non-JSON garbage | grades on the valid line, records the bad-line count, does not crash |
| `f7-empty.ndjson` | zero bytes | `unparseable` |
Add a numeric-normalisation fixture too: `ANSWER: 84.0` against `expected: 84`, `match: numeric` →
`correct`; and the same value against `match: exact_normalized` → record whichever verdict the
implementation actually gives, and if it is `incorrect`, that is why numeric tasks must use
`match: numeric`. Write that observation into `AB-TASKSET.md` §2 rather than leaving it implicit.

The self-test writes `phase-11/fixtures/selftest.tsv` (`fixture, required_verdict,
observed_verdict, observed_qualifier, PASS|FAIL`) and exits non-zero if any row is FAIL. Read the
TSV as text before declaring the task done — an exit code is not the evidence here, for the reason
`phase-10/PHASE-10-FINDINGS.md` §4.6 gives six times over.
