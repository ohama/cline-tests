<objective>
Make `verify_config.sh` able to catch a mode/alias mismatch and a `--thinking` leak — and prove it
by breaking the wrappers on purpose and watching the real script fail.

Purpose: USE-02, ROADMAP criterion 2. The diagnosis first, because it changes the shape of the
work: **a mismatch does not live in any config file.** `providers.json` records neither the mode
flag nor which alias a given invocation used — Phase 10 confirmed `cline -m` leaves `model` at
`"flashnext"` regardless of which alias the call actually used (`phase-10/VRF-04-OBSERVATION.md`
§1). There is nothing to inspect after the fact. The check must therefore be about the *wrappers*:
what they literally contain, and what argv they actually construct.

Phase 10 shipped five instruments that reported clean while observing almost nothing
(`phase-10/PHASE-10-FINDINGS.md` §4.6), every one caught by reading output rather than exit codes.
So the deliverable here is not "checks exist" — it is "the checks were seeded with real defects and
observed to fail". A check that cannot fail is worthless.

Output: `phase-11/verify_wrappers.sh`, an extended `phase-01/config/verify_config.sh`, minimal
call-site guards in the two Phase 4 scripts that consume it, and
`phase-11/selftest_verify_wrappers.sh` with its recorded mutant table.

**Outcome neutrality:** if some defect class turns out to be undetectable by this mechanism, record
it as a measured blind spot in the mutant table (`MISSED`) and in the summary — the same way plan
10-01 recorded MUTANT-4 as a measurement rather than engineering it away. A recorded blind spot is a
better outcome than a check quietly widened until everything passes.
</objective>

  <files>phase-11/verify_wrappers.sh</files>
  <action>
Create `phase-11/verify_wrappers.sh`. It checks a wrapper directory — `$WRAPPER_DIR`, defaulting to
the `phase-11/` directory resolved from the script's own location, so pointing it at a mutant copy
is a one-variable change and so a future relocation of the wrappers changes one default.

**Absence is a failure, not a skip.** If `$WRAPPER_DIR/cline-plan`, `cline-act` or `wrapper.env` is
missing, FAIL. A "wrappers not present, skipping" branch that returns 0 would be exactly the
instrument-that-observes-nothing pattern this phase is trying not to repeat.

Every failure message begins with `FAIL[WRAPPER]: ` and names the assertion. Every pass prints
`OK[WRAPPER]: ` plus what was observed (the actual alias, the actual argv), so the output is
readable evidence rather than a checkmark.

**Group A — static assertions on file contents:**
- `wrapper.env` defines `WRAPPER_PLAN_ALIAS` and `WRAPPER_ACT_ALIAS`, they are non-empty and
  different from each other.
- Each is a member of the known-alias set. **Outcome-neutral membership**, because USE-03 may revert
  the plan wrapper to `flashnext`: plan alias ∈ {`flashnext-plan`, `flashnext`}, act alias ∈
  {`flashnext-act`, `flashnext`}. Neither may be `flashnext-codex` — calling that alias has been
  measured to kill the model server, so it is forbidden outright with its own message.
- `cline-plan` sets `WRAPPER_MODE_FLAG="-p"`; `cline-act` sets it to the empty string and contains
  no `-p`/`--plan` token outside comments.
- Neither wrapper contains a literal alias string (they must go through `wrapper.env`).
- The real binary is referenced by absolute path, and neither wrapper nor the common file invokes a
  bare `cline`.
- No unguarded `"$@"` or `$*` forwards caller arguments into the constructed command. Implement this
  as: extract the construction region (from the `set --` sequence to the invocation line) and assert
  no caller-argument array is appended there. Print the extracted region so the assertion is
  auditable.
- **Optional, opt-in, off by default:** when `WRAPPER_CHECK_ALIAS_LIVE=1`, `curl -sf
  http://127.0.0.1:4000/v1/models` and assert both configured aliases appear in `.data[].id`. This
  is gateway-only and never reaches the model server — `/v1/models` is served by litellm and costs
  zero model requests. It is off by default per hard constraint 5; document that in the script
  header, and name precisely where it is exercised: **plan 11-04, Task 3, Part A0** runs
  `WRAPPER_CHECK_ALIAS_LIVE=1 bash phase-11/verify_wrappers.sh` exactly once against the live
  gateway and records the exit status and the observed `.data[].id` list. Naming the plan and task
  makes the forward reference checkable instead of a promise.

**Group B — behavioural assertions on real captured argv.** Run each wrapper under
`CLINE_WRAPPER_TEST=1 CLINE_WRAPPER_TEST_BIN=$WRAPPER_DIR/testing/stub-cline
VERIFY_CONFIG_NO_WRAPPER_CHECK=1` and assert on what the stub recorded:
- `cline-plan "wrapper-check"` → argv contains `-p`, contains `-m` immediately followed by the
  configured plan alias, contains `-P` followed by the configured provider, contains exactly one
  `-m`, contains zero `--thinking`.
- `cline-act "wrapper-check"` → contains `-m` + act alias, contains neither `-p` nor `--plan`, one
  `-m`, zero `--thinking`.
- `cline-plan --thinking high "wrapper-check"` → **wrapper exits non-zero and the stub argv file is
  byte-unchanged**. This is the USE-02 `--thinking high` check. Comparing the argv file before and
  after is what makes "the flag did not reach the binary" provable rather than assumed.
- `cline-act --thinking high "wrapper-check"` → same.
- `cline-plan -m flashnext "wrapper-check"` → non-zero, stub argv unchanged.

Group B is strictly stronger than Group A — it exercises the code path a real invocation takes,
including any conditional logic — but keep both: Group A catches a wrong literal instantly and
Group B catches wrong behaviour behind a right-looking literal. Say so in the header; they cover
each other's blind spot, the same argument `phase-10/validate_config.sh` rung 3 makes for keeping
two overlapping checks.

Exit **0** on all-pass, **3** on any wrapper failure. Exit 3, not 1, so a caller can tell a wrapper
problem from a `providers.json` problem.
  </action>
  <verify>
