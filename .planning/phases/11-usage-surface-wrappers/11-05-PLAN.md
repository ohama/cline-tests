<objective>
Fix the A/B's rules in writing before any comparison data exists, build the runner, measure what a
run actually costs, and get a human to authorise the spend.

Purpose: USE-03 asks whether `medium` thinking improves results. Two things make a naive answer
worthless. First, the model samples stochastically — `generation_config.json` declares
`do_sample: true, temperature: 1.0` — so a single run per cell cannot separate signal from noise.
Second, thinking shares a fixed per-turn completion budget with the answer (Phase 9 watched `xhigh`
consume a 300-token budget entirely and return empty content at `finish_reason: length`), so an
under-budgeted comparison is rigged against the thinking arm before it starts. A protocol written
after seeing the numbers can be fitted to them; this one is written first, including the rule that
would have produced the opposite decision.

Output: `phase-11/AB-PROTOCOL.md`, `phase-11/run_ab.sh`, a pilot run directory, and a human
authorisation for the main run's budget.

**Outcome neutrality:** the pilot may reveal that the design cannot discriminate — tasks too easy,
tasks too hard, per-run cost too high to afford a meaningful N, or a harness problem. Saying so with
evidence is a better outcome than a number that looks like an answer. §6 of the protocol says this
in advance and the checkpoint offers "abort and report the design as unable to discriminate" as a
first-class option, not a failure.

**Live-request budget for this plan, stated up front and enforced in code: 10.** Planned: 6 pilot
invocations (2 tasks × 3 arms × 1 repetition) plus 4 spare for single operational retries. The main
run's budget is proposed here and spent in plan 11-06.
</objective>

  <name>Task 1: AB-PROTOCOL.md — arms, fairness controls, sizing rule and the pre-registered decision rule</name>
  <files>phase-11/AB-PROTOCOL.md</files>
  <action>
Write the protocol **before** running anything. Sections:

**§1 Arms.** Three, invoked at the flag-minimal shape
`CLINE_NO_AUTO_UPDATE=1 cline -P openai-compatible -m <alias> --compaction agentic --json -t 600 "<prompt>"`
— identical to `phase-10/probe_vrf04_cline.sh`'s already-validated invocation, varying only
`<alias>`:
- **A = `flashnext`** — the ROADMAP's and USE-03's literal control (`openai/` prefix, no reasoning
  parameters anywhere).
- **C = `flashnext-plan`** — the shipped Plan alias (`hosted_vllm/`, `enable_thinking:true` +
  `reasoning_effort:medium`).
- **B = `flashnext-act`** — the **prefix-matched control** (`hosted_vllm/`, thinking off), run at
  reduced replication. Its job is to separate "the reasoning parameter did something" from "the
  `hosted_vllm/` transformation path did something". Phase 10 closed that confound for
  `prompt_tokens` (`phase-10/REACH-PROOF.md` §4, delta 0 across three same-body pairings) but never
  for answer quality or latency, and A-vs-C differs in both prefix and reasoning at once.

**§2 The wrappers are deliberately not used for the A/B, and why.** `cline-plan` sets `-p`, which is
Cline's own agent-mode flag: it restricts the tool set to `switchToActModeTool` only
(`11-RESEARCH.md` Q2, `phase-11/WRAPPER-DESIGN.md` §5). Comparing `cline-plan` against `cline-act`
would confound the reasoning-parameter effect with a tool-availability effect. The A/B holds the
mode flag constant by omitting it in every arm. State plainly that this means the A/B measures the
*alias*, which is the thing USE-03's keep-or-revert decision is actually about, and that the
wrapper-level end-to-end behaviour is covered separately by USE-01/USE-02's own tests.

**§3 Fairness controls, each with its measurement:**
- **Completion budget.** Quote the value plan 11-04 measured (`phase-11/OPEN-ITEMS.md`, open item 2)
  rather than the 3.0.53 figure. State that it is a **shared constraint, not a per-arm knob** —
  `docs/cline-max-tokens-findings.md` established cline does not honour any configured
  `max_tokens`, so neither arm can be given more room than the other. State the consequence: if the
  thinking arm's trace eats that budget, the result is an empty answer, which the grader records as
  `no-output`, **reported as its own category and never folded into "incorrect"**.
- **Timeout.** `-t 600`, carried forward from VRF-04 unchanged, so a slow thinking generation is
  never truncated into what would look like a wrong answer.
- **Prompt size.** Every task's measured `prompt_tokens` must stay far below the live compaction
  trigger printed by `verify_config.sh` (currently 26,100). The pilot measures this; the protocol
  states the abort condition: if any pilot run's `prompt_tokens` exceeds 25% of the trigger, the
  task set is too large and must be reduced before the main run.
- **Stochasticity.** `temperature: 1.0`, `do_sample: true` — cite the `generation_config.json` path.
  Repetitions are therefore mandatory, not optional.
- **Version stability.** `cline --version` captured before and after the whole batch; a mismatch is
  grounds to **discard** the run rather than report it (VRF-04 precedent). State it as a discard
  rule, not a warning.
- **Order.** Cells are executed in a fixed interleaved order (task-major, arm-minor) so that any
  time-varying condition on the shared model — another tenant's load, thermal state — affects the
  arms as equally as possible. Do not run all of arm A and then all of arm C.

**§4 Sizing, and the rule that picks it — written before the pilot.**
Default plan: **8 tasks × (A × N + C × N + B × 1)**. With N=3 that is 8 × 7 = **56 invocations**.
The rule, fixed now:
- Choose the largest N ∈ {5, 3} such that the projected total invocations ≤ 72 **and** projected
  wall clock ≤ 90 minutes, using the pilot's measured median per-invocation seconds for the slowest
  arm.
- If N=3 with 8 tasks exceeds either ceiling, reduce to 6 tasks (dropping the two whose pilot
  behaviour was least informative — state the criterion: prefer dropping a task both arms answered
  identically) and re-apply.
- If N=3 with 6 tasks still exceeds either ceiling, **do not shrink further**: report that the A/B
  could not be sized affordably at a defensible N, and treat that as USE-03's answer with its
  reasoning. This is an allowed outcome.
State the resulting **hard request cap for plan 11-06** as a number, and note that it is a cap on
*model requests observed in the server log*, not on invocations, with a runaway-agent-loop guard:
abort if measured requests exceed 3× the invocation count.

**§5 DECISION RULE — pre-registered.** Write it as its own labelled block:
> **Keep** `cline-plan → flashnext-plan` only if arm C's correct-count exceeds arm A's by at least
> **4 cells out of 24** (with N=3 and 8 tasks; scale proportionally if the sizing rule changes N or
> the task count — state the scaled number explicitly once sizing is fixed). **Otherwise revert**
> `wrapper.env`'s `WRAPPER_PLAN_ALIAS` to `flashnext`, per USE-03's own text.
> The threshold is set at roughly one-sixth of the cells because per-cell N=3 against a
> temperature-1.0 sampler cannot distinguish a smaller gap from noise; a smaller observed gap is
> therefore reported as "no measurable improvement", which USE-03 accepts as a valid pass.
> **What would produce the opposite decision:** a gap of ≥4 cells in C's favour. **What would make
> the comparison void rather than negative:** a `cline --version` change mid-batch; more than 25% of
> either arm's cells grading `unparseable`; or any task whose `prompt_tokens` exceeded the §3 ceiling.
Also state, separately: **latency is reported but does not enter the decision rule** — it is
recorded as median and p90 wall clock per arm and discussed in the findings, because a "keep"
decision that doubles every call's latency is information the reader needs even though USE-03's own
text conditions the revert on improvement, not on speed.
And state the statistic that will be reported alongside: a two-sided permutation test over per-cell
correctness (`python3` stdlib, ≥10,000 shuffles), **descriptive only** — explicitly not the decision
criterion, because N is small and treating a p-value as the gate would over-claim.

**§6 What the pilot could reveal that would stop the main run**, written in advance: both arms at
ceiling; both at floor; per-invocation cost making a defensible N unaffordable; a grader that
mis-verdicts real output. Each of these is a legitimate stopping point and is reported as USE-03's
answer with its evidence.

<task type="auto">
  <name>Task 2: run_ab.sh and the pilot</name>
  <files>phase-11/run_ab.sh, phase-11/results/CURRENT_AB_PILOT_RUN</files>
  <action>
**Part A — `phase-11/run_ab.sh`.** Usage:
`run_ab.sh --tasks <id,id,...|all> --arms <A,B,C> --reps <n> --out <run-dir> [--resume]`.
It sources `phase-11/probe_lib11.sh` (envelope, idleness gate, enforced counter) and:
- Builds the cell list in **task-major, arm-minor** order per §3, expanding repetitions in place.
- Before every request: `wait_idle` (`in_flight=0`) and `assert_budget`. The cap comes from
  `--cap`, defaulting to the §4 number; exceeding it **aborts**, it does not warn.
- Runs each cell with the §1 invocation, capturing raw stdout NDJSON to
  `"$RUN"/streams/<task>-<arm>-r<rep>.ndjson`, stderr beside it, plus exit code and wall-clock
  seconds. Never delete a raw stream — the aggregate must be independently recomputable.
- Attributes server-side numbers by **log watermark**, not `tail -N`: capture the `flashnext.err`
  byte offset before the cell and parse only the new lines after it, extracting `prompt_tokens`,
  `completion_tokens`, `max_tokens` and `finish_reason` where present. This is the same attribution
  discipline `phase-09/PRB-03-ORACLE.md` established; `tail -N` on a log shared with Kanban and
  Telegram would silently mis-attribute.
- Grades each stream with `phase-11/grade_ab.py` against the task's `.expected`.
- Appends one row per cell to `"$RUN"/ab.tsv` **immediately after each cell**, never buffered to the
  end: `task_id, arm, alias, rep, exit_code, duration_s, prompt_tokens, completion_tokens,
  finish_reason, verdict, qualifier, extracted_answer, expected, stream_path, requests_this_cell,
  running_total`. Incremental writing means an interrupted run is still fully analysable, and
  `--resume` skips any cell already present in `ab.tsv`, so an interruption costs no budget twice.
- **Retry policy, narrow and recorded:** retry a cell at most once, and only on an *operational*
  failure (non-zero exit, empty stream, connection error). **Never** retry because a verdict was
  disappointing. Mark retried rows.
- Runaway guard: if `requests_this_cell` exceeds 3 for a task designed as single-turn, record it and
  abort the run — a task that has started an agent loop is no longer the instrument the protocol
  describes.
- Bracket the whole run with `cline --version` and with `preflight11`/`postflight11`, and write
  `"$RUN"/manifest.txt` holding: the protocol's §4 sizing decision in force, the alias per arm, the
  timeout, the cap, the task ids, the start/end versions, and the live compaction trigger value read
  from `verify_config.sh`'s own output.

**Part B — run the pilot.** `--tasks <two ids> --arms A,B,C --reps 1 --cap 10`. Choose the two tasks
to span categories (one word problem, one code-trace). Then, reading `ab.tsv` and the raw streams as
text — not the exit code — record in the run directory a short `pilot-notes.md` covering:
- median and max per-invocation wall clock per arm;
- measured `prompt_tokens` per task, and each as a percentage of the live compaction trigger,
  against §3's 25% abort condition;
- measured `completion_tokens` and `finish_reason` per cell, and whether the thinking arm shows any
  sign of budget starvation;
- the grader's verdict per cell, and — importantly — a **manual read of at least two raw streams**
  to confirm the grader's verdict matches what the model actually said. A grader that agrees with
  itself is not evidence; this is the step that catches a mis-verdict before 56 more runs are built
  on it;
- the sizing decision produced by applying §4's rule to the measured numbers, shown as the
  arithmetic, and the resulting proposed total invocation count and request cap for plan 11-06.

If the pilot triggers any §6 stopping condition, write that as the conclusion and carry it into the
checkpoint as the recommended option — do not adjust the design to get past it.
  </action>
