<objective>
Build the oracle: a pure function that reads a captured Cline `--json` NDJSON stream plus a slice of
`flashnext.err` and decides, with evidence, which of exactly three things happened —
① compaction fired at ~26.5k, ② no compaction and the server rejected at 32,768, ③ anything else.

Purpose: VER-02 and VER-03. VER-02 forbids judging by the Cline UI progress bar; the verdict must rest
on the API `usage` events and/or the server's own `prompt_tokens` log lines. VER-03 requires the three-way
distinction. This is written test-first because the classification rules are exactly the kind of thing that
looks obvious and is wrong: the ③ bucket has to absorb "the run finished before it ever reached the
trigger", which is a very likely real outcome and must NOT be silently reported as a pass or a failure.

Output: `phase-01/parse_result.py` plus a fixture-driven test suite, both runnable with zero non-stdlib
dependencies and with no model server involved.
</objective>

<feature>
  <name>Three-way compaction verdict classifier</name>
  <files>phase-01/parse_result.py, phase-01/tests/test_parse_result.py, phase-01/tests/fixtures/*</files>
  <behavior>
`classify(ndjson_events, server_log_lines, predicted_trigger=26542, max_kv=32768) -> Verdict`

The `Verdict` carries: `outcome` (one of the three literals below), `reason` (one short sentence),
`peak_input_tokens` (max per-iteration `usage.inputTokens` seen), `peak_prompt_tokens` (max
`prompt_tokens=` seen in the server log slice), `compaction_events` (list of the raw notice payloads),
`server_error` (the 400 text if present), and `evidence_source` (`"ndjson_usage"`, `"flashnext_err"`,
or `"both"`).

Cases:

1. `"compaction_fired"` (outcome ①) — the stream contains an `agent_event` whose
   `event.type == "notice"`, `event.noticeType == "status"`, and `event.message` starts with
   `"auto-compact"` (matches both `auto-compacting` and `auto-compacted`).
   Verdict must surface `metadata.triggerTokens`, `metadata.maxInputTokens`, and, from the
   `auto-compacted` event, `tokensBefore`/`tokensAfter`/`messagesBefore`/`messagesAfter`.
   → `expect(classify(fixture_outcome1).outcome).toBe("compaction_fired")`
   → `expect(classify(fixture_outcome1).compaction_events[0]["metadata"]["triggerTokens"]).toBe(26542)`

2. `"server_400_no_compaction"` (outcome ②) — NO `auto-compact*` notice anywhere, AND the stream contains
   an `agent_event` with `event.type == "error"` whose message matches the mlx_vlm.server rejection
   shape. Match on `MAX_KV_SIZE` OR the phrase `context tokens` together with a number — do not match on
   generic "error". The verdict's `reason` must state that Cline does not self-heal from this error
   (its overflow-recovery classifier's 8 regexes do not match this text).
   → `expect(classify(fixture_outcome2).outcome).toBe("server_400_no_compaction")`

3. `"other"` (outcome ③) — everything else. Two distinct sub-reasons must be distinguishable via
   `Verdict.reason`:
   a. **below_trigger** — run ended with `finishReason` `completed` and `peak_input_tokens <
      predicted_trigger`. Reason text must say the test never reached the threshold and must recommend
      increasing the filler file count. This is inconclusive, NOT a failure of the phase.
   b. **unexpected** — timeout, crash, non-context error, or an `overflow-recovery-compact*` notice
      appearing (which would mean the recovery path fired, contradicting the research prediction).
   → `expect(classify(fixture_outcome3_below).outcome).toBe("other")`
   → `expect("never reached" in classify(fixture_outcome3_below).reason).toBe(True)`
   → `expect(classify(fixture_outcome3_timeout).reason).toContain("unexpected")`

4. Oracle independence (VER-02) — `parse_flashnext_log(lines)` extracts every `prompt_tokens=(\d+)` and
   every `max_tokens=(\d+)` from `Generation queued:` / `Prefill started:` / `Prefill completed:` /
   `Request completed:` lines and returns peaks.
   → `expect(parse_flashnext_log(sample).peak_prompt_tokens).toBe(<value in fixture>)`
   The verdict must NEVER be derived from any field that only exists in the TUI rendering; assert in a
   test that `parse_result.py` contains no reference to a progress-bar/percentage source.

5. Disagreement handling — if both oracles are present and `peak_prompt_tokens` and
   `peak_input_tokens` differ by more than 15%, `evidence_source` is still `"both"` but `reason` must
   append a `WARNING: oracle disagreement` note. Neither oracle silently wins.

6. CLI behavior — `python3 phase-01/parse_result.py --ndjson <f> --server-log <f> [--predicted-trigger <int>] --out <dir>`
   writes `<dir>/verdict.md` (headed with the outcome, the two peak numbers, the trigger used, the
   evidence, and the timestamp) and exits with code 0 for ①, 2 for ②, 3 for ③. Exit codes must be
   distinct so `run_regression.sh` can branch without re-parsing.
   `--predicted-trigger` defaults to `PREDICTED_TRIGGER_TOKENS` (26542, the value at contextWindow
   32768) and is threaded straight into `classify(..., predicted_trigger=...)`. It exists because the
   `below_trigger` sub-case of outcome ③ is a comparison against that number, and Plan 05 Branch B2 may
   lower `contextWindow` (⇒ a different trigger) as a `max_tokens` mitigation. `run_regression.sh`
   derives the trigger from the live `providers.json` and passes it here, so the classifier never judges
   against a config that did not run. `verdict.md` must print which trigger value it used and whether it
   came from the flag or the default.
  </behavior>
  <implementation>
Read NDJSON line by line, tolerating blank/partial trailing lines (a killed run leaves a truncated last
line — `json.JSONDecodeError` on the final line must not crash the parser; count it and note it).

Per 01-RESEARCH.md: `usage.inputTokens` is the size of that single fresh request (system prompt + full
history + tools), while `totalInputTokens` is a separate cumulative-cost field. Compare
`inputTokens` — never `totalInputTokens` — against the trigger.

Keep `classify()` pure (no file I/O, no clock) so tests call it directly; do file reading and
`verdict.md` rendering in separate functions.
  </implementation>
</feature>
