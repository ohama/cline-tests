<objective>
Build and run the standing Phase 3 gate: one re-runnable script that proves all four ROADMAP
success criteria, and that is itself proven able to fail.

Purpose: plans 03-01 and 03-02 produced the mechanism and the assertion machinery. Nothing is yet
*proven*. This plan wires them together into the artifact that Phases 4, 5, 6 and 7 will call the
same way Phase 2 left `phase-02/infra/verify_no_regression.sh` as a standing gate — and it adds the
meta-test that Phase 2 did not have: a deliberate negative control that feeds the verifier a
fail-open profile and requires the verifier to notice. Per 03-RESEARCH.md Pitfall 5, a sandbox that
passes because it fails open is the failure mode that a shallow test cannot see; the only defence is
to demonstrate the test itself can fail.

Cost note: every case here uses `/bin/cat`, `/bin/sh` or a five-line Node script. No `cline`
invocation happens in this plan — a real run costs ~64s TTFT, requests are serialized at
`--max-num-seqs 1` since Phase 2, and each invocation risks `providers.json` corruption. The single
budgeted `cline` smoke test belongs to plan 03-04.

Output: `phase-03/sandbox/verify_sandbox.sh` and a timestamped evidence directory under
`phase-03/results/` containing every case transcript, both generated profiles, and the verdict file.
</objective>

<task type="auto">
  <name>Task 1: verify_sandbox.sh — the standing gate covering criteria 1-4</name>
  <files>phase-03/sandbox/verify_sandbox.sh</files>
  <action>
Write `phase-03/sandbox/verify_sandbox.sh`, modelled structurally on
`phase-02/infra/verify_no_regression.sh` (read it first): `set -uo pipefail`, sources
`phase-03/sandbox/config.env`, accepts `--out-dir <dir>` (default
`$RESULTS_ROOT/$(date -u +%Y%m%dT%H%M%SZ)-sbx`), makes no change to any live service, and is safe to
re-run any number of times. macOS `/bin/bash` is 3.2 — parallel indexed arrays only, no `declare -A`.

It exports `EVIDENCE_DIR="$OUT_DIR"` so `assert_denied.sh` writes a transcript per case, then runs
two groups.

**Setup:** call `phase-03/sandbox/make_fixtures.sh --root "$FIXTURES_ROOT"` first (rebuilds a clean
tree, so a leftover file from a previous run cannot mask a failure). Generate BOTH profiles with
`gen_sandbox_profile.py`, copying each into `$OUT_DIR` as evidence:
  - `$OUT_DIR/fixture.sb` from `$FIXTURES_ROOT/allowed_repos.test.json`
  - `$OUT_DIR/production.sb` from `$ALLOWED_REPOS_JSON` (with `--extra-allow "$CLINE_DATA_DIR"` and
    each `EXTRA_ALLOW_PATHS` entry, exactly as `run_sandboxed.sh` does)

**Profile sanity pre-check (fail-open guard), before any case runs:** for each profile assert it is
non-empty, its first line is `(version 1)`, it contains `(allow default)`, it contains BOTH
`(deny file-read* (subpath "<realpath of PROTECTED_ROOT>"))` and the matching `file-write*` line,
and the index of the first `(allow file-read*` punch-through line is greater than the index of the
deny lines. Abort with exit 1 if any fails — a profile that lost its deny rules would make every
subsequent "allow" case pass for the wrong reason.

**Group F — fixture profile (`$OUT_DIR/fixture.sb`), each case via `assert_denied.sh`:**
  - `F1 allow-read-in-whitelist` — `/bin/cat <fx>/allowed/canary.txt`, `--expect allow
    --expect-stdout ALLOWED-CANARY-OK`
  - `F2 deny-read-outside` — `/bin/cat <fx>/forbidden/secret.txt`, `--expect deny --target secret.txt`
  - `F3 deny-write-outside` — `/bin/sh -c "echo x > <fx>/forbidden/newfile.txt"`, `--expect deny
    --write-target <fx>/forbidden/newfile.txt` (helper asserts the file is absent afterwards)
  - `F4 deny-exec-command-outside` — `/bin/sh -c "cat <fx>/forbidden/secret.txt"`, `--expect deny
    --target secret.txt` — the `execute_command` shape of the same denial
  - `F5 deny-prefix-trap` — `/bin/cat <fx>/allowed_extra_should_not_match/canary.txt`,
    `--expect deny --target canary.txt`. Additionally assert the string `PREFIX-TRAP-CANARY` does
    not appear anywhere in that case's captured stdout.
  - `F6 allow-canonical-of-symlinked-entry` — `/bin/cat <fx>/symlinked/real/canary.txt`,
    `--expect allow --expect-stdout CANON-CANARY-OK`. This is the canonicalization regression: the
    whitelist entry is spelled `<fx>/symlinked/link`, so this case only passes if the generator
    realpath'd it. If `realpath()` is ever dropped, this case flips to a denial and the gate fails.
  - `F7 deny-escape-symlink` — `/bin/cat <fx>/allowed/escape-link/secret.txt`, `--expect deny
    --target secret.txt` — a symlink inside an allowed directory pointing out must not be a hole.
  - `F8 probe` — `/usr/bin/sandbox-exec -f "$OUT_DIR/fixture.sb" /usr/bin/env
    ALLOWED_PATH=<fx>/allowed FORBIDDEN_PATH=<fx>/forbidden node phase-03/sandbox/probe_fs.js`,
    capturing stdout to `$OUT_DIR/probe-sandboxed.txt`. Assert line by line:
    `inproc-read-allowed SUCCEEDED`, `inproc-write-allowed SUCCEEDED`, and
    `DENIED` for `inproc-read-forbidden`, `inproc-write-forbidden`, `subproc-read-forbidden`,
    `subproc-write-forbidden`, `escape-symlink-read`. Any `ERROR` result is a FAIL, not a pass —
    print the offending line. This one case is what proves SBX-02 and SBX-03 are the same mechanism.

**Group P — production profile (`$OUT_DIR/production.sb`):**
  - `P1 allow-scratch-repo-read` — `/bin/cat workspace/scratch-repo/README.md`, `--expect allow`
  - `P2 allow-scratch-repo-write` — `/bin/sh -c "echo ok > workspace/scratch-repo/.sbx-write-probe"`,
    `--expect allow`, then remove the probe file
  - `P3 deny-bench-canary-read` (CRITERION 4) — `/bin/cat bench/runs/CANARY.txt`, `--expect deny
    --target CANARY.txt`
  - `P4 deny-bench-listing` (CRITERION 4) — `/bin/sh -c "cat bench/runs/*"`, `--expect deny`, and
    additionally grep every file in `$OUT_DIR` for `SBX04-CANARY-MUST-NOT-BE-READABLE-FROM-INSIDE-SANDBOX`
    outside of the profile/verdict files; the canary content must never appear in any captured
    sandboxed stdout.
  - `P5 deny-read-own-whitelist` — `/bin/cat "$ALLOWED_REPOS_JSON"`, `--expect deny` — the agent
    cannot read the file that defines its own boundary (workspace/ itself is not whitelisted; only
    the individual repos under it are).
  - `P6 deny-read-planning-dir` — `/bin/cat .planning/STATE.md`, `--expect deny` — a project file
    outside the whitelist but inside `$HOME`.

**Verdict output** to `$OUT_DIR/sbx-verdict.txt` and stdout, one line per ROADMAP criterion so the
mapping is explicit and greppable:
```
CRITERION 1 (SBX-01 ALLOWED_REPOS.json exists and is the source of truth): PASS|FAIL <detail>
CRITERION 2 (SBX-02 read/write outside the whitelist actually fails): PASS|FAIL <cases>
CRITERION 3 (SBX-03 execute_command outside the whitelist is blocked by sandbox-exec): PASS|FAIL <cases>
CRITERION 4 (SBX-04 bench results dir unreadable from inside the sandbox): PASS|FAIL <cases>
```
Criterion 1's check is concrete: `ALLOWED_REPOS_JSON` exists, parses, every entry resolves to an
existing directory, and `$BENCH_DIR` is not equal to nor a parent of any entry.

Also print a `CASES <passed>/<total>` line and a `CRASHED <n>` count. Exit code contract, mirroring
Phase 1's `parse_result.py`: `0` = all criteria PASS, `1` = at least one FAIL, `2` = at least one
case classified CRASHED (inconclusive — a crashed sandbox is not a denied one and must never be
reported as a pass).

Header comment must state: this is the standing Phase 3 gate; Phases 4/5/6/7 should call it before
trusting `run_sandboxed.sh`; it mutates no live service; and it carries the same stated scope
limitation as `config.env` (protects `$HOME`, not the whole filesystem).
  </action>
  <verify>
`chmod +x phase-03/sandbox/verify_sandbox.sh && phase-03/sandbox/verify_sandbox.sh --out-dir phase-03/results/selfcheck`
runs to completion and prints four `CRITERION` lines plus `CASES n/n`. Confirm the script never

`grep -n 'assert_denied.sh' phase-03/sandbox/verify_sandbox.sh | wc -l` is at least 12, and

  <done>The gate runs end to end, delegates every allow/deny judgement to assert_denied.sh, aborts early if either generated profile lost its deny-root lines, and emits one verdict line per ROADMAP criterion with the 0/1/2 exit contract.</done>

```
(version 1)

```
and runs Group F against it, inverting the expectation: the run PASSES the negative control only if
the profile sanity pre-check rejects it, or (if the pre-check is bypassed with
`--negative-control-skip-precheck`) if every deny case reports `FAIL not-denied`. If any deny case
still reports PASS against a profile with no deny rules at all, the verifier itself is broken and
the mode exits 1 with `NEGATIVE-CONTROL FAILED: verifier reports PASS against a fail-open profile`.

Run all three of these and archive the output under
`phase-03/results/<UTC ts>-negative-control/`:

  2. `verify_sandbox.sh --negative-control --negative-control-skip-precheck` — expect every Group F
     deny case to report `FAIL not-denied`, and the mode to exit 0 meaning "the verifier correctly
     detected the fail-open sandbox".
