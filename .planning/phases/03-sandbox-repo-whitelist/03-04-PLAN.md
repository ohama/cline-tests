<objective>
Answer 03-RESEARCH.md's Open Question 1 with exactly one budgeted real `cline` run under the
sandbox, then write the phase's shipped-state document.

Purpose: everything proven so far used `/bin/cat`, `/bin/sh` and a Node stand-in — deliberately, per
research, because those share the same syscall surface and cost nothing. What remains genuinely
unknown is whether the real `cline` binary's startup (hub daemon spawn, auto-update check, its own
credential-store read) needs any punch-through beyond the generic Cline-data-dir allow already in
the profile. That question needs one real invocation and no more: a `cline` run costs ~64s TTFT,
requests are serialized at `--max-num-seqs 1` since Phase 2, the binary self-updates in the
background on nearly every invocation despite `CLINE_NO_AUTO_UPDATE=1`, and any arbitrary invocation
strips `models[]`/`contextWindow` from `~/.cline/providers.json`. Phase 1 already built the exact
tooling for this (`apply_provider_config.sh`, `verify_config.sh`, the reinstall-chaining pattern);
this plan uses it rather than re-deriving it.

Why this plan is autonomous despite touching `cline`: the risky part is config drift, and that has a
built, tested, idempotent heal path. The one place a human judgement could be needed — "the sandbox
blocks cline, should we widen it?" — is removed by a bounded rule stated in the task: widen only
within the pre-declared candidate list of Cline-owned directories, and for anything broader make no
change at all and hand the finding to Phase 4 as a documented open item. Failing closed needs no
approval; widening the security boundary would, and this plan never does it.

Output: one recorded smoke-test result under `phase-03/results/`, at most a narrow documented
`EXTRA_ALLOW_PATHS` entry, and `docs/sandbox-whitelist.md`.
</objective>

  <name>Task 1: The single budgeted cline smoke test under the sandbox</name>
  <files>phase-03/results/, phase-03/sandbox/config.env</files>
  <action>
**Pre-flight, before any cline invocation:**
  1. `ps aux | grep -E '[c]line|[k]anban'` — confirm no cline or kanban process is running, so a
     reinstall cannot pull the binary out from under a live process (Phase 1, plan 01-04 pattern).
  2. `phase-03/sandbox/verify_sandbox.sh --out-dir phase-03/results/<ts>-pre-cline` must exit 0.
     Do not proceed if the gate is red.
  3. Snapshot `~/.cline/data/settings/providers.json` into the results directory.

**The invocation.** ONE shell command, chained, because `cline` background-updates itself within
seconds of any invocation — a manual `cline` call between the reinstall and the real run reintroduces
the drift. Run through the wrapper so the profile is regenerated fresh, and start with the cheapest
possible subcommand:

```
bash -c 'set -a; . phase-01/config/cline-invocation.env; set +a; \
  npm install -g cline@3.0.53 >/dev/null 2>&1 && \
  phase-03/sandbox/run_sandboxed.sh -- "$CLINE_BIN" --version' \
  > phase-03/results/<ts>-cline-smoke/version.out 2> phase-03/results/<ts>-cline-smoke/version.err
```
Record the exit code. Then classify the outcome into exactly one of three, and write the verdict to
`phase-03/results/<ts>-cline-smoke/verdict.txt`:

  - **(A) CLEAN** — exit 0 and stdout is `3.0.53`. The generic Cline-data-dir punch-through is
    sufficient; Open Question 1 is answered, no profile change needed.
  - **(B) BOUNDED-FIX** — non-zero exit with a permission error naming a specific Cline-owned
    directory that is on the pre-declared candidate list in `config.env`
    (`$HOME/.npm`, `$HOME/.cache`, `$HOME/.config/cline`, `$HOME/Library/Caches/cline`). Add ONLY
    that path to `EXTRA_ALLOW_PATHS` in `phase-03/sandbox/config.env`, with an inline comment giving
    the date, the exact stderr line that motivated it, and which cline subcommand triggered it. Then
    re-run the smoke test once. Two bounded fixes maximum; if a third distinct path is demanded,
    treat it as (C).
  - **(C) BLOCKED-NEEDS-HUMAN** — the failure demands a punch-through broader than a specific
    Cline-owned directory (for example all of `$HOME/Library`, `$HOME` itself, or an unbounded set),
    or the process died on a signal with no diagnostic (exit > 128 / empty stderr — a crashed
    sandbox, per 03-RESEARCH.md Pitfall 1, NOT a denial). **Make no profile change.** Record the
    exact stderr, the classification, and write the finding into `docs/sandbox-whitelist.md` (task 2)
    as an explicit open item for Phase 4, stating that widening the boundary is a human decision and
    was deliberately not taken.

  Outcome (C) does not fail this phase: none of the four ROADMAP success criteria require `cline`
  itself to run under the sandbox — criteria 2/3/4 are already proven by plan 03-03 at the kernel
  level, and Phase 4 owns the headless wrapper. Say so plainly in the verdict file so a later reader
  does not mistake a documented open item for a hidden failure.

**Post-flight, unconditionally, whatever the outcome:**
  1. `phase-01/config/verify_config.sh`; if it exits non-zero, run
     `phase-01/config/apply_provider_config.sh` and then `verify_config.sh` again. Capture both
     runs' output into the results directory. Drift here is expected and recoverable, not a failure.
  2. `phase-01/config/check_versions.sh` (or `cline --version` via the same chained pattern if that
     script needs it) to record whether the binary drifted off 3.0.53 again, purely as evidence.
  3. Re-run `phase-03/sandbox/verify_sandbox.sh` — it must still exit 0 with all four criteria PASS,
     including after any `EXTRA_ALLOW_PATHS` change (a widening that broke criterion 2, 3 or 4 must
     be reverted immediately).
  4. Write a `README.md` in the smoke-test results directory recording: the outcome letter, the exact
     command chained, stdout/stderr, the pre- and post- config-guard results, and the statement that
     this was the phase's ONLY `cline` invocation.
  </action>
  <verify>
`cat phase-03/results/*-cline-smoke/verdict.txt` shows exactly one of A / B / C with the supporting
stderr quoted. `phase-01/config/verify_config.sh; echo rc=$?` prints `rc=0` (after heal if needed).
`phase-03/sandbox/verify_sandbox.sh; echo rc=$?` prints `rc=0` with four `CRITERION ... PASS` lines.

1. **무엇을 만들었나** — `ALLOWED_REPOS.json` (SBX-01) 하나가 진실의 원천이고,
   `gen_sandbox_profile.py` 가 그것을 `workspace/sandbox.sb` 로 컴파일하며, `run_sandboxed.sh` 가
   호출 때마다 프로필을 새로 만든 뒤 `sandbox-exec` 로 감싼다는 흐름. `sandbox.sb` 는 절대 손으로
   고치지 않는다는 규칙을 명시.

2. **왜 Cline 자체 기능을 쓰지 않았나** — `03-RESEARCH.md` 가 실제 설치된 바이너리에 `strings` 로
   확인한 사실 두 가지를 기록: `CLINE_COMMAND_PERMISSIONS` 와 `.clineignore` 는 이 빌드에
   존재하지 않으며(유일한 매치는 무관한 Discord.js 상수), `CLINE_SANDBOX`/`CLINE_SANDBOX_DATA_DIR`
   는 설정/데이터 저장 위치만 옮길 뿐 파일시스템 샌드박스가 아니다. 따라서 커널이 강제하는
   `sandbox-exec` 만이 유일한 수단이다.

3. **⚠️ 이 샌드박스의 한계 (명시된 범위 경계)** — 이 문서에서 가장 눈에 띄어야 하는 절.
   프로필의 베이스는 `(deny default)` 가 아니라 `(allow default)` + `$HOME` 통째 deny +
   화이트리스트 punch-through 다. 그러므로:
   - **보호되는 것**: `$HOME` 아래 화이트리스트 밖의 모든 경로.
   - **보호되지 않는 것**: `$HOME` 밖 — `/tmp`, `/opt`, `/usr/local`, 그리고 외장 볼륨이나
     네트워크 공유가 마운트될 경우 그 내용. 샌드박스 안의 프로세스는 여전히 읽고 쓸 수 있다.
   - 이것은 실수가 아니라 **의도적으로 받아들인 범위 경계**다. 조사 시점에 이 기계에는 보호가
     필요한 다른 마운트 지점이 없었고, 기계의 저장소 구성이 바뀌면 재검토해야 한다.
   - `(deny default)` 를 쓰지 않은 이유도 함께 기록: 실측에서 dyld 가 런타임 의존성을 읽지 못하는
     순간 실제 바이너리가 진단 메시지 하나 없이 SIGABRT 로 죽었다. "종료 코드가 0 이 아니면 차단된
     것"이라는 순진한 테스트는 그 크래시를 성공한 차단으로 오보한다 — 이 프로젝트의 모든 차단
     테스트가 stderr 의 실제 거부 신호까지 확인하는 이유.
   이 절을 요약이나 각주로 줄이지 말 것.

4. **저장소를 추가하려면** — `workspace/ALLOWED_REPOS.json` 의 `repos` 배열에 절대 경로 한 줄을
   추가하고 `verify_sandbox.sh` 를 돌린다. 그게 전부다(프로필은 매 호출마다 재생성된다).

   (`bench/` 가 그 아래에 있어 SBX-04 가 깨진다), 그리고 `sandbox.sb` 를 손으로 고치지 말 것.
   심볼릭 링크로 적힌 경로도 생성기가 `realpath()` 로 정규화하므로 안전하지만, 정규화 단계를

   - 종료 코드와 stderr 는 감싼 명령의 것이 그대로 전달된다.
   - 화이트리스트 밖 경로를 건드리는 명령은 `Operation not permitted` 로 거부된다 — Phase 4

   - 기본 작업 디렉터리로 쓸 수 있는 화이트리스트 안 경로: `workspace/scratch-repo`.
   - 상시 게이트: `phase-03/sandbox/verify_sandbox.sh` (종료 코드 0=전부 통과, 1=실패,
     2=크래시/판정 불가). Phase 4·5·6·7 은 이 래퍼를 믿기 전에 이걸 먼저 돌린다.
