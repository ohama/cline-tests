<objective>
Answer the question this gap phase exists to answer: **what change, if any, would have let these
tasks survive?** — and get a human decision before anything shipped is touched.

Purpose: 07-11 and 07-12 establish what killed each task. Knowing the cause does not by itself
choose a remedy, and the obvious remedy (lower `contextWindow` again) may not address the actual
mechanisms. This plan tests each candidate against each measured cause and refuses to recommend one
that does not fit.

Output: a candidate-versus-cause matrix, a recommendation with a falsification condition (or an
honest indeterminate), and a recorded user decision. **No production file is modified here** —
07-15 executes whatever is decided.
</objective>

Standing facts that bound the arithmetic (from `docs/32k-compaction-policy.md`):
- Server budget is `prompt_tokens + max_tokens <= 32768` (`MAX_KV_SIZE`), enforced before prefill.
- `settings.contextWindow` maps to `maxInputTokens`; `trigger = maxInputTokens x 0.9`.
- Shipped value is `contextWindow: 29000` → trigger `26,100`.
- The 29000 value was sized around a measured overshoot of **2,700–3,100 tokens**, obtained from a
  **synthetic** regression using uniform ~1,440-token filler files read one at a time.
</context>

  <name>Task 1: Build the candidate-versus-root-cause matrix with per-task arithmetic</name>
  <files>phase-07/results/&lt;UTC&gt;-remediation/CANDIDATE-MATRIX.md</files>
  <action>
Create `phase-07/results/$(date -u +%Y%m%dT%H%M%SZ)-remediation/`.

First, restate the root causes from 07-11 and 07-12 as one row per distinct mechanism (not one row
per task — if two tasks share a mechanism, merge them; if one task had two, split it). Carry each
mechanism's measured numbers with it.

Then, per task, compute the **required headroom**: the largest `prompt + max_tokens` the task
actually attempted, minus 32,768. This is the deficit any remedy must close. Show the arithmetic.
Where a task's peak came from a rejected request, use the attempted figure from 07-11's token
ladder, not the accepted-only figure.

Then score every candidate against every mechanism. Candidates to evaluate — **treat all of them as
open questions; do not assume any is right**:

- **A. Lower `contextWindow` further** (e.g. 26000, 24000, 20000). For each trial value compute
  `trigger = value x 0.9`, then `trigger + measured_overshoot + max_tokens` for the overshoot
  actually measured in 07-11 (not the synthetic 3,100), and state whether each task survives.
  Also state the cost: a smaller working set means more compactions, more summarisation calls, more
  wall-clock, and possibly a context too small to hold the task's own repository files.
- **B. Cap tool-output size** so one tool result cannot consume the margin. Determine from the
  evidence whether a single large tool result was implicated, and if so how large. State whether
  such a cap is even reachable through Cline's CLI configuration surface, or whether it would
  require a change this project has ruled out (upstream PRs are out of scope per PROJECT.md).
  If it is not configurable, say so — an unavailable remedy scores zero, not "promising".
- **C. A different `--compaction` strategy.** Enumerate what strategies the pinned cline 3.0.53
  actually exposes; if a task failed because compaction was *skipped* rather than late, state
  whether any available strategy addresses skipping.
- **D. Reduce `max_tokens`.** The stored ladder shows the wire `max_tokens` is dynamic in the bench
  path, and falls to a floor. Compute whether lowering the floor closes any deficit, and what it
  costs (truncated responses).
- **E. Address memory contention** (Docker/colima competing with the model), if 07-12 found
  memory exhaustion to be a material cause. This is an operational remedy, not a context one.
- **F. Accept the limit.** Some tasks may need more context than 32,768 total can provide
  regardless of configuration. For each task, state whether ANY setting of A–E keeps it under the
  wall. If none does, F is the correct answer for that task and must be scored as a win, not a
  concession.

Score each cell as `closes` / `partially closes` / `does not close` / `not applicable` /
`unknown-from-evidence`, each with a one-line justification. `unknown-from-evidence` is a legitimate
cell value.
  </action>

  </verify>
  <done>

  <files>phase-07/results/&lt;UTC&gt;-remediation/RECOMMENDATION.md</files>
  <action>
Write the recommendation. Required sections:

1. **The answer in one paragraph** — what change, if any, would have let these tasks survive. If
   the honest answer is "none of the available changes would have saved task X", write that.

2. **Recommended action**, one of:
   - a specific config change with its exact value and the file that must apply it, or
   - an operational change (e.g. do not run bench tasks while colima holds memory), or
   - no change, with the reason, or
   - **indeterminate** — the stored evidence does not settle it. If so, list the specific captures
     that would (e.g. per-request cline-side token accounting, host memory pressure sampled during
     the run, on-wire request bodies) and where in the harness each would be added.

3. **Cost of the recommendation** — what it makes worse. A lower `contextWindow` trades working-set
   size and wall-clock for headroom; that trade must be stated in measured terms, not asserted as
   free.

4. **Falsification condition** — the specific observation that would show this recommendation is
   wrong. A recommendation with no falsification condition is not finished.

5. **What this does NOT claim.** In particular: this analysis is about why three specific tasks
   died; it does not establish that the recommendation makes cline-bench pass, and it does not
   change the fact that zero tasks passed. Say so explicitly so 07-15 cannot propagate an
   overclaim into the shipped docs.

6. **Scope check against the Core Value.** `PROJECT.md` records the Core Value as achieved on the
   strength of a synthetic regression. State plainly whether this phase's real-agent evidence
   supports, qualifies, or contradicts that record — and what wording change (if any) 07-15 should
   make. Do not edit `PROJECT.md` here.

An **indeterminate** recommendation is a passing outcome. Do not upgrade a weak inference to a
recommendation in order to have one.
  </action>

  <context>
`settings.contextWindow = 29000` is a whole-stack value. It is enforced by
`phase-01/config/apply_provider_config.sh`, checked by `verify_config.sh`, asserted by the standing
`verify_bench.sh` gate, and documented in `docs/32k-compaction-policy.md` and
`docs/manual/04-32k-operations.md`. It was proven by a Phase 1 synthetic regression that this phase
has **not** re-run. Changing it invalidates that proof until the regression is re-run.

Present to the user, filled in from Task 1 and Task 2:
- the per-task root causes (one line each),
- the recommendation and its cost,
- for each option below, what it fixes and what it breaks.

Costs and exposures to weigh before selecting:

- **Wall-clock and memory contention.** Each live bench task costs 6–10 minutes and competes with
  colima for wired memory — the same contention that 07-12 examines as a possible cause of failure.
  A validation run is therefore not free and not guaranteed clean.
- 🔴 **Live effect on the running Kanban/Telegram services.** `com.ohama.kanban` and
  `com.ohama.kanban-proxy` are running **right now**, and `com.ohama.kanban` is a live wrapper
  around `cline`. Any value 07-15 writes to `~/.cline/data/settings/providers.json` takes effect for
  them **immediately, on their next request, with no restart**. So a real Kanban or Telegram task
  that happens to run during the apply → `verify_config.sh` → regression window would execute
  against an **as-yet-unvalidated** `contextWindow`, and a bad value would only be rolled back
  *after* that task had already been affected. 07-15 Task 1 checks for in-flight work before
  writing and records the residual risk, but that check is a point-in-time snapshot, not a lock.
  `doc-only` and `accept-limit` avoid this exposure entirely; both `config-change` options carry it.
  </context>
  <options>
    <option id="doc-only">
      <name>Document the findings, change no configuration</name>
      <pros>Zero risk to a working, gate-verified stack. The forensic answer is recorded and the
      docs stop implying the synthetic result generalises to real agent loads. Costs no run time.</pros>
      <cons>The next real bench task will die the same way. BCH-01 stays not_met.</cons>
    </option>
    <option id="config-change">
      <name>Apply the recommended config change and re-verify, without a bench run</name>
      <pros>Ships the fix. Validated by re-running `verify_config.sh` and the Phase 1 synthetic
      regression, both of which are cheap and already exist.</pros>
      <cons>Proves the setting is applied and the synthetic case still passes — does NOT prove a
      real bench task now survives. Smaller working set costs wall-clock on every task.</cons>
    </option>
    <option id="config-change-plus-run">
      <name>Apply the recommended change and spend the one permitted live run validating it</name>
      <pros>Only option that produces direct evidence a real task behaves differently under the new
      setting.</pros>
      <cons>6–10 minutes, competes with colima for memory, and a single task is a sample of one —
      a pass would be encouraging but not conclusive, and a failure would not distinguish the
      setting from memory contention.</cons>
    </option>
    <option id="accept-limit">
      <name>Record that this hardware cannot serve these tasks, and change nothing</name>
      <pros>The honest answer if the matrix shows no candidate closes the deficit. Closes the
      question rather than leaving it open, and feeds a clear constraint into v2.</pros>
      <cons>Concedes that real cline-bench tasks are out of reach at 32K on this machine.</cons>
    </option>
  </options>
