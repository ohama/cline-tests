  <name>Task 1: Re-derive the true token ladder, including the rejected requests</name>
  <files>phase-07/results/&lt;UTC&gt;-context-forensics/token-ladder.tsv</files>
  <action>
Create the results dir as `phase-07/results/$(date -u +%Y%m%dT%H%M%SZ)-context-forensics/` and
record the chosen path in a `README.md` there.

For each of `telegram-plugin-refactor` and `v-edit-workspace-tests`, parse its
`bench/runs/20260830T122809Z-phase07-fix/server-log/<task>.flashnext.err.txt` into
`token-ladder.tsv` with columns:
`task, seq, timestamp, request_id, prompt_tokens, max_tokens, sum, outcome`

You must parse **two different line formats**, because the fatal request is only present in the
second one:

1. Accepted requests — `Generation queued: request=<id> prompt_tokens=<P> max_tokens=<M>`
   → `outcome=accepted`.
2. Rejected requests — `WARNING - Request failed: ... error=Request needs <T> context tokens
   (<P> prompt + <G> max generation), but MAX_KV_SIZE is 32768.`
   → `outcome=rejected-maxkv`, `prompt_tokens=<P>`, `max_tokens=<G>`, `sum=<T>`.
3. Any other `Request failed:` line (e.g. a METAL/OOM error) → `outcome=failed-other` with the
   error text preserved in a trailing column.

**This is the crux of the plan.** `run_task.sh` computed `max_prompt_tokens` by grepping only
`prompt_tokens=[0-9]+`, which appears exclusively in accepted-request lines. A request the server
REJECTS is never queued, so its token count is invisible to that grep. The ledger's
`max_prompt_tokens=21036` for `telegram-plugin-refactor` is therefore a lower bound on accepted
requests, NOT the peak the task actually reached. Report both numbers explicitly:
`peak_accepted_prompt_tokens` and `peak_attempted_prompt_tokens`.

Do not assume any specific value. Derive them and report what you find. If the rejection line is
absent for a task, say so — that is itself a finding.
  </action>
  <verify>
`token-ladder.tsv` exists and has at least one row with `outcome=rejected-maxkv` OR an explicit
note in `README.md` naming which task had no rejection line. Cross-check: the count of
`outcome=accepted` rows per task equals
`grep -c 'Generation queued:' <that task's server-log slice>`.
Re-derive `peak_accepted_prompt_tokens` independently with a one-liner and confirm it matches the
`max_prompt_tokens` field in that task's `meta/*.json` (it should — that is the field being audited).
  </verify>
  <done>
For both tasks, `peak_accepted_prompt_tokens` and `peak_attempted_prompt_tokens` are recorded, and
where they differ, the difference is attributed to a specific rejected request quoted verbatim.
  </done>

<task type="auto">
  <name>Task 2: Reconstruct the compaction timeline and quantify overshoot per task</name>
  <files>phase-07/results/&lt;UTC&gt;-context-forensics/compaction-events.tsv</files>
  <action>
From each task's `agent/cline.txt` (and the matching
`agent/sessions/*/*.compaction.json`), extract every `auto_compaction` status record into
`compaction-events.tsv` with columns:
`task, iteration, phase, triggerTokens, maxInputTokens, tokensBefore, tokensAfter, raw_json`

`phase` takes values like `started` / `completed` / `skipped`. **Capture `skipped` records — do
not filter them out.** A skipped compaction is a different failure mode from a late compaction and
the two tasks may not share one.

Then compute, per task:
- `overshoot = tokensBefore - triggerTokens` for each compaction event.
- The maximum overshoot observed.
- Whether the agent ever sat ABOVE `triggerTokens` across multiple consecutive requests without a
  compaction completing (cross-reference the accepted-request ladder from Task 1 by timestamp).

Compare each measured overshoot against the **2,700–3,100 token** figure that
`docs/32k-compaction-policy.md` §4 used to justify `contextWindow=29000`. State the ratio. If a
measured overshoot is several times that budget, say so plainly and identify what arrived in that
turn (a large tool result is the obvious candidate — check the transcript around that iteration
and name the tool call and its approximate size if it is determinable).

If a task shows `skipped` compactions, dig for the reason recorded alongside them, and state
whether the reason is available in the stored record or not.
  </action>
  <verify>
`compaction-events.tsv` has at least one row per task. `grep -c auto_compaction` on each
`cline.txt` is non-zero and the row count is consistent with it. Every row's `overshoot` is
arithmetically re-checkable from its own `tokensBefore` and `triggerTokens` columns.
  </verify>
  <done>
Per task: max overshoot quantified with its ratio to the 2,700–3,100 budget; presence/absence of
skipped compactions recorded; any multi-request stall above the trigger identified by timestamp.
  </done>
