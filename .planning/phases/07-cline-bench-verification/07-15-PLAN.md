  <name>Task 1: Capture rollback state, then apply the decision (or record the no-op)</name>
  <files>phase-07/results/&lt;UTC&gt;-apply/APPLIED.md</files>
  <action>
Create `phase-07/results/$(date -u +%Y%m%dT%H%M%SZ)-apply/` with a `pre/` subdirectory.

**Before anything else**, capture rollback state into `pre/`:
- `cp ~/.cline/data/settings/providers.json pre/providers.json.bak`
- `shasum -a 256 ~/.cline/data/settings/providers.json > pre/providers-hash.txt`
- `ps` snapshot of the six live service pids → `pre/pids.txt`
- host cline version read from the installed package's `package.json`
  (`$(npm root -g)/cline/package.json`) → `pre/host-cline.txt`. **Read the file; do not run the
  `cline` binary for this** — invoking it can trigger the self-update this project is fighting.

**Live-service precondition — gates the config-change branches only. Read `DECISION.md`'s `SELECTION:` FIRST — if it is `doc-only` or `accept-limit`, skip these live-service checks entirely and go straight to the dispatch below; the checks exist only to protect a write.**
`com.ohama.kanban` (a live wrapper around `cline`) and `com.ohama.kanban-proxy` are running, and they
read `~/.cline/data/settings/providers.json` per request with **no restart**. A value written here
therefore reaches any concurrent Kanban or Telegram task immediately — before `verify_config.sh` and
the regression have validated it. So before writing anything, confirm nothing is in flight, using
**read-only checks only** (🔴 do NOT invoke `cline` or `kanban` for this — invoking them is the
self-update drift vector this phase is fighting, and `kanban task list` is not needed):

- `pgrep -fl 'bin/\.cline|bin/cline'` → `pre/inflight-procs.txt`. The cline hub daemon
  (`--cline-hub-daemon`) is long-lived and expected; any *other* `cline` process is a running task.
- mtimes of `~/.cline/logs/kanban.log` and `~/.cline/logs/telegram-connect.log` →
  `pre/inflight-logs.txt`. Require both quiescent for at least 60s.

If either check shows activity: **do not write.** Wait 60s and re-check, up to 5 times. If it is
still active, stop and report a blocker — do not apply a config change underneath a running task.
Record both checks and their result in `APPLIED.md`.

Record the **residual accepted risk** in `APPLIED.md` regardless of the outcome of the checks: this
is a point-in-time snapshot, not a lock, so a task starting during the apply → `verify_config.sh`
→ regression window would still pick up the new value before it is validated. The rollback command
below is the only remedy for that case, and it is after-the-fact.

Then read the selection from 07-14's `DECISION.md`. Dispatch on its canonical `SELECTION:` label
(07-14 is required to resolve every reply, including an off-menu one, to exactly one of four labels
before writing the file):

- **`doc-only` or `accept-limit`** → change nothing. Write `APPLIED.md` stating the selection, that
  no production file was touched, and confirming the post-state hash equals the pre-state hash.
  Skip to Task 3. This is a complete, passing execution.

- **`config-change` or `config-change-plus-run`** → apply the confirmed `contextWindow` value using
  `bash phase-01/config/apply_provider_config.sh` (consult the script for how it takes the value;
  if it hardcodes 29000, change the script's value rather than bypassing it, so the script remains
  the single source of truth that `verify_config.sh` checks against). Then run
  `bash phase-01/config/verify_config.sh` and capture output to `gates/verify_config.txt`.

- 🔴 **Anything else — including a missing, empty, or unrecognised `SELECTION:` label** → this is a
  **blocker**, never a fall-through and never a silent no-op. If 07-14 did not resolve the reply to
  one of the four labels, the authority to act does not exist. Change nothing, copy the unrecognised
  value verbatim into `APPLIED.md`, and stop with a blocker asking the user to confirm one of
  `doc-only` / `config-change` / `config-change-plus-run` / `accept-limit`. **Do not infer intent
  from surrounding prose** — an interpretation is not an authorisation.

Write `APPLIED.md` with: the selection verbatim, the before value, the after value, the
`verify_config.sh` result, and an explicit **rollback command** that restores `pre/providers.json.bak`
and reverts any edit to `apply_provider_config.sh`.
  </action>
  <verify>
`APPLIED.md` exists and names the selection, and records the two in-flight checks plus the residual
risk statement. If the `SELECTION:` label was missing or unrecognised: nothing changed, the plan
stopped as a blocker, and `APPLIED.md` records the unrecognised value verbatim. If no change was

  </verify>

events, and the count of server 400 / `MAX_KV_SIZE` rejections. **If the regression fails at the
new value, that is a decisive finding and the change should be rolled back** using the command from
Task 1 — do so, record it, and say plainly that the recommended value did not survive its own
regression.
