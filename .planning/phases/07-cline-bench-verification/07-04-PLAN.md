<objective>
Run the tasks the user chose, then turn the whole run directory into the two artifacts the
roadmap asks for: prompts and results on disk for every task, and one table of pass/fail and
duration.

Purpose: this is the plan that satisfies BCH-01, BCH-02 and BCH-03 — or that records honestly
which of them was not met and why. The discipline that matters here is refusing to tidy the
table: a task that died on the container's 128k context assumption is a row with a named cause,
not a dropped outlier.

Output: the completed `bench/runs/<RUN>/` with `summary.md` and `config.json`, and a post-batch
gate sweep under `phase-07/results/`.
</objective>

<house_rules_reminder>
All ten house rules from `07-01-PLAN.md` apply. For a long batch, these matter most:
- Sequential only. Docker-local harbor execution uses this machine's resources and every model
  turn queues at `--max-num-seqs 1`; there is no parallelism available even though the tasks are
  logically independent. Never launch two `harbor run` calls at once.
- Between tasks, re-assert: port 3000 unbound, six pids present, free disk still above the floor.
  `run_task.sh` already does this — do not bypass it with a raw `harbor run`.
- Sluggish Kanban/Telegram during the batch is expected. Do not restart anything.
- Stop the batch and report on: swapping / memory pressure on `flashnext`, a pid that moved, a
  bound port 3000, or free disk dropping below the floor.
- `cline` invocation budget this plan: 0.
</house_rules_reminder>

<task type="auto">
  <name>Task 1: Run the selected tasks sequentially into the phase run directory</name>
  <files>bench/runs/, phase-07/results/</files>
  <action>
Read `phase-07/bench/SELECTED_TASKS`. If it contains no task lines (the `stop-at-one` decision),
skip straight to Task 2 and record in `phase-07/results/<UTC>-batch/README.md` that zero
additional tasks were run **by the user's recorded decision**, quoting
`phase-07/results/*-smoke/decision.md`. Do not treat that as a failure of this plan.

Otherwise, for each line in order:
  `bash phase-07/bench/run_task.sh <task-dir-name>`
running into the SAME run directory named by `phase-07/bench/CURRENT_RUN`. `run_task.sh` is
skip-if-done, so an interrupted batch can simply be re-invoked and will not re-burn model time on
tasks that already have a meta record.

Between tasks, append one line to `phase-07/results/<UTC>-batch/progress.txt`:
UTC timestamp, task, verdict, wall-clock, cumulative wall-clock, free disk, `docker system df`
image total. This makes an abandoned batch legible after the fact.

Handling per-task outcomes:
  - `fail-context` (a 400 / context-window rejection): expected for at least some tasks given
    `CW_INJECTION` from 07-02. Record it and CONTINUE to the next task. Do not retry, do not
    tune, do not stop the batch.
  - `fail-infra` (image build failure, OOM, harness error — no model request ever made): record
    the cause verbatim and continue, unless it is a resource failure (OOM, disk), in which case
    stop the batch and report.
  - a task exceeding its own `task.toml` `timeout_sec`: that is harbor's own timeout doing its
    job. Record the wall-clock and the timeout value side by side and continue.
Never edit a task's `task.toml`, `environment/Dockerfile` or `instruction.md` to make anything
pass — that would stop this being an official-suite run.

After the last task, write `bench/runs/<RUN>/config.json`: harbor version, harbor executable
path, cline-bench commit SHA, model spec, BASE_URL, `--agent-kwarg cline-version` value and
whether it was actually honoured inside the container, `CW_INJECTION`, the live task pool size,
the ordered list of tasks attempted, the user's chosen option id, and the UTC start/end of the run.
  </action>
  <verify>
`ls bench/runs/$(cat phase-07/bench/CURRENT_RUN)/meta/*.json | wc -l` equals 1 + the number of
lines in `phase-07/bench/SELECTED_TASKS`.
`progress.txt` has one line per additional task.
`bench/runs/<RUN>/config.json` parses as JSON and names the cline-bench SHA and harbor version.
Six pids unchanged; port 3000 unbound; free disk still above `MIN_FREE_GIB`.
  </verify>
  <done>Every selected task ran once, sequentially, into one run directory, with per-task guards
held and every outcome recorded — including the failures.</done>
</task>

<task type="auto">
  <name>Task 2: Build the BCH-03 table and prove BCH-02 for every task</name>
  <files>bench/runs/, phase-07/results/</files>
  <action>
Run `bash phase-07/bench/make_summary.sh` to produce `bench/runs/<RUN>/summary.md`. Then check it
by hand against the meta records and fix the generator (not the table) if anything disagrees:
  - every attempted task has exactly one row; no task is omitted
  - `fail-context` rows carry, in the note column, the turn at which the 400 appeared and the
    `max_prompt_tokens` observed — the cause, not just the label
  - the totals line adds up to the row count
  - the 한계 section is present and says, in plain language, that a `fail-context` row proves the
    pipeline reached the model and was rejected by the 32K ceiling because the container's Cline
    was unconfigured, NOT that this stack cannot complete agent tasks; and that N passing tasks
    is not evidence about the other tasks in the pool
  - the header states the run count as a fraction of the live pool measured in 07-01

Then write `bench/runs/<RUN>/prompts/INDEX.md`: one row per task listing the relative paths of
`instruction.md`, `task.toml`, `agent-command.txt`, the `system-prompt-probe.txt` verdict, and
the result files (`verifier/reward.txt`, `verifier/test-stdout.txt`, `agent/cline.txt`) with each
file's byte size. This is the file a reader opens to see that BCH-02 is satisfied by prompt
artifacts, not by a transcript.

Measure the run directory's total size (`du -sh`) and record it. If any single copied file
exceeds 5 MB, keep it but note it in `MANIFEST.txt` with its size so the commit's weight is
visible and deliberate; do not silently drop evidence.

Finally run `bash phase-07/bench/verify_bench.sh --out phase-07/results/<UTC>-batch/verify/` and
require exit 0 with every `CHECK:` line PASS.
  </action>
  <verify>
`bash phase-07/bench/verify_bench.sh` exits 0 and its final line reads `CASES 10/10`.
Data-row count in `summary.md` equals `ls bench/runs/<RUN>/meta/*.json | wc -l`.
`grep -c '한계' bench/runs/<RUN>/summary.md` is at least 1.
For every task, both `prompts/<task>/instruction.md` and `prompts/<task>/agent-command.txt` are
non-empty (`find bench/runs/<RUN>/prompts -name 'instruction.md' -empty | wc -l` is 0).
  </verify>
  <done>One table holds pass/fail, duration, verdict class and cause for every attempted task;
an index proves prompt and result files exist for each; and the re-runnable verifier passes.</done>
