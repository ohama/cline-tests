<objective>
Find out, cheaply and from evidence, why the one cline-bench task that ran never reached this
stack's model server — and produce a ranked list of candidate fixes with a verdict on each.

Purpose: ROADMAP criterion 1 (BCH-01) is `not_met` at 1/12 tasks. The user's `stop-at-one`
reasoning was correct *given a broken injection*: every task shares the same invocation shape, so
more runs buy repeated evidence of one known limitation. That reasoning stops applying the moment
a task provably reaches flashnext. So the fix comes first, and the fix needs a diagnosis first.

Output: `phase-07/bench/injection_probe.sh` (a re-runnable probe ladder) and
`phase-07/results/<UTC>-injection-diag/DIAGNOSIS.md` (ranked hypotheses, evidence, verdicts,
candidate fixes).

**This plan runs no `harbor run` and no host `cline`.** Its model spend is bounded to trivially
short container-side probe prompts (a handful of tokens each), and every rung that can be answered
offline is answered offline before any rung that touches the model.
</objective>

<hypotheses>
Rank and test these. They are not equally likely; H1 is the leading one and is the cheapest to
settle, so it goes first.

- **H1 — version skew in the static analysis itself.** 07-02's FINDING says it read "the INSTALLED
  cline 3.0.53 compiled binary." The host binary is **3.0.60** and has been since `Aug 30 13:27`,
  hours before 07-02 ran. So the `sC()` resolver that honours `CLINE_PROVIDER_SETTINGS_PATH`, and
  the `getProviderConfig()` call in the `--json` non-interactive branch, were both confirmed
  against **3.0.60** — while the container installs **3.0.53** (`--agent-kwarg
  cline-version=3.0.53`, and `agent/setup/install-agent-runtime.log` confirms 3.0.53 really
  installed). If either primitive is absent or different in 3.0.53, the whole mechanism is
  addressed at a build that is not running. **This alone would fully explain the observed failure.**
- **H2 — the overlay never landed in the container.** The flag reached harbor, but the bind mount
  and/or the `environment:` entry may not have survived into the created container:
  `${PROJECT_ROOT}` may have interpolated empty in `docker compose`'s own environment; the merge
  order may place harbor's own env-compose file such that the `main` service is reconstructed; or
  the service key `main` may not be the service the agent actually execs into.
- **H3 — CLI args win over the persisted settings.** `-P openai-compatible -k $API_KEY -m $MODELID`
  may cause cline to synthesise an ephemeral provider config from the flags alone (apiKey present,
  `baseUrl` absent → SDK default endpoint), bypassing or overriding whatever the settings file says.
- **H4 — the settings file is read but rejected.** `cline-cw-providers.json` carries a
  `_comment` key and a `lastUsedProvider` key and was authored by hand. If cline validates the file
  with a strict schema, a parse/validation failure would silently fall back to defaults.
- **H5 — the file is unreadable or must be writable.** The mount is `read_only: true` at
  `/opt/harbor-cline-cw/providers.json`. A task image's non-root `USER`, or a settings manager that
  opens its store read-write, would both produce a silent fallback.

These are hypotheses, not conclusions. **Do not assume any of them.** Report what the probes show,
including "none of the above" if that is what happens.
</hypotheses>
