<objective>
Determine whether the `fail-context` label can be trusted at all — by dissecting
`discord-trivia-approval-keyerror` (the task with the most failure events) and by tracing every
byte that drove `run_task.sh`'s verdict for all four post-fix tasks.

Purpose: the milestone audit's headline claim is "3/3 reached-the-model tasks died at the 32K
ceiling." If the classifier that produced those labels can fire on something other than a context
rejection, that headline is unsound and every downstream conclusion inherits the error. This plan
tests the instrument, not just the readings.

Output: a per-task failure composition table, a provenance record of exactly what matched, and
`CLASSIFIER-AUDIT.md` with a correctness verdict. No code is changed here — 07-13 owns the fix.
</objective>

  <name>Task 1: Quantify the failure composition of every post-fix task</name>
  <files>phase-07/results/&lt;UTC&gt;-classifier-audit/failure-composition.tsv</files>
  <action>
Create `phase-07/results/$(date -u +%Y%m%dT%H%M%SZ)-classifier-audit/` and record the path in a
`README.md`.

For each of the four post-fix tasks (`discord-trivia-approval-keyerror`,
`telegram-plugin-refactor`, `filmarchiver`, `v-edit-workspace-tests`), count and timestamp every
distinct failure event in its `server-log/<task>.flashnext.err.txt`, writing
`failure-composition.tsv` with columns:
`task, event_class, count, first_ts, last_ts, sample_line`

Event classes to separate — do NOT collapse them:
- `maxkv-rejection` — lines matching `Request needs [0-9]+ context tokens .* MAX_KV_SIZE is 32768`
- `metal-oom` — lines matching `kIOGPUCommandBufferCallbackErrorOutOfMemory` or
  `Insufficient Memory`
- `other-request-failed` — any remaining `Request failed:` line
- `completed` — `Request completed:` (the denominator; this is what `model_turns` counts)

Then, for `discord-trivia-approval-keyerror` specifically, build a short timeline interleaving its
OOM events with its accepted-request ladder, and answer: **which class dominates, and did the task
die of memory exhaustion or of the context ceiling?** Note that this machine's known failure mode
is Docker/colima competing with the model for wired memory (measured OOM around 20k tokens with
colima holding 2.4 GB) — check whether the OOM timestamps are consistent with that, but do not
assert the colima link unless the stored evidence supports it. If memory-pressure evidence was not
captured during the run, say so rather than inferring.
  </action>
  <verify>
`failure-composition.tsv` has a row per (task, event_class) pair present. Each `count` is
independently re-derivable with `grep -c` against the named pattern on the named file. The four
tasks' `completed` counts match the `model_turns` field in their respective `meta/*.json`.
  </verify>
  <done>
Per-task counts of MAX_KV rejections versus METAL/OOM failures are recorded with timestamps, and
`discord-trivia-approval-keyerror`'s dominant failure class is named.
  </done>

<task type="auto">
  <name>Task 2: Trace exactly which bytes set each verdict, and test the classifier's precision</name>
  <files>phase-07/results/&lt;UTC&gt;-classifier-audit/match-provenance.md</files>
  <action>
Read the verdict rule in `phase-07/bench/run_task.sh` and record it verbatim in
`match-provenance.md`. It has three inputs: `HTTP_400_SEEN`, `MAX_PROMPT_TOKENS`, and
`MODEL_TURN_COUNT`. `HTTP_400_SEEN` is set by a `grep -qE '\b400\b'` run against **two** files:
the server-log slice, and `<trial>/agent/cline.txt`.

For each of the four post-fix tasks, replay those greps yourself against the stored bytes and
record, with surrounding context, **every substring that matched `\b400\b`** in each of the two
files. Quote them. Then classify each match as:
- `true-signal` — it really is a context-window rejection, or
- `false-positive` — it is something else that merely contains the digits 400.

Pay particular attention to two candidate false-positive vectors, but verify rather than assume:
(a) decode telemetry such as `generated_tokens=400` in the server log, and (b) the **benchmark
task's own repository source code**, which is echoed into `agent/cline.txt` and may legitimately
contain HTTP-status literals like `case 400:` or `new ApiError(..., 400, ...)`. If either vector
is real, it means a task can be labeled `fail-context` for reasons unrelated to context.

Then test the opposite direction — a **false negative**. Take the authoritative rejection line
format found in Task 1 (`Request needs N context tokens (P prompt + G max generation), but
MAX_KV_SIZE is 32768.`) and determine whether that line itself contains a bare `400`. If it does
not, the classifier is not detecting context rejections at all in the server log; it is detecting
them only indirectly via whatever litellm wrote into the agent transcript. Record the finding
either way.

Finally, confirm whether `make_summary.sh` re-derives verdicts or merely transcribes the `meta`
field, and confirm `verify_bench.sh`'s B2 allowed-verdict set. This tells 07-13 how far a fix has
to reach.
  </action>
  <verify>
`match-provenance.md` contains, for each of the four tasks, the literal matched strings (or an
explicit "no match in this file") for both grep targets, each labeled `true-signal` or
`false-positive`. The false-negative test on the MAX_KV line is answered yes/no with the line
quoted. The `make_summary.sh` and `verify_bench.sh` findings are stated with line references.
  </verify>
  <done>
Every recorded verdict is explained by named bytes, and the classifier's false-positive and
false-negative behaviour is demonstrated (or shown absent) against real stored data.
  </done>
</task>

   `task | recorded_verdict | what the evidence supports | correct? | why`.
   `correct?` is one of `correct` / `incorrect` / `coincidentally-correct` / `indeterminate`.

   false-positive match — that distinction matters for whether the instrument can be trusted.

2. **Resolution of the `discord-trivia-approval-keyerror` conflict.** The smoke run's
   `phase-07/results/20260830T093515Z-smoke/ANALYSIS.md` calls it `fail-infra`; the milestone audit
   calls it `fail-context`. Establish which run directory each statement describes
   (`bench/runs/20260830T093657Z-phase07/` versus `bench/runs/20260830T122809Z-phase07-fix/`),
   quote each source's own meta record, and state whether this is a genuine contradiction or two
   correct statements about two different runs. If it is the latter, say so plainly — resolving a
   non-contradiction is a legitimate result.

3. **Classifier correctness verdict.** One of: the classifier is sound; the classifier is unsound
   and here are its specific defects; or correctness cannot be determined from stored evidence.
   If unsound, list each defect as a discrete, fixable item with the evidence that proves it —
   this list is the direct input to 07-13.

4. **Impact on the milestone claim.** State what "3/3 reached-the-model tasks died at the 32K
   ceiling" should be restated as, given the evidence. Do not soften and do not exaggerate; if the
   claim survives intact, say that.

5. **Limits** — anything you could not determine, and the specific capture that would settle it.

**An "indeterminate" verdict is an acceptable, passing outcome** provided the missing evidence is
named. Do not manufacture a defect to have something to fix, and do not clear the classifier to
avoid work — follow the bytes.

list.
