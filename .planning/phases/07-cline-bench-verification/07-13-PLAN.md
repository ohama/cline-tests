<objective>
Make the bench's verdict mean what it says — then re-derive the historical verdicts from stored
evidence without touching the stored evidence.

Purpose: 07-12 tests whether `fail-context` is a trustworthy label. If it is not, every number in
`docs/cline-bench.md`, the ROADMAP and the milestone audit is resting on a miscount, and no
remediation decision (07-14) can be made on top of it. This plan repairs the instrument and
re-reads the old measurements with it.

Output: a corrected classifier, a re-classification script, sidecar verdicts for both stored run
directories, and negative-control proof that the new detector is not merely a different way to be
wrong.
</objective>

  <name>Task 1: Repair the verdict rule in run_task.sh</name>
  <files>phase-07/bench/run_task.sh</files>
  <action>
Address each defect in 07-12's defect list. Where 07-12 found no defect, change nothing and say so.

Expected shape of the repair (adjust to 07-12's actual findings — do not apply blindly):

1. **Detect context rejections from the authoritative line.** Match the server's own rejection
   text — `Request needs <T> context tokens (<P> prompt + <G> max generation), but MAX_KV_SIZE is
   <K>` — and/or litellm's `BadRequestError` carrying that same text. Replace the bare
   `grep -qE '\b400\b'` test. A bare `400` must no longer be sufficient to set a context verdict,
   because it matches decode telemetry (`generated_tokens=400`) and the benchmark repository's own
   HTTP-status source literals.

2. **Fix `MAX_PROMPT_TOKENS`.** Take the maximum over BOTH accepted requests
   (`Generation queued: ... prompt_tokens=N`) and rejected requests (the `<P> prompt` capture from
   the rejection line). Keep the accepted-only figure too, under a distinct field name
   (e.g. `max_prompt_tokens_accepted` alongside `max_prompt_tokens_attempted`), so the two are never
   conflated again. Preserve the existing `max_prompt_tokens` key for backward compatibility with
   `make_summary.sh` and `verify_bench.sh`, and document in a comment which of the two it now
   carries.

3. **Separate memory exhaustion from context exhaustion.** Add a distinct verdict class for
   GPU/host memory failures (`kIOGPUCommandBufferCallbackErrorOutOfMemory` / `Insufficient
   Memory`) — e.g. `fail-oom` — and define precedence explicitly in the rule's comment block when a
   task exhibits both (as at least one stored task does). State the precedence you chose and why;
   a task with many OOM events and one context rejection should not be silently reported as a pure
   context failure.

4. **Keep the rule auditable.** The existing comment block above the classifier documents the rule;
   update it so it still describes the code exactly. Add per-task counters
   (e.g. `maxkv_rejections`, `oom_failures`) to the emitted meta record so a future reader can see
   the composition, not just the label.

Do not change how prompts, transcripts or artifacts are captured. Do not change harbor invocation.
Scope is the classification block and the meta record it emits.
  </action>

classification/meta-emit region. The updated comment block enumerates every verdict the code can

  </verify>
