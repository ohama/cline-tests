<objective>
Write the two launchd wrapper scripts and their shared config. These are the entire SVC-03/SVC-04
mechanism: they are what launchd actually supervises, and they are what makes "no crash loop"
and "honest `state = running` with an empty token" true rather than aspirational.

Purpose: Phase 5's two hardest failure modes both live here. `cline connect telegram`
self-daemonizes unless `-i` is passed (the supervised parent would exit instantly and leak
orphaned bot children every ThrottleInterval), and an empty token throws synchronously (a
permanent crash loop that never resolves itself). Both are designed out in the wrapper, not
worked around in the plist.

Output: `phase-05/services/{config.env,wait_for_port.sh,run_kanban_service.sh,run_telegram_service.sh}`.

**Budget: ZERO `cline` invocations in this plan.** Nothing here runs cline or kanban; this plan
authors files and syntax-checks them. `kanban --version` is permitted if a sanity check is wanted
(it is cheap and does not touch cline's config), but is not required.
</objective>

**A load-bearing comment block on `SERVICE_LOG_DIR`** — this is not a style choice:
launchd opens `StandardOutPath`/`StandardErrorPath` itself and the sandboxed child inherits those
fds across exec. Redirecting a sandboxed process's stdio at a path that is not punched through the
`$HOME` deny has produced a bare `Abort trap: 6` (SIGABRT inside Node's own bootstrap, before a
single line of app code) four separate times in this project (03-03 F8, 03-04, 04-02, 04-04). The
other three house services log to `$HOME/llm-system/services/logs/`, which is under `$HOME` and is
NOT punched. `$HOME/.cline` IS always punched, read AND write (confirmed in the live
`workspace/sandbox.sb`: `(allow file-read* (subpath "/Users/ohama/.cline"))` +
`(allow file-write* ...)`), so `$HOME/.cline/logs/` is the log location that cannot resurrect that
crash. **The fix is the log path, never `EXTRA_ALLOW_PATHS` — that stays empty.** If even this
path were to fail, the documented fallback is a path OUTSIDE `$HOME` (the sandbox only denies
under `$HOME`), still never a widening.

**`phase-05/services/wait_for_port.sh`** — `wait_for_port.sh <host> <port> <timeout_s> <interval_s>`.
`#!/bin/bash`, `set -uo pipefail` (not `-e`: a refused connection is data). Loop
`/usr/bin/nc -z -G 2 -w 2 "$host" "$port"` until it succeeds (exit 0) or `timeout_s` elapses
(exit 1, with a single explicit stderr line naming host, port and elapsed seconds). Do not use a
fixed `sleep` as a substitute for polling. Print at most one progress line per
`UPSTREAM_WAIT_PROGRESS_EVERY` seconds (default 60) — launchd never rotates these logs, so a
per-poll line is unacceptable. `nc -z -G 2 -w 2` was confirmed live on this machine: exit 0
against the open `:4000`, exit 1 against a refused `:1`.

`#!/bin/bash`, `set -euo pipefail`. macOS `/bin/bash` is 3.2 — indexed arrays only, no `declare -A`.

**Header comment block, in this order:**
1. This file is `ProgramArguments[1]` of `~/Library/LaunchAgents/com.ohama.kanban.plist`. It is
   never called by hand except for testing.
2. **THE CWD RULE** (`docs/headless-wrapper.md` §6): the OS-level process cwd must already be
   inside `workspace/ALLOWED_REPOS.json` or Bun/Node dies during startup with a path-less generic
   error that looks exactly like a sandbox tightening. The plist sets `WorkingDirectory` AND this
   script `cd`s and asserts — belt and braces, because the plist alone silently fails if the
   directory is missing.
3. **Never `kill`/`pkill` this service; never `launchctl load`/`unload`/`kickstart`.** Restart is
   `phase-02/infra/restart_service.sh com.ohama.kanban 3484`; take-down is
   `launchctl bootout gui/$(id -u)/com.ohama.kanban`.
4. **Never invoke `cline kanban`.** That subcommand has its own auto-install fallback
   (`npm install -g kanban@latest`) and is a silent drift vector off the pinned 0.1.70. Always the
   standalone `$KANBAN_BIN`.
5. **Never widen the sandbox from here.** `EXTRA_ALLOW_PATHS` is empty and this wrapper does not
   need it.

**Body:**
1. `source phase-05/services/config.env`; `source phase-01/config/cline-invocation.env` (paths via
   `BASH_SOURCE`-derived `PROJECT_ROOT`).
2. `export CLINE_NO_AUTO_UPDATE=1` and `export KANBAN_NO_AUTO_UPDATE=1` defensively — the plist
   also sets both, but a hand-run wrapper must be equally protected. `KANBAN_NO_AUTO_UPDATE=1` is
   kanban's own, separate auto-update gate (confirmed via `strings`: `env2.KANBAN_NO_AUTO_UPDATE === "1"`);
   `CLINE_NO_AUTO_UPDATE` does not cover it.
3. `mkdir -p "$SERVICE_LOG_DIR" "$SANDBOX_WORKDIR"` then `cd "$SANDBOX_WORKDIR"`.
4. Assert `$PWD` is a prefix-match of some `repos[]` entry in `$ALLOWED_REPOS_JSON` using the same
   `python3` idiom as `phase-04/run_headless.sh` step 5. On failure: one explicit stderr line
   naming `$PWD` and the allow-list file, then `exit 1` (KeepAlive + ThrottleInterval retries; it
   will not spin, and it will not silently run outside the whitelist).
5. Bounded upstream wait:
   `bash "$SCRIPT_DIR/wait_for_port.sh" "$UPSTREAM_WAIT_HOST" "$UPSTREAM_WAIT_PORT" "$UPSTREAM_WAIT_TIMEOUT" "$UPSTREAM_WAIT_INTERVAL"`.
   On non-zero: print ONE line saying the upstream was still unreachable after N seconds and that
   launchd will retry the whole cycle after `ThrottleInterval`, then `exit 1`. This is the SVC-04
   mechanism: the wrapper, not launchd, absorbs the flashnext-not-up window, so the retry cadence
   is roughly one process spawn per (timeout + ThrottleInterval), not a tight loop.
6. Final line, `exec` so the supervised pid IS the kanban process (pid is preserved through
   `exec` → `run_sandboxed.sh`'s own `exec sandbox-exec` → kanban), which is what makes the
   SVC-03 kill test and the anti-orphan check meaningful:
```
exec "$PROJECT_ROOT/phase-03/sandbox/run_sandboxed.sh" -- \
  "$KANBAN_BIN" --no-open --host "$KANBAN_HOST" --port "$KANBAN_PORT"
```
   `--no-open` (no browser under launchd). `--port 3484` pinned explicitly, never `auto`.
   Deliberately NOT passed: `--no-passcode` (kanban auto-generates a remote-access passcode by
   default; Phase 6's NET-02 will build ON that, not around it), `--skip-shutdown-cleanup`,
   `--https`/`--cert`/`--key` (Phase 6), `--update`. Write a comment saying so for each.

  <name>Task 3: phase-05/services/run_telegram_service.sh</name>
  <files>phase-05/services/run_telegram_service.sh</files>
  <action>
Same shell discipline and the same header items 1-3 and 5 as Task 2, plus two more that are
specific to this surface and must be the most visible text in the file:

**A. `cline connect telegram` SELF-DAEMONIZES by default.** Without `-i/--interactive` it forks a
detached child (`CLINE_TELEGRAM_CONNECT_CHILD=1`), prints `[telegram] starting background
connector pid=<N>`, and the parent — the process launchd is supervising — exits almost
immediately. Under `KeepAlive` that either crash-loops the parent or leaks a NEW orphaned,
unsupervised bot child every `ThrottleInterval`. **`-i` is mandatory here and must never be
removed.** (Confirmed via `strings` on the pinned 3.0.53; the same base-class behavior exists for
every other `connect <channel>` subcommand.)

**B. The `--auto-approve false` posture, translated onto the surface that actually exists.**
`--auto-approve <boolean>` is a flag of the one-shot `cline <prompt>` mode (Phase 4), NOT of
`cline connect telegram` — copying it here would be an ignored/invalid flag that silently leaves
tools ENABLED, the exact opposite of the intent. The faithful translation on this surface is
**`--no-tools`** (tools are enabled by default; `--hook-command` is the only other approval
surface and it is mutually exclusive with `--allowed-user-id`). This is the settled decision
carried over from `docs/headless-wrapper.md` §4/§8: the connector comes up, self-recovers and
survives reboot, but stays intentionally inert for tool-using prompts. Do not add a switchable
flag; revisiting the posture is Phase 6's, and it is a human decision.

**Body:**
1. Source `config.env` then `cline-invocation.env`; `export CLINE_NO_AUTO_UPDATE=1` and
   `export KANBAN_NO_AUTO_UPDATE=1`.
2. `mkdir -p "$SERVICE_LOG_DIR" "$SANDBOX_WORKDIR"`; `cd "$SANDBOX_WORKDIR"`; same python3
   cwd assertion as the kanban wrapper.
3. **The empty-token idle branch — before anything else that could cost anything.**
   `TOKEN="${TELEGRAM_BOT_TOKEN:-}"`. If empty:
   - print exactly ONE stderr line saying the token slot is empty, the service is registered but
     intentionally inert, and that **cline is NOT being invoked**;
   - print the injection recipe on a second line: set `TELEGRAM_BOT_TOKEN` in
     `phase-05/plists/com.ohama.telegram-connect.plist`'s `EnvironmentVariables`, re-run
     `phase-05/services/install_services.sh com.ohama.telegram-connect`, then
     `phase-02/infra/restart_service.sh com.ohama.telegram-connect none`. Never hand-edit
     `~/local-llm-settings/`;
   - then block **without spinning and without exiting**:
     `while :; do /bin/sleep "$IDLE_SLEEP_SECONDS" || /bin/sleep 60; done`.
     **Do NOT use `sleep infinity`** — verified live on this machine, macOS `/bin/sleep` rejects
     it (`usage: sleep number[unit]`) and returns instantly, which would turn this branch into a
     100%-CPU spin. Numeric seconds only. Exiting is equally wrong: `exit 0` under
     `KeepAlive: true` relaunches immediately, which is a real crash loop by definition, and
     `exit 1` is the same thing with a longer period.
   Never generate, guess, or fabricate a token. The slot stays empty in this phase.
4. If the token IS non-empty: bounded upstream wait (identical to the kanban wrapper), then
```
exec "$PROJECT_ROOT/phase-03/sandbox/run_sandboxed.sh" -- \
  "$CLINE_BIN" connect telegram -k "$TOKEN" -i --no-tools \
  -P "$CLINE_PROVIDER" -m "$CLINE_MODEL" --cwd "$SANDBOX_WORKDIR"
```
   `-i` and `--no-tools` as literal adjacent tokens (they are grep-verified). Add a comment that
   Phase 6 must add `--allowed-user-id <digits>` here — confirmed via `strings` that cline 3.0.53
   does NOT itself refuse to start without it, so Phase 6's criterion 4 will need wrapper-level
   enforcement, not a CLI guarantee.
  </action>
