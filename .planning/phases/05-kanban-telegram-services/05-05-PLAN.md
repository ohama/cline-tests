<objective>
Register the second always-on service — the Telegram connector — with its token slot deliberately
empty, and prove both services coexist.

Purpose: this is the service that would crash-loop forever if it were registered naively. An
empty token makes `cline connect telegram` throw synchronously, and a missing `-i` makes it
self-daemonize so launchd supervises a parent that has already exited while an orphan bot runs
unsupervised. Neither happens here, because the wrapper (proven in 05-03) idles instead — and this
plan verifies that under launchd rather than assuming 05-03 carries over.

Output: the staged plist, a live `com.ohama.telegram-connect` service, and both-services-up evidence.

**Budget: ZERO `cline` invocations.** The empty-token service never invokes cline, and this plan
must confirm that from the outside (`pgrep`), not just from the code.

**Never ask for, generate, or fabricate a Telegram bot token.** The slot stays empty. The service
is verified up to exactly the point the token would be required, and the injection recipe is
recorded for the human to use later.

**Process hygiene:** the only `kill` is the single deliberate SVC-03 KeepAlive test on the exact
pid `launchctl print` reports. Take-down is `launchctl bootout`.
</objective>

  <files>phase-05/plists/com.ohama.telegram-connect.plist</files>
  <action>
Same house style as the kanban plist (alphabetical keys, tab indentation, `KeepAlive` a bare
boolean, `RunAtLoad` true, explicit `WorkingDirectory`):

```
EnvironmentVariables:
    PATH                  = /opt/homebrew/bin:/usr/bin:/bin:/usr/sbin:/sbin
    CLINE_NO_AUTO_UPDATE  = 1
    KANBAN_NO_AUTO_UPDATE = 1
    TELEGRAM_BOT_TOKEN    = ""            <-- deliberately EMPTY. This is the injection slot.
KeepAlive             = <true/>
Label                 = com.ohama.telegram-connect
ProgramArguments      = [ /bin/bash, /Users/ohama/projs/cline-tests/phase-05/services/run_telegram_service.sh ]
RunAtLoad             = <true/>
StandardErrorPath     = /Users/ohama/.cline/logs/telegram-connect.err
StandardOutPath       = /Users/ohama/.cline/logs/telegram-connect.log
ThrottleInterval      = 30
WorkingDirectory      = /Users/ohama/projs/cline-tests/workspace/scratch-repo
```

The empty `TELEGRAM_BOT_TOKEN` string must be a real `<string></string>` entry, not an omitted key
— it is the documented slot, and the wrapper's `${TELEGRAM_BOT_TOKEN:-}` treats both the same way,
but an explicit empty entry is what makes the slot discoverable by whoever injects the real token.

Both auto-update gates are set even though this plist runs `cline` rather than `kanban`: defence in
depth, and it keeps the two plists structurally identical apart from the token key. (Note that
`check_versions.sh` Check C matches this plist on the `"cline"` branch regardless, because the
wrapper path itself lives under `/Users/ohama/projs/cline-tests/`.)

Do not add `--allowed-user-id` anywhere yet — that is Phase 6's NET criterion 4, and cline 3.0.53
does not itself refuse to start without it, so Phase 6 will need wrapper-level enforcement.

Then install it (files only, no bootstrap):
`bash phase-05/services/install_services.sh com.ohama.telegram-connect` → `installed:`, and a
second run → `unchanged:`.

   - `launchctl print gui/$(id -u)/com.ohama.telegram-connect > launchctl-print.txt` →

   - `ps -o pid=,ppid=,%cpu=,args= -p <pid> > supervised-proc.txt` → args show
     `run_telegram_service.sh`, `%cpu` under ~2.
3. **Orphan sweep — the failure this whole design exists to prevent.** Record into
   `$RES/orphan-sweep.txt`:
   - `pgrep -f 'connect telegram' | wc -l` is `0`;
   - `ps -Ao pid=,args= | grep -c '[c]line'` shows no cline process attributable to this service;
   - the connector log contains no `starting background connector pid=` line (that string is the
     self-daemonize signature; it must never appear while the token is empty, and with `-i` it
     must never appear at all).
   Take three samples over ~60s so an accumulating leak would be visible.
4. **Log quietness:** line counts of `~/.cline/logs/telegram-connect.{log,err}` at the start and
   end of a 60s window are identical apart from the single startup notice. Note in the README that
   launchd never rotates these files and that the steady-state growth of this one is
   one notice per service start.
5. **SVC-03 / criterion 2:** `kill -TERM <the exact pid from launchctl>` (never `-9`, never
   `pkill`). Poll for a NEW pid with `state = running`, then confirm that new pid is unchanged 15s
   later. Record `PID_BEFORE`/`PID_AFTER`/elapsed into `$RES/svc03.txt`, with an explicit line
   saying this kill is the criterion-2 test and not the take-down path.
6. **Take-down path, tested:** `launchctl bootout gui/$(id -u)/com.ohama.telegram-connect`, confirm
   `launchctl print` fails for the label and stays failing for 30s and that the orphan sweep is
   still zero, then bring it back with
   `bash phase-02/infra/restart_service.sh com.ohama.telegram-connect none --timeout 120`.
7. Post-gate: `verify_no_regression.sh` → `INF03: PASS`, `pids-after.txt` == `pids-before.txt`
   (kanban's pid included — bringing the connector up must not disturb it).
  </action>
