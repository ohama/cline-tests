<objective>
Prove, by hand and outside launchd, that both wrappers behave the way SVC-03/SVC-04 need them to —
BEFORE a single always-on service is registered on this machine.

Purpose: the worst outcome available in this phase is leaving a crash-looping service on the
user's machine. The cheapest way to guarantee that never happens is to observe both failure modes
in the foreground first, where taking the process down is trivial and nothing is supervised.
This plan also answers research Open Question 2 (kanban/telegram local RPC port coexistence) with
a real port inventory, and pre-checks the one design decision that could kill both services at
startup: the log path the plists will hand to launchd.

Output: one timestamped evidence directory under `phase-05/results/` with a README.md verdict.

**Budget: ZERO `cline` invocations.** The telegram wrapper is exercised only on its empty-token
idle path, which by construction never reaches cline. `kanban` is launched for real (it is a
separate binary; it does not touch `~/.cline/data/settings/providers.json`).

**Process hygiene:** every process in this plan is one this plan started in the foreground and is
NOT supervised by launchd. Taking those down with `kill <that exact pid>` is correct and is NOT a
violation of the house rule — that rule ("never `kill`/`pkill` a service") governs launchd-managed
jobs, whose take-down path is `launchctl bootout`. Never use `pkill` or any pattern-matched kill
here; always the specific pid this plan recorded. Before finishing, confirm no process this plan
started is still alive.
</objective>

**(a) Hard-down: the upstream port is refused.**
```
FLASHNEXT_PORT=1 FLASHNEXT_HEALTH_URL=http://127.0.0.1:1/health \
UPSTREAM_WAIT_TIMEOUT=30 UPSTREAM_WAIT_INTERVAL=5 \
  bash phase-05/services/run_kanban_service.sh >"$RES/deadport.log" 2>"$RES/deadport.err" &
WPID=$!
```
While it runs, sample `ps -o pid=,%cpu=,etime=,args= -p $WPID` at ~5s intervals into
`$RES/deadport-ps.txt`, and confirm with `lsof -nP -iTCP:3484 -sTCP:LISTEN` that nothing is
listening on 3484 (kanban must never have been launched). Wait for it to exit; record the exit
code in `$RES/deadport-rc.txt`.

Required observations (all recorded, all asserted):
- exit code 1, at roughly 30s (the bounded timeout), not instantly and not never;
- `%cpu` stays under ~2 on every sample — a poll, not a spin;
- `deadport.err` contains at most 2 progress lines plus one timeout line naming the failing stage

- 3484 never listened; `ps` shows no `kanban` process was ever spawned.

**(b) The decisive case the criterion actually describes: a listener is up but flashnext is NOT
ready.** This is the failure a bare TCP probe of litellm's `:4000` could not distinguish — litellm
binds its listener whether or not the 104 GiB model has loaded, which is precisely the boot-order
situation and the "flashnext down, litellm untouched" situation. Emulate the accepting-but-wrong
backend with a throwaway HTTP server rather than by disturbing anything real:
```
FAKEPORT=8999   # assert free first: `lsof -nP -iTCP:$FAKEPORT -sTCP:LISTEN` must be empty,
                # same live-verification discipline every other port in this phase got.
                # If it is taken, pick another free high port and record which.
( cd "$(mktemp -d)" && python3 -m http.server "$FAKEPORT" --bind 127.0.0.1 ) &
HTTPPID=$!
FLASHNEXT_PORT=$FAKEPORT FLASHNEXT_HEALTH_URL=http://127.0.0.1:$FAKEPORT/health \
UPSTREAM_WAIT_TIMEOUT=20 UPSTREAM_WAIT_INTERVAL=5 \
  bash phase-05/services/run_kanban_service.sh >"$RES/notready.log" 2>"$RES/notready.err" &
WPID2=$!
```
The TCP stage now SUCCEEDS (the port genuinely accepts) and the health stage must still reject it.
Sample `ps -o pid=,%cpu=,etime=,args= -p $WPID2` at ~5s intervals into `$RES/notready-ps.txt`,
exactly as case (a) does — this is the run where a missing tail-sleep in the poll loop would show
up as subprocess churn, so it must be measured, not assumed.
Required: exit code 1 at ~20s, every `%cpu` sample under ~2, kanban never launched, 3484 never
listening, and the timeout line naming the **health** stage — not the TCP stage — as the one that
failed.

`LITELLM_MODELS_URL=http://127.0.0.1:$FAKEPORT/` (a 200 whose body does not contain `flashnext`),
sampling `%cpu` into `$RES/notready-ps.txt` the same way, and require exit 1 with the **alias**
stage named. Then `kill $HTTPPID` (that exact pid) and confirm `$FAKEPORT` is free again.
Record both in `$RES/notready-rc.txt` / `$RES/notready-stage.txt`. Without this case, the
must_have "the wait absorbs the flashnext-not-ready window" would be asserted but not evidenced.

**(c) The launchd-shaped stdio pre-check — do this in the SAME kanban run as (b).**
